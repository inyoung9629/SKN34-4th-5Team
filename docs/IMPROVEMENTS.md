# 프로젝트 개선 후보

## 4단계 코스 30초 내외 목표

2026-10-12 후속 요청으로 일반 추천의 신규 평점·실내 조사는 응답 대기에서 분리하고, 메뉴·브랜드·방문 순서·날짜·출발지와 확인된 휴무 검사는 유지한다. 외부 장소 갱신 워커와 정확히 같은 검색의 사전 준비 재사용을 추가했다. 단순 수정의 도구 선택·최종 재작성 중복을 줄이고, 술집 검색 결과의 일반 음식점을 임의로 술집으로 분류하던 문제를 수정했다. 설정·품질 범위·실측 방법은 [일반 추천 속도와 필수 조건 유지 기록](test_results/course-balanced-latency-20261012.md)에 정리한다.

실제 업종까지 대조한 광주·잠실 생성/수정 20건은 요청한 구성 검사에 모두 통과했고, 19건은 30초 이내·1건은 41.204초였다. 신규 생성 중앙값은 18.668초, 수정은 9.835초다. 이후 발견한 공개 지도 데이터의 술집 세부 업종 누락도 최초 저장·복원으로 보완했으며, 추가 4건은 13.637~15.843초에 장소·브랜드·기존 체류시간 보존까지 통과했다. 운영 캐시 사용 표본으로, 모든 요청의 30초 완료 보장이나 고정 캐시 A/B 결과는 아니다.

2026-10-12에는 광주 자장면→내부 간식→경기→술집→산책 요청에서 명확한 메뉴의 추가 LLM 해석, 내부·외부 혼합 코스의 전체 후보 선행 검증, 동일 지점 중복 검증을 줄였다. 최종 엔진 재실행은 **23.757초**, 계측한 ChatOpenAI 호출은 변경 전 5~6회에서 2회였다. 중간 재실행은 62.110초·74.687초였으므로 캐시·외부 원문 응답의 편차가 남으며 고정 상태의 단축률이나 전체 HTTP 30초 보장으로 해석하지 않는다. 코스 회귀 503개 중 501개 통과, 기존 메뉴 데이터 불일치 2개를 변경 전 코드에서도 재현했다. 조건·품질·근거리 우선 기준과 실제 결과는 [추가 해석·중복 검증 개선 기록](test_results/course-duplicate-verification-20261012.md)에 정리했다.

2026-10-11 사용자가 **4단계 코스는 늦어도 30초 내외**를 요구했다. 속도를 위해 필수 조건·메뉴 원문·품질 검사를 생략하거나 미완성 코스를 성공 처리하지 않는다. 복합 질문의 기존 답변 모델은 유지한다.

코스 화면의 새 요청을 전문 도구에 직접 전달하고, 코스 지시와 장소 조건을 분리하며, 실제 방문 위치에서 가까운 유효 근거를 우선 확인하도록 수정했다. 원문 조회는 최대 두 건씩 겹치고 중복 조회·해석을 줄였다. 로컬 실제 HTTP 시험의 식당→카페→경기→산책 5종은 **9.738~16.306초, 평균 12.606초**, 산책 대신 주차 호텔을 넣은 추가 1건은 **22.131초**였다. 코스·답변 저장, 업종·메뉴 원문 대조와 회귀 451개를 확인했다.

**모든 상황의 최대 30초는 아직 충족하지 못했다.** 동적 품질 캐시가 빈 양식 요청은 45.919초였다. 구장 내부 식사를 추가한 5개 방문지 5종은 평균 19.956초, 최대 35.210초였다. 외부 식당·카페의 새 원문 조사와 일부 메뉴 재조사가 남아 있다. 10월 11일 당시 사전 갱신 워커는 숙박 원문에만 적용됐다. 음식점·카페 갱신과 일반 추천 기준의 후속 변경은 위 10월 12일 기록에 구분한다.

최종 일반 4단계 1건 평균 API 비용은 **$0.000544085**, 호텔 1건은 **$0.001722674**였다. 이번 중간·재시험 68건의 API 비용은 **$0.272402840**다. 서버 운영 비용은 별도이며 운영 배포는 하지 않았다. 입력별 결과·비용 발생 위치·느린 표본을 [4차 속도·비용 검증](test_results/course-latency-round4-20261011.md)에 보존한다.

## Chrome 단독 숙박 검색으로 유료 검색 호출 줄이기

후속 [출발 핀·식당 5종·부분 변경 시험](test_results/course-scenarios-20261011.md)에서는 다섯 방문지 새 코스가 **63.6~80.1초, 평균 72.2초**였다. 아래 27~33초 및 25.7초는 경기→숙박 두 장소 표본이며 일반적인 코스 전체의 시간 보장이 아니다. 본 시험 20건은 구조·저장 검사 19건 성공, 컴포즈 1건 보류 후 별도 재시험 성공이었다. 출발 핀 참조 해석과 숙박 편집의 판정 전달을 보완했다. 다음 후보는 다중 장소의 중복 검증 감소와 독립 조회 병렬 처리이며, 모델·원문 검증 기준은 유지한다. 자장면 메뉴 탐색에는 유료 검색 1회가 발생해 숙박과 구분하여 비용에 포함했다.

2026-10-11 사용자 요청으로 코스 생성의 숙박 원문 수집을 **서버 Chrome 단독으로 변경하고 로컬 Docker에서 코스 생성까지 검증**했다. 운영 서버 배포와 동시 사용자 부하 검증은 별도다. 상세 결과는 [숙박 코스 통합 검증](test_results/lodging-chrome-integration-20261011.md)에 기록한다.

같은 날 후속 요청으로 지연 시간을 줄였다. 고정 대기를 DOM 준비·안정화 확인으로 바꾸고, 검증한 원문을 숙소별로 재사용하며, 조건 근거를 원문 줄 번호로 선택하도록 수정했다. 숙박만 요청한 코스의 불필요한 장소 검색도 생략한다. 모델과 주소·유형·후기 검증 기준은 유지했다. [속도 개선 검증](test_results/lodging-latency-20261011.md)에 캐시 유무별 전체 채팅 시간과 품질 결과를 기록한다. 아래 초기 실험의 수치는 변경 전 측정값이다.

1차 개선의 최종 캐시 없는 전체 채팅은 **94.266초 → 44.859초**, 약 52% 단축됐다. 실제 코스 생성·저장·최종 답변 10개 검사와 회귀 336개를 통과했다. 확인된 숙박 조건을 최종 답변이 미확인으로 설명하던 문제도 판정 전달을 보완해 재검증했다. 운영 지연 시간·정확도를 보장하는 대규모 평가는 아니다.

후속 요청으로 **새 코스 해석과 숙박 조건 추출을 한 번으로 통합하고, 코스만 요청한 경우 검증된 원문을 바로 반환**한다. 복합 질문·지정 형식·첨부·기존 코스 수정에는 기존 답변 모델을 유지한다. 새로 수집한 첫 숙소가 성공한 표본은 32.828초와 27.062초였고, 두 후보의 차단/부분 수집 후 세 번째를 채택한 표본은 51.313초였다. 마지막 재작성 대기는 기존 8.828초에서 0.016~0.031초로 줄었다. 복합 질문의 실제 코스·추가 답변·저장, 해석 5종, 백엔드 회귀 401개를 확인했다. [2차 개선 검증](test_results/course-latency-round2-20261011.md)에 캐시 적중 여부와 남은 변동 원인을 구분해 기록한다.

### 적용한 동작

3차 개선에서는 새 요청 해석 중 경기·구장·카카오 후보를 병렬로 준비하고, 별도 `lodging-warmer`가 자주 쓰는 숙소의 유효 원문을 사전 갱신한다. 사용자 브라우저 조회가 들어오면 갱신을 중단해 양보한다. 별도 워커가 준비한 캐시를 사용한 첫 코스 생성·저장은 **25.672초**, 원문 재사용은 **39ms**였다. 복합 질문은 기존 모델을 유지했고 회귀 436개를 통과했다. 명시한 호텔 유형이 통합 해석에서 빠지는 경우에는 기존 전용 해석기로 보완한다. [병렬 처리·사전 갱신 검증](test_results/course-latency-round3-20261011.md)에 실제 표본, 작업량, 한계와 운영 방법을 기록한다.

- 숙박 조회에서 OpenAI 웹 검색과 JEV 브라우저 에이전트를 호출하지 않는다. 조건 추출·원문 해석 LLM은 유지하므로 코스 전체의 API 비용이 0인 것은 아니다.
- Compose 백엔드는 인증된 `chrome_lodging` MCP 도구로 서버의 Chrome을 실행한다. 사용자는 PC·모바일에서 Chrome을 설치할 필요가 없다. JEV의 다른 도구는 같은 서버에 유지된다.
- 한 번에 숙소 한 곳을 조사하고 조건 충족 시 중단한다. 전체 탐색 예산 90초, 브라우저 한 건 최대 45초, 결과 캐시 6시간을 유지한다. 실패는 유료 검색으로 재시도하지 않으며 실패·부분 수집은 캐시하지 않는다.
- 호텔 요청이면 카카오 업종이 호텔인 후보부터 조사한다. 업종은 검색 순서에만 쓰고, 최종 판정은 NOL의 이름·주소·페이지 분류·시설·날짜가 있는 후기 근거로 한다.
- 실제 코스 검증에서 발견한 부정 문장의 시점 해석 오류를 함께 수정했다. ‘경기 후 숙박, 경기 전 다른 장소는 넣지 말고 숙박만 포함’ 요청의 숙박을 경기 뒤에 한 번 배치한다.

### 확인한 흐름과 결과

JEV와 검색·브라우저 조작용 모델 API를 호출하지 않고, Python·Node 표준 라이브러리와 Chrome DevTools Protocol로 다음 흐름을 실행했다.

1. 테스트용 Chrome 프로필에서 NOL 검색창에 정확한 숙소명을 입력하고 검색 버튼을 누른다.
2. 일반 검색 결과에서 숙소명이 일치하는 실제 상세 링크와 숙소 ID를 확보한다.
3. 숙소 ID를 유지해 관찰된 국내숙소 상세 주소 형식인 `/stay/domestic/{id}?verticalCategory=PRODUCT_CATEGORY_KOREA_ACCOMMODATION`을 사용한다.
4. 별도 Chrome 조회 세션에서 탭을 활성화하고 화면을 렌더링한 후 보이는 DOM 본문을 읽는다.
5. 숙소명·주소·평점·후기 수·시설과 날짜가 있는 일부 후기의 존재를 확인한다.

Windows의 일반 Google Chrome 154에서 글래드 강남 코엑스센터 2회, 호텔 리베라 청담 1회로 최종 흐름을 검증했다. **3회 모두 성공**, 소요 시간은 각각 32.656초, 28.656초, 30.813초였다. 검색 및 모델 API 호출은 0회로 해당 API 비용은 $0이었다. Codex 사용료, 컴퓨터·서버 운영 비용, 향후 조건 판정용 LLM 비용은 이 수치에 포함하지 않는다.

자동완성에서 바로 상세로 진입하거나 검색 결과의 상세 링크를 같은 세션에서 열면 두 숙소 모두 서비스 이용 불가 화면이 나타났다. 초기 본문 읽기에는 숙소 화면이 보이는데 하단 링크만 추출되는 문제도 있었다. 최종 흐름에서는 세션 분리, 상세 URL 형식 변경, 렌더링 후 본문 읽기를 함께 적용했다. 각 변경의 효과와 접속 오류 원인은 개별적으로 입증하지 않았다.

### 초기 실험의 한계와 운영 확인 사항

- **속도:** 29~33초는 숙소 한 곳의 검색·수집 시간이다. 아래 3종 비교에서 OpenAI와 Chrome이 모두 성공한 두 곳의 평균은 각각 30.133초와 28.969초로 비슷했다. 현재 속도로 4곳을 순차 조사하면 단순 계산상 약 2분으로, 기존 숙박 검증의 90초 탐색 예산을 넘을 수 있다.
- **동시 요청과 운영 비용:** 검색·조회 세션을 실행하는 데 CPU·메모리가 든다. JEV도 브라우저를 실행하므로 브라우저 비용 자체는 공통이다. 서버 적용 시 작업 수 제한·취소·타임아웃·프로세스 정리와 기존 JEV의 접속 제한 및 격리 기능을 검토해야 한다.
- **사이트 변경과 접속 실패:** 고정된 검색창·버튼·URL·본문 구조에 의존한다. 화면이나 접근 정책이 바뀌면 코드 수정이 필요하며 오류 화면이나 부분 본문을 성공으로 처리하면 안 된다.
- **데이터 검증:** 후속 비교까지 정확한 숙소명 세 개를 시험했다. 카카오 주소와 대조해 동명 숙소·다른 지점을 구분해야 한다. 본문 수집만으로 무료 주차·조용함 같은 요청 조건을 확정하지 말고 기존 조건 판정 및 후기 근거 검증을 유지한다. 일부 후기의 존재 확인은 충분한 최신 후기 검증과 다르다.
- **환경과 표본:** 아래 비교는 세 숙소의 짧은 Windows 실험이다. 이후 로컬 Docker의 Google Chrome에서도 수집과 코스 생성을 확인했지만 운영 서버의 성공률·동시 부하는 측정하지 않았다. 날짜별 가격·객실 재고·예약 가능 여부는 검증하지 않는다.

수집한 원문은 조건 해석과 방문 가능 여부 검사에 재사용한다. 이후 운영 환경에서는 다양한 숙소명·동명 지점의 검색 성공률, 동시 요청 시 `busy` 비율과 자원 사용을 추가로 측정한다. 유료 검색 대체 경로는 현재 없다.

### 같은 숙소 3건씩 비교한 결과

2026-10-11에 글래드 강남 코엑스센터·호텔 리베라 청담·신라스테이 삼성을 세 방식으로 각각 새로 실행했다. 총 9건의 [비교 보고서](test_results/lodging-search-comparison-20261011.md)에 판정 기준·건별 시간·비용·자원 측정을 기록했다.

- 상세 원문 확보: 기존 OpenAI 2/3건, JEV + Chrome 0/3건, Chrome 단독 3/3건. OpenAI의 나머지 한 건은 URL·일부 정보는 확보했으나 독립 원문 조회가 403으로 실패했다.
- Chrome 단독 평균은 28.964초, 검색·조작용 API 비용은 $0이었다. JEV는 서비스 이용 불가 화면에서 모두 중단했고 3건 API 비용 합계는 $0.014278304였다.
- OpenAI는 확인된 사용량 기준 최소 약 $0.02438이다. 초기 두 건에 비용 계측 누락이 있어 전체 비용이나 정확한 절감률은 계산하지 않는다.
- 실행별 최고 로컬 작업 집합의 평균은 OpenAI 167.3 MiB, JEV 1,576.0 MiB, Chrome 1,321.3 MiB였다. 공유 메모리 중복 합산 가능성이 있고 원격 API 서버 자원은 제외한 값이다.
- JEV의 자동완성 클릭 흐름과 Chrome 단독의 일반 검색·별도 세션 흐름이 달랐다. Chrome 단독은 원문 수집까지만 하므로 기존 조건 해석까지 포함한 전체 성능의 우열을 확정하지 않는다.
