# 코스 생성 30초 목표: 중복 호출·원문 조회 개선

2026-10-11 사용자가 4단계 코스의 최대 지연을 30초 내외로 요청했다. 최종 코드의 **식당 → 카페 → 경기 → 산책** 5종 시험은 **9.738~16.306초, 평균 12.606초**, 구조·저장 검사 5/5 통과였다. 출발 핀은 방문지 수와 별도로 보존한다.

**30초의 절대 상한을 달성한 것은 아니다.** 같은 최종 코드에서 동적 평점·실내 판정 캐시만 빈 별도 경로로 실행한 양식 코스는 **45.919초**였다. 정적 검증 목록·DB 메뉴 근거 등은 남겨 둔 시험이므로 모든 캐시가 없는 상태도 아니다. 외부 원문을 처음 조사해야 하는 경로의 상한은 남은 과제다. 30초에 미완성 코스를 성공 처리하거나 메뉴·품질 검증을 생략하는 제한은 넣지 않았다.

이전 [20건 실측](course-scenarios-20261011.md)과 동일한 **외부 식당 → 카페 → 구장 내부 식사 → 경기 → 산책** 다섯 방문지 및 부분 변경은 별도로 구분한다. 서로 다른 방문지 수의 평균을 전후 개선율로 계산하지 않는다.

## 30초와 70초의 측정 차이

과거 27~33초의 원본 요청은 “경기 전 다른 장소는 넣지 말고, 경기 관람과 숙박만 포함해줘”였다. `latency-v2-release-warm.json`은 잠실야구장·글래드 강남 코엑스센터 두 장소로 27.093초, `latency-v2-final-cold.json`도 같은 두 장소로 32.875초다. 이전 문서의 27.062·32.828초는 SSE 완료 이벤트까지, 여기의 값은 응답 스트림 종료까지라 수십 ms 차이가 있다.

이번 측정은 출발 핀을 별도로 지정하고 외부 식당·카페·구장 내부 식사·경기·산책 다섯 장소를 만드는 요청이다. 2곳과 5곳의 수치를 같은 입력의 전후 성능으로 설명한 것은 부정확하다. 확인된 기록에서 5곳 코스가 30초에서 70초로 회귀했다고 입증되지는 않았다. 별도의 동일 조건 30초 기록이 존재하지 않는다고 단정하는 것도 아니다.

## 변경한 처리

1. 조건 전체가 알려진 긍정형 업종·브랜드 표현인 경우 카카오 후보의 실제 업종 경로·상호로 판정한다. 상호에 ‘일식’이 있다는 이유만으로 일식 업종으로 승인하지 않는다. 돈카츠·돈까스, 자장면·짜장면의 제한된 표현은 같은 메뉴 요구로 해석하지만 **메뉴 판정에는 실제 원문 근거가 여전히 필요**하다. 부정·선택·희망·후기·알 수 없는 표현은 기존 모델 경로로 보낸다. 편집 계획의 요약만으로 사용자의 원문을 덮어쓰지 않는다.
2. 음식점·카페 후보의 검색 목록과 지점 원문 읽기를 최대 두 건씩 겹친다. 후보 순서와 주 스레드의 모델 판정·결과 반영 순서는 유지한다. 같은 URL은 한 번만 읽고 요청 내에서 공유한다.
3. 지역명+지점명 검색에서 상호·주소·평점이 일치하는 원문을 찾으면 지점명 단독의 추가 검색은 생략한다. 첫 검색이 다른 지점을 반환하면 기존 두 번째 검색을 수행한다.
4. 모델이 공통 조건으로 반환한 ‘모든 이동은 도보’, ‘각 장소는 한 곳씩’ 같은 제한된 코스 지시는 장소의 속성으로 재심사하지 않는다. 기존 경로·방문지 구성 코드에서 처리한다. ‘도보 10분 이내’, 접근성·휠체어, 선택·부정 표현은 이 생략 경로에 들어가지 않는다.
5. 출발 핀이 있는 첫 명시 방문의 넓은 구장 주변 조사를 실제 출발지 조사와 중복 실행하지 않는다. 외부 장소만 있는 코스는 각 방문지의 실제 앞 지점이 정해졌을 때 조건을 검증한다. 내부 음식점이 있는 코스는 기존 별도 선별을 유지한다. 경로 구성에 실패해 모델 경로로 복귀할 때도 조건 필터를 적용한다.
6. 알려진 긍정 조건은 실제 카카오 조회 후 가까운 검증 완료 후보를 먼저 확인한다. 거리 한도는 800m와 가장 가까운 후보 거리+250m 중 작은 값이다. 메뉴·업종·방문 가능 시각·경계·중복·방향 검사를 모두 통과해야 채택한다. 검증 자료가 없는 후보를 승인하지 않으며, 실패 시 새 원문 조사로 복귀한다. 실패한 사전 확인은 정상 검색을 막는 부정 캐시·재시도 대기를 만들지 않는다. 따라서 선택 가능한 대안을 전부 새로 조사하지는 않지만, 선정 장소의 필수 근거 기준은 유지한다.
7. 코스 만들기 화면에서 허용 판정과 새 코스 분류가 끝났고 구장이 정해진 요청은 `ask_course`로 바로 전달한다. 원문 전체를 넘기고 기존 도구 실행 제한·계측·조건 해석을 유지한다. 이를 위해 쓰던 첫 전달 모델 호출을 생략한다. 추가 질문·첨부·형식 요청 등은 기존 경로를 유지하고, 코스 해석에서 복합 질문으로 판정하면 기존 최종 답변 모델로 이어진다.

숙박 추가 시험에서 방문 표현과 조건 배열에 ‘구장 밖’이 중복되는 사례도 확인했다. 외부 방문 표현을 보존하고 기존 구장 경계 정책이 검사하는 정확한 중복 토큰만 제거했다. ‘구장 밖 도보 10분 이내’ 같은 추가 제약은 유지한다. 숙박·산책에는 음식점 품질 조사 재사용 여부를 해석하는 호출을 하지 않는다.

모델 종류, 실제 메뉴 근거 확인, 상호·주소 대조, 평점·후기·실내 판정, 방문 시각 검사는 유지했다. 원문 조회의 전체 요청 수·기한·호스트별 간격·robots·접근 차단을 함께 관리한다. 복합 질문 및 코스 편집의 기존 최종 답변 모델도 유지한다.

## 시험 조건과 성공 기준

- 양식·일식·중식·자장면·돈카츠 각각 생성 → 산책만 주차 가능한 호텔로 변경 → 카페만 메가MGC커피 → 카페만 컴포즈커피, 20건을 순차 실행한다.
- 출발 핀은 잠실새내역 2호선, 경기는 로컬 DB의 2026-10-07 18:30 잠실 LG 대 두산이다. 과거 경기이며 미래 경기나 예약 재고 시험은 아니다.
- 실제 Django HTTP 요청부터 SSE 스트림 종료까지 잰다. 공급자 결과를 모의하지 않으며 채팅을 다시 조회해 코스·답변 저장을 확인한다. 브라우저·리버스 프록시 통신 시간은 포함하지 않는다.
- 오류 없는 완료, 다섯 장소와 방문 순서·시각, 핀 보존, 구장 내부 시설 ID, 경기 전후 구분, 코스 payload, 저장 일치를 검사한다. 편집은 대상 외 장소 ID·이름·좌표·종류·방문 ID를 보존해야 한다. 숙소 상세 링크와 커피 브랜드도 검사한다.
- 캐시와 숙박 사전 갱신을 운영 설정대로 둔다. 모델·네트워크·누적 캐시 상태를 고정한 통제 실험은 아니므로 차이 전체를 특정 코드 하나의 효과로 귀속하지 않는다.

### 산책 대신 주차 가능한 호텔을 넣은 4단계

`speed13`은 38.809초였다. 중복된 ‘구장 밖’ 조건 때문에 추가 해석·후보 선택·품질 조사가 발생했다. 정확히 중복된 위치 조건을 정리한 `speed14`는 **22.131초**, 생성·저장 및 NOL 상세 링크 검사 통과였다. 식당 → 카페 → 잠실야구장 → 글래드 강남 코엑스센터 순서다.

호텔·주차 조건은 NOL 원문을 해석해 확인했다. 실제 페이지는 서버 Chrome이 미리 수집한 유효 캐시를 33ms에 읽었고, 원문 해석은 9.033초였다. 새 코스 통합 해석 외 별도 숙박 요구 추출은 0ms였다. 처음부터 Chrome으로 새로 읽는 숙박 시험이나 객실 재고·무료 주차 보장은 아니다. 두 실행의 모델·네트워크 변동도 있으므로 16.678초 차이 전체를 코드 변경 하나의 효과로 귀속하지 않는다.

### 동적 품질 캐시가 빈 시험

- `speed8`: 근거리 후보 사전 확인 전 돈카츠 51.325초, 생성·저장 성공.
- `speed9`: 가까운 검증 후보 사전 확인 후, 첫 전달 모델 생략 전 5종 평균 35.907초, 16.569~54.625초, 모두 성공. 빈 별도 캐시 하나로 시작해 5건을 순서대로 실행했으므로 뒤 요청은 앞 요청의 새 판정을 재사용할 수 있다.
- `speed11`: 최종 코드에서 별도 빈 동적 품질 캐시로 양식 1건 **45.919초**, 생성·저장 성공. 정적 검증 목록과 메뉴 DB, 모델 공급자 캐시는 비우지 않았다.

이 결과 때문에 일반 캐시 사용 표본이 30초 이하여도 모든 요청의 최대 시간을 보장하지 않는다. 처음 조사할 후보의 원문·실내·메뉴 검증을 사용자 요청 전에 갱신하는 처리가 추가로 필요하다. 현재 별도 사전 갱신 워커는 **숙박 원문**에만 적용되어 있다.

### 동시에 진행한 이미지 생성의 영향

사용자가 이미지 생성도 실행 중이라고 알려 준 시점의 호스트 측정은 CPU 23%, 전체 메모리 31.84GiB 중 여유 4.05GiB였다. Docker 백엔드 CPU 1.23%, 브라우저 컨테이너 0.24%였으며 순간적인 포화는 관찰되지 않았다. 이미지 생성을 켜고 끈 통제 시험이나 지속 자원 기록이 아니므로 영향이 0이라고 단정하거나 지연 초를 귀속하지 않는다.
