# 독립 조회 병렬 처리·숙박 원문 사전 갱신 검증

측정 범위 안내: 이 문서의 25.672초는 경기→숙박 두 장소 코스다. 후속 [출발 핀과 다섯 방문지 실측](course-scenarios-20261011.md)은 평균 72.2초였다. 숙박 원문 최적화를 모든 코스의 30초 이내 완성으로 일반화하지 않는다.

2026-10-11, [이전 단계](course-latency-round2-20261011.md)에 이어 사용자가 요청한 3·4번 개선을 적용했다. 실제 코스 생성·저장과 복합 질문 답변까지 로컬 Docker에서 확인했다. 모델 등급과 숙박 조건·주소·후기 검증 기준은 유지한다.

## 구현

### 요청 해석과 독립 조회를 동시에 실행

새 코스 해석 모델이 응답하는 동안 별도 스레드 하나가 경기 일정, 구장 정보, 원래 질문에 명시된 활동의 카카오 후보를 준비한다. 숙소 조건 판정과 장소 선택은 해석 완료 후 기존 요청 스레드에서 수행한다. 구장 내부 허용 범위, 근거 사용 예산, 방문 순서를 조회 스레드에서 결정하지 않는다.

준비한 자료는 질문·구장·날짜가 같은 요청에만 사용한다. 빈 후보 목록도 조회 완료로 취급해 중복 요청을 피하고, 준비 중 실패한 항목은 기존 경로로 조회한다. 날짜 미확정·경기 없음/조회 실패 시 숙소 조회를 시작하지 않는다. 기존 코스 편집은 이 경로를 사용하지 않는다. 취소·진행 상태의 문맥은 복사하고 스레드별 DB 연결을 닫으며, 작업을 남겨둔 채 응답을 완료하지 않는다.

### 원문 사전 갱신 워커

Compose의 `lodging-warmer`가 `warm_lodging_cache --loop`를 실행한다. 같은 파일시스템의 백엔드와 기존 비공개 `lodging_pages` 캐시를 공유한다. 한 차례 처리 후 15분 간격으로 확인하고, 만료까지 30분 이하인 원문만 새로 수집한다. 기존 6시간 유효기간은 새 수집·검증이 성공했을 때만 새로 시작한다. 실패한 갱신은 유효한 기존 원문을 덮어쓰거나 만료를 연장하지 않는다.

최근 실제로 사용한 숙소를 우선 준비한다. 사용 빈도는 공개 숙소 ID·이름·주소와 횟수·최근 사용 시각만 저장하며 사용자 ID·질문은 저장하지 않는다. 빈도 집계는 최대 128곳, 최근 7일이며 동시 갱신 시 일부 횟수 손실이 가능한 대략적인 우선순위다. 추천 순서에는 사용하지 않는다. 처음에는 설정된 각 구장 주변 후보 2곳으로 시작하고, 한 차례 최대 6건·180초 예산으로 수집한다. 외부 후보 API 호출 자체의 기존 타임아웃은 별도로 적용된다.

사전 갱신은 JEV/검색/조건 모델을 호출하지 않는다. 일반 요청 때 조건 판정은 그대로 수행한다. Chrome MCP가 사용 중이면 다음 차례로 미루고, 갱신 중 사용자 Chrome/JEV 요청이 오면 갱신을 취소한 뒤 프로세스·프로필 정리를 기다려 사용자가 실행한다. 정리가 3초 안에 끝나지 않으면 기존 `busy` 계약을 유지하며 겹쳐 실행하지 않는다. 이 우선순위를 제공하는 MCP 환경에서만 워커를 실행한다.

## 실제 검증

이전과 같은 잠실 10월 7일 경기 관람 → 주차 가능한 호텔 한 곳 숙박 요청을 새 게스트 세션에서 실행했다. 시간은 요청 시작부터 SSE `done`까지다.

| 실행 | 전체 채팅 | 숙소 원문 | 병렬 준비 / 해석 후 추가 대기 |
| --- | ---: | --- | ---: |
| 초기 진단, 호텔 유형 누락 보완 전 | 64.141초 | 5곳 조회, 마지막 글래드 성공 | 305ms / 0ms |
| 별도 워커 사전 갱신 후 첫 사용자 요청 | **25.672초** | 글래드 캐시 적중 **39ms** | 275ms / 0ms |
| 워커 실행 중 복합 질문: 코스 + 볼넷 설명 | 34.031초 | 글래드 캐시 적중 32ms | 43ms / 0ms |

초기 진단에서 통합 해석이 '호텔' 유형을 빠뜨려 모텔 후보부터 조사한 사례를 발견했다. 명시된 호텔/모텔 유형이 조건에 빠졌거나 다른 조건과 합쳐진 경우에는 기존 숙박 전용 해석기로 다시 확인하도록 보완했다. 정상 통합 해석은 한 번으로 유지하고, 불완전한 경우에만 추가 모델 호출을 허용한다. 이 보완 전 64.141초를 최종 코드의 성능 기준이나 사전 갱신의 순수 개선율로 사용하지 않는다.

사전 갱신 검증에서는 원문 캐시를 비운 뒤 **별도 Compose 워커**로 잠실 후보 3곳을 수집했다. 37.763초에 글래드·파크 하얏트 원문을 검증해 저장했고, 리베라는 부분 수집으로 캐시에 넣지 않았다. 이후 백엔드를 재시작해 프로세스 메모리가 없는 첫 요청에서도 파일 캐시를 사용하는지 확인했다. 사용자 요청의 원문 수집은 39ms였지만 조건 모델 해석에는 10.265초가 필요했다. 사전 수집 비용을 사용자 대기 전에 지출한 결과이며 수집 작업 자체가 없어진 것은 아니다.

병렬 준비는 275ms의 조회를 7.815초의 요청 해석 구간과 겹쳤다. 이 표본에서는 기존 조회도 짧아 병렬 처리의 단독 절감 폭이 크다고 할 수 없다. 사전 캐시가 없거나 만료됐거나 후속 숙소를 조사하면 Chrome 시간이 다시 들며, 모든 요청을 25초대에 보장하지 않는다.

실제 MCP에서 사전 갱신을 시작하고 2초 뒤 사용자 조회를 넣는 추가 실험도 수행했다. 사전 갱신은 `busy`로 반환되고 사용자 조회는 이름·주소·원문 검증을 통과한 `read`로 완료됐다. 실험 전체는 11.629초였다. 모의 프로세스 테스트에서는 이전 프로필이 삭제된 뒤 사용자 Chrome을 시작하는 순서까지 확인했다.

복합 질문은 `course_direct_answer`를 만들지 않았으며 코스 완료 후 기존 답변 모델이 약 10.875초 동안 코스와 볼넷 설명을 함께 작성했다. 단순 코스는 코스 완료 후 47ms에 응답이 완료됐다. 모든 코스에서 생성·저장·NOL 링크·경기 후 숙박·방문 시간·답변 일치 등 10개 검사를 통과했고, 복합 질문은 볼넷 설명까지 11개를 통과했다.

## 회귀와 실행 상태

- 최종 백엔드 회귀 **423개** 통과
- 실제 서비스와 같은 Linux 이미지에서 브라우저 수명주기·우선순위·추적 **13개** 통과
- 합계 **436개**. Windows 직접 실행은 Linux 전용 `os.killpg`가 없어 사용할 수 없으므로, 판정은 Linux 실행 결과를 사용한다.
- 모델과 원문 검증을 낮추지 않고 요청 격리, 취소 전달, DB 연결 정리, 원문 만료, 갱신 실패 시 원문 보존, 캐시 공유, 갱신 작업이 인기도를 부풀리지 않음까지 검사
- 로컬 `lodging-warmer` 실행 중. 첫 주기 로그에서 유효 원문 저장과 부분 수집 제외 확인
- Chrome 서비스와 워커 이미지 빌드 성공, `git diff --check` 통과

운영 서버 배포, 다수 사용자 부하, 미래 경기 연결 문제, 화면 렌더링은 이번 검증에 포함하지 않는다. 로컬 DB의 기존 경기로 검증했으며 과거 날짜 안내를 유지했다.

## 실행과 조정

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build jev-browser lodging-warmer
docker compose exec lodging-warmer python manage.py warm_lodging_cache --stadium JAMSIL --per-stadium 3 --limit 3
docker compose stop lodging-warmer
```

기본 범위는 지원 구장 전체다. `LODGING_WARM_STADIUMS=JAMSIL,SAJIK`처럼 제한할 수 있다. 명령의 `--interval`, `--refresh-before`, `--limit`, `--per-stadium`, `--max-seconds`로 작업량을 조정한다. 여러 서버는 캐시 공유를 별도 구성해야 한다. 가격·객실 재고·예약 가능 여부는 사전 갱신 대상이 아니다.

원본과 재현 스크립트는 Git 제외 경로 `backend/artifacts/lodging-comparison-20261011/`의 `latency-v3-cold.json`, `latency-v3-prewarmed.json`, `latency-v3-mixed.json`, 각 `*-timing.json`, `latency-v3-preemption.json`, `live_chat.py`, `latest_timing.py`, `preempt_probe.py`, `run_regressions.py`다. 공개 보고서에는 세션·쿠키·인증 정보·원문 본문을 포함하지 않는다.
