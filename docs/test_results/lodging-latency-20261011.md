# 숙박 코스 지연 시간 개선 검증

2026-10-11, 서버 Chrome 숙박 수집 적용 후 전체 채팅의 대기 시간을 줄였다. 로컬 Docker의 실제 DB·카카오·NOL·조건 해석 모델·V2 채팅 API를 사용했다. 모델 종류, 필수 조건, 후보 수 상한, 주소·유형·후기 검증 기준은 유지했다.

## 전체 채팅 측정

기존 [통합 검증](lodging-chrome-integration-20261011.md)의 동일 요청을 새 게스트 세션에서 실행했다.

> 2026년 10월 7일 잠실야구장에서 경기 관람 후 주차 가능한 호텔 한 곳에서 숙박하는 코스를 만들어줘. 경기 전 다른 장소는 넣지 말고, 경기 관람과 숙박만 포함해줘.

시작부터 SSE `done`까지의 실제 시간이다. 숙소 원문 수집만의 시간과 구분한다. 첫 요청 측정 전에는 숙박 원문 캐시를 비우고 백엔드를 재시작했다.

| 실행 | 전체 채팅 | 코스 도구 실행 | 숙소 원문 캐시 | 선택 숙소 |
| --- | ---: | ---: | --- | --- |
| 변경 전 재측정 | 94.266초 | 80.641초 | 없음 | 파크 하얏트 서울 |
| 대기·검색 최적화 후 중간 측정 | 74.234초 | 61.000초 | 없음 | 파크 하얏트 서울 |
| 근거 선택 방식까지 변경, 첫 요청 1 | 38.032초 | 25.578초 | 없음 | 글래드 강남 코엑스센터 |
| 반복 요청 | 47.015초 | 27.797초 | 있음 | 글래드 강남 코엑스센터 |
| 속도 개선 후 첫 요청 2 | 44.672초 | 30.641초 | 없음 | 글래드 강남 코엑스센터 |
| 최종 답변 판정 전달 보완 후 | 44.859초 | 29.656초 | 없음 | 글래드 강남 코엑스센터 |

최종 코드의 캐시 없는 요청은 44.859초로 변경 전 재측정 대비 약 52% 줄었다. 앞선 개선 후 측정도 38.032~47.015초였다. 작은 표본이므로 평균·상위 지연 시간의 운영 보장값은 아니다. 반복 요청의 원문은 4ms에 재사용했지만 요청 해석과 모델 응답의 변동으로 전체는 첫 요청 1보다 오래 걸렸다. 모든 사용자의 요청이 같은 숙소나 같은 속도로 완료된다는 뜻은 아니다.

각 실제 채팅에서 다음 8개 검사를 통과했다: 오류 없는 SSE 완료, 경기·숙박 두 곳만 포함, 숙박의 `AFTER` 배치, NOL 상세 링크, 방문 시각, 저장용 `coursePayload`, GET으로 재조회한 코스 일치, 재조회한 답변 일치. 개선 후에는 18:10 잠실야구장 → 22:03 글래드 강남 코엑스센터로 생성됐다.

최종 답변 대조에서 기존의 ‘내부 주차 판정은 충족인데 답변은 미확인’ 문제가 지속된 것을 발견했다. 첫 요청 1에는 답변 모델이 NOL 도메인의 철자를 바꾼 사례도 있었다(구조화 코스의 링크는 정확했다). 선택된 숙소의 조건별 판정을 내부 도구 문맥으로 전달하고 원본 링크·판정 보존 지침을 추가했다. 공개 코스나 저장 카드에 내부 근거를 추가하지 않았다. 최종 실행에서는 답변 링크 일치와 잘못된 주차 미확인 문구 없음까지 **총 10개 검사**를 통과했고, 답변은 요청 조건에 맞는 숙소로 확인됐다고 안내했다. 모델 출력이므로 이 1회 성공을 모든 답변의 오류 방지 보장으로 해석하지 않는다.

테스트 날짜는 로컬 DB에서 구장 연결이 있는 기존 경기다. 구장 연결이 누락된 10월 9~12일 경기나 미래 일정 문제를 해결·검증한 결과가 아니다. 화면 렌더링 검증이나 운영 배포는 포함하지 않는다.

## 바꾼 부분과 근거

1. Chrome의 고정 대기를 검색창·검색 결과·상세 DOM 준비 및 안정화 확인으로 바꿨다. 검색과 상세의 별도 프로필, 실제 검색 버튼, 이름이 일치하는 관찰된 URL, 본문·주소 대조는 유지한다. 시설/이용 안내 제목이 없는 유효 페이지에는 기존과 같은 보수적인 대기 경로를 둔다.
2. 조건 모델이 검증된 이름·주소·평점을 다시 생성하지 않고 원문의 짧은 줄 구간을 선택하게 했다. 이전에는 모델이 근거 앞에 설명을 붙여 연속 원문 대조에서 실패했고, 첫 숙소를 놓쳐 후속 후보를 조회했다. 줄 범위를 벗어난 근거·과도하게 긴 인용은 미확인으로 남기며 후기 날짜·원문·상반된 의견의 검증은 그대로 수행한다.
3. 숙소 ID·이름·주소별로 검증한 공개 원문을 최대 6시간 재사용한다. 다른 조건 요청은 새 조건 판정을 수행한다. 재사용 때도 동일 숙소인지 대조하며 원문 만료 시각을 연장하지 않는다. 조건 결과의 유효 기간에서도 모델 처리 시간을 차감해 원문보다 오래 남지 않게 한다. 실패·부분 원문은 저장하지 않는다.
4. 방문 목록을 명시한 경우 필요한 종류의 장소만 검색한다. 경기와 숙박만 있는 요청에는 식당·카페·관광 임베딩과 검색을 생략한다. 산책·실내 활동을 충족할 수 있는 관광 후보와 일반적인 기본 코스 검색은 유지한다.
5. 요청 해석·수집·조건 판정 시간을 내부 코스 기록에 남긴다. 사용자에게 보내는 코스 JSON의 공개 필드는 유지한다.
6. 최종 코스에 남은 숙소의 조건별 `match`/`unknown`/`mismatch`를 답변 모델에 전달한다. 원문·후기 인용은 전달하지 않고, 확인되지 않은 조건을 확인됐다고 바꾸거나 확인된 조건을 미확인으로 바꾸지 않도록 한다. 숙소 설명·카드는 기존 링크 중심으로 유지한다.

주요 계측은 다음과 같다. `kakao_ms`에는 숙박 검증이 포함되므로 아래 구간을 중복 합산하면 안 된다.

| 구간 | 중간 측정 74.234초 | 첫 요청 1 | 반복 요청 | 첫 요청 2 |
| --- | ---: | ---: | ---: | ---: |
| 요청 해석 | 9.088초 | 9.057초 | 15.360초 | 5.568초 |
| 숙박 조건 추출 | 2.579초 | 2.189초 | 5.124초 | 1.957초 |
| Chrome 원문 수집 | 37.767초, 후보 3곳 | 7.926초, 1곳 | 0.004초, 캐시 | 11.446초, 1곳 |
| 조건 해석 합계 | 8.926초 | 2.924초 | 2.836초 | 8.879초 |
| 임베딩·RAG 검색 | 0초 | 0초 | 0초 | 0초 |

최종 답변 보완 후에는 요청 해석 7.682초, 조건 추출 2.240초, Chrome 수집 8.886초, 조건 해석 8.206초였다. 임베딩·RAG 검색은 0초였고 첫 숙소를 채택했다.

중간 측정의 세 후보 중 하나는 부분 수집으로 실패했다. 개선 후에는 같은 첫 후보의 주차와 호텔 유형을 검증해 기존의 ‘첫 조건 충족 후보에서 중단’ 규칙으로 끝났다. 빨리 끝내려고 조사 개수나 조건을 줄인 것이 아니다. 전체 90초, 수집 45초, 최대 12개 후보의 제한과 실패 시 유료 검색으로 전환하지 않는 정책을 유지했다.

## 숙소 3건의 실제 조건 검증

동일 질문: “주차 가능하고 피트니스 센터가 있는 숙소. 가능하면 조용한 곳으로 확인해줘.” 각 숙소는 원문 캐시 없이 조회했다. 조건 추출·해석 시간까지 포함한다.

| 숙소 | Chrome 수집 | 조건 검증 전체 | 주차 / 피트니스 | 선택 조건 ‘조용함’ |
| --- | ---: | ---: | --- | --- |
| 글래드 강남 코엑스센터 | 9.613초 | 21.968초 | 충족 / 충족 | 충족, 긍정 3·반대 0 |
| 호텔 리베라 청담 | 9.415초 | 19.293초 | 충족 / 충족 | 충족, 긍정 3·반대 1 |
| 신라스테이 삼성 | 9.657초 | 23.298초 | 충족 / 충족 | 반대 우세, 긍정 1·반대 2 |

주차는 원문의 `주차가능`, 피트니스는 시설 목록 또는 위치·이용 시간의 실제 원문으로 확인했다. 주차 가능이 무료 주차를 뜻하지는 않는다. 이름·주소·평점·평가 수·NOL URL은 이전 결과와 일치했다. 리베라의 이전 근거 문자열 오류는 해소됐고, 신라스테이의 반대 후기는 그대로 유지됐다. 조용함은 사용자 요청에서 선택 조건이므로 필수 시설을 충족한 신라스테이를 전체 불일치로 바꾸지 않는다. 전체 후기를 읽었다는 의미는 아니다.

이전 동일 질문의 3건은 Windows에서 30.860~31.734초였고, 이번 측정은 Docker에서 19.293~23.298초였다. 환경이 달라 엄밀한 수집기 전후 성능 비율로 사용하지 않는다. 전체 채팅 전후 비교는 같은 로컬 Docker 환경이다.

## 회귀 검증과 한계

- 최종 백엔드 숙박·후기·방문 가능 여부·코스 생성/수정·브라우저·첨부·메인 그래프 회귀 325개 통과
- Linux MCP 수명주기·Chrome 도구·추적 회귀 11개 통과, 최종 이미지 빌드 성공
- 새 회귀에서 원문 캐시 만료/오염/주소 변경, 조건 변경 시 재판정, 모델 처리 시간 차감, 잘못된 근거 줄, 불필요한 검색 없는 숙박 코스의 실제 출력 확인
- 판정 전달 회귀에서 충족·미확인·불일치를 유지한 메인 모델 입력과 공개 코스의 내부 필드 제외 확인
- `git diff --check` 통과

모델을 더 작게 바꾸거나 조건·주소·후기 검증을 생략하지 않았다. 이번 실제 표본과 회귀에서 품질 저하는 발견하지 않았지만 모든 숙소·질문의 정확도나 운영 동시 부하를 보장하는 평가는 아니다. 브라우저 동시 실행 제한과 `busy` 처리는 유지한다. 원문 캐시는 같은 파일시스템의 워커 사이에서 공유되며 여러 서버 사이의 분산 캐시는 별도 설정이 필요하다. 가격·객실 재고·예약 가능 여부는 대상에서 제외한다.

원본은 Git 제외 경로 `backend/artifacts/lodging-comparison-20261011/`에 있다: `latency-before.json`, `latency-after-cold.json`, `latency-final-cold.json`, `latency-final-warm.json`, `latency-final-cold-2.json`, `latency-final-cold-2-timing.json`, `latency-final-quality-cold.json`, `latency-final-quality-cold-timing.json`, `latency-quality-verify-{glad,riviera,shilla}.json`. 재현은 `live_chat.py`, `integration_smoke.py`, `run_regressions.py`를 사용한다. 게스트 세션·쿠키·브라우저 프로필·실제 환경 변수는 문서와 Git에 포함하지 않는다.
