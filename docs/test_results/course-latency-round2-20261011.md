# 코스 생성 해석 통합·직접 응답 검증

측정 범위 안내: 이 문서의 27~33초는 경기→숙박 두 장소 코스다. 후속 [다섯 방문지 실측](course-scenarios-20261011.md)은 평균 72.2초였으며, 두 수치는 같은 작업의 전후 비교가 아니다.

2026-10-11 사용자 요청에 따라 새 코스 요청의 해석과 숙박 조건 추출을 한 번으로 합치고, 코스만 요청한 경우 검증된 코스 원문을 바로 응답하도록 변경했다. 복합 질문은 기존 최종 답변 모델을 유지한다. 모델 종류·숙소 후보 상한·원문·주소·시설·후기 검증 기준은 바꾸지 않았다.

## 적용 범위

- `NEW` 코스는 `CreationPlan`으로 방문 순서, 방문별 조건, 구장 내부 요청, 취향, 숙박 조건을 함께 해석한다. 수정 전용 필드를 모델이 채우지 않도록 하고 기존 `EditPlan` 기본값으로 연결한다. 구조화 해석 실패 시 기존 전체 해석기로 돌아가며 취소 요청은 재시도하지 않는다.
- 숙박 검증에는 미리 추출한 조건을 전달한다. 명시적으로 빈 조건 목록인 경우도 재추출하지 않는다. 호텔/모텔 유형, 필수·제외·선택 조건, OR, 시설/후기 근거 구분은 유지한다. 조건 결과 캐시는 전달된 조건도 키에 포함한다.
- 단순 코스 요청은 성공한 코스 원문을 SSE와 저장 답변에 그대로 전달한다. 링크·시간·거리·영업/이동 경고를 유지하고 과거 경기에는 날짜 안내를 추가한다. 공개 코스 JSON에 내부 판정이나 계측 필드를 추가하지 않는다.
- 별도 질문, 설명·비교, 번역·표 등 형식 요청, 첨부, 복수 도구, 모호한 분류, 실패/불완전한 코스, 기존 코스 수정은 기존 답변 모델을 사용한다. `course_only=true`와 빈 `additional_requests`를 함께 요구하고, 원래 사용자 질문과 분류 결과도 별도로 확인한다.

## 실제 전체 채팅 측정

동일 로컬 Docker 환경에서 실제 DB·카카오·NOL·모델·V2 채팅 API를 사용했다. 각 실행은 새 게스트 세션이며, 시작부터 SSE `done`까지의 시간이다. 첫 요청은 숙박 원문 캐시를 비우고 백엔드를 재시작했다.

> 2026년 10월 7일 잠실야구장에서 경기 관람 후 주차 가능한 호텔 한 곳에서 숙박하는 코스를 만들어줘. 경기 전 다른 장소는 넣지 말고, 경기 관람과 숙박만 포함해줘.

| 실행 | 전체 채팅 | 코스 도구 완료 → 응답 완료 | 원문 조회 결과 |
| --- | ---: | ---: | --- |
| 이번 변경 전, 이전 단계 최종 측정 | 44.859초 | 8.828초 | 글래드 1곳 새로 수집 |
| 직접 응답 적용, 첫 요청 | 32.828초 | 0.031초 | 글래드 1곳 새로 수집 |
| 조건 해석 예시 보완 후, 첫 요청 | 51.313초 | 0.016초 | 글래드 차단 → 리베라 부분 수집 → 파크 하얏트 성공 |
| 이어서 반복 요청 | 27.062초 | 0.031초 | 글래드 1곳 새로 수집, 캐시 미적중 |
| 원문 캐시 적중 확인 요청 | 44.765초 | 0.031초 | 글래드 캐시 → 리베라 부분 수집 → 파크 하얏트 캐시 |
| 복합 질문: 위 요청 + 볼넷 설명 | 25.766초 | 9.797초 | 글래드 원문 캐시 사용, 기존 답변 모델 |

첫 정상 수집 표본은 기존 44.859초보다 약 27% 짧았다. 두 직접 응답 첫 요청 사이에는 '깔끔한 호텔'에서 호텔 유형도 별도 조건으로 남기는 프롬프트 예시를 보강했다. 모델과 실행 경로는 동일하다. 51.313초 표본처럼 사이트 차단·부분 수집으로 후속 후보를 조사하면 기존 정상 수집 표본보다 오래 걸릴 수 있다. 고정 완료 시간이나 평균 지연 개선율을 보장하는 표본은 아니다.

명확히 제거된 대기는 별도 숙박 조건 추출과 마지막 답변 재작성이다. 새 경로의 숙박 `requirements_ms`는 모두 0이고, 코스 생성 후 응답 완료는 16~31ms였다. 복합 질문은 직접 응답을 만들지 않았으며 코스 생성 뒤 약 9.8초간 기존 답변 경로를 거쳐 코스와 볼넷 설명을 함께 반환했다.

51.313초 실행의 Chrome 조회는 각각 3.754초(차단), 19.413초(부분 수집), 9.815초(성공)였다. 불완전한 자료를 채택하지 않고 기존 후보 탐색 정책으로 검증을 통과한 파크 하얏트를 선택했다. 이어진 27.062초 요청에서는 글래드를 10.453초에 새로 수집했다. 반복 요청이라는 이유만으로 캐시 적중이라고 집계하지 않았다.

실제 원문 캐시가 적중한 44.765초 실행에서는 글래드와 파크 하얏트 원문을 각각 4ms에 읽었다. 첫 후보가 최종 채택되지 않아 후속 후보를 조사했으며, 리베라의 부분 수집에 23.262초가 들었다. 원문 캐시를 사용해도 조건 재판정과 후보 탐색은 유지하므로 전체 응답이 반드시 짧아지는 것은 아니다.

## 품질 확인

모든 실제 코스 요청에서 오류 없는 SSE 완료, 경기·숙박 두 곳, 경기 후 숙박, NOL 링크, 방문 시각, 저장용 `coursePayload`, GET 재조회 코스/답변 일치, 답변 링크와 코스 링크 일치, 잘못된 주차 미확인 문구 없음의 10개 검사를 통과했다. 복합 질문에는 볼넷 설명 포함 검사도 추가해 11개를 통과했다. 답변에서 볼넷을 볼 네 개에 따른 1루 진루로 설명했다.

실제 통합 해석 모델에 다음 5종 질문을 보내 의미 보존도 확인했다.

| 질문 유형 | 확인 결과 |
| --- | --- |
| 주차 호텔 코스 + 볼넷 설명 | 별도 요청 원문 유지, 직접 응답 금지 |
| 모텔 제외 + 반려동물 또는 금연 + 가능하면 조용함 | 제외·OR·선택 후기 조건 유지 |
| 조용한 식당 + 깔끔한 호텔 | 식당 조용함과 숙소 청결 분리, 호텔 유형 유지 |
| 외부 초밥 → 구장 내부 간식 → 경기 → 호텔 | 방문 순서와 내부 먹거리 범위 유지 |
| 호텔 코스를 표로 요청 | 형식 요청 유지, 기존 답변 모델 사용 |

초기 실험에서 '깔끔한 호텔'을 청결만으로 해석한 1건을 발견해 유형과 특성을 별도 조건으로 남기도록 보완했다. 보완 후 5종 검사를 모두 통과했다. 프롬프트 기반 의미 추출이므로 모든 자연어 질문의 누락 가능성이 사라졌다는 보장은 아니다.

- 백엔드 회귀 401개 통과: 숙박·후기·코스 생성/수정·기억 범위·장소 선택·첨부·주 그래프·스트리밍 포함
- 마지막 프롬프트 보완 후 관련 64개 재검증 통과(401개와 중복)
- 실제 그래프 테스트에서 단순 코스는 최초 모델 호출 1회 뒤 바로 종료, 복합 질문은 기존 최종 모델 호출까지 2회 진행 확인
- 첨부/추가 도구/오류/수정 요청의 우회 금지, 경고·링크 보존, 직접 응답 SSE 1회 출력, 조건 변경 시 캐시 분리 확인
- `git diff --check` 통과, 측정 원본과 숙박 캐시의 Git 제외 확인

측정은 로컬 DB에서 구장이 연결된 10월 7일 경기를 사용했다. 미래 경기 연결 문제, 화면 렌더링, 운영 배포·동시 부하는 이번 검증 범위가 아니다. Chrome 수집 실패와 모델 지연 변동은 남아 있다.

원본과 재현 스크립트는 Git 제외 경로 `backend/artifacts/lodging-comparison-20261011/`에 있다: `latency-v2-final-cold.json`, `latency-v2-release-cold.json`, `latency-v2-release-warm.json`, `latency-v2-release-cached.json`, `latency-v2-mixed.json`, 각 `*-timing.json`, `creation-semantic-probe.json`, `live_chat.py`, `latest_timing.py`, `creation_probe.py`, `run_regressions.py`. 게스트 세션 식별자·쿠키·프로필·환경 변수는 이 보고서와 Git에 포함하지 않는다.
