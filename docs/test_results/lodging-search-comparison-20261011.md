# 숙박 검색 방식 3종 비교 — 2026-10-11

같은 숙소 3곳을 기존 OpenAI 방식, JEV + Chrome, Chrome 단독 방식으로 각각 한 번씩 새로 실행했다. 총 9건이며 이전 성공 결과를 재사용하지 않았다. 공통 기준에 따른 **상세 원문 확보는 기존 OpenAI 2/3건, JEV 0/3건, Chrome 단독 3/3건**이었다. 이 표본에서 Chrome 단독은 유료 검색·모델 API 없이 원문을 확보했지만, 속도 우위나 운영 환경의 성공률을 입증한 결과는 아니다.

## 범위와 판정 기준

코스 생성 전체가 아닌 **숙소 한 곳의 검색과 근거 수집**을 비교했다. 카카오에서 확인한 숙소명·주소를 공통 입력으로 사용했다. 공통 후보 탐색, 사용자 문장의 요구사항 추출, 최종 코스 생성은 측정에서 제외했다. 결과 캐시는 사용하지 않았고 브라우저는 실행마다 새 테스트 프로필을 썼다.

성공에는 같은 상세 페이지에서 다음 항목을 모두 확인하도록 했다.

- 입력 숙소명과 도로명·건물번호·구가 일치한다.
- 평점과 후기 수가 있다.
- 주차와 피트니스 시설 안내가 있다.
- 최근 1년 안의 날짜와 실제 후기 본문이 있다. AI 후기 요약은 인정하지 않는다.

최근 1년은 2025-10-11부터 2026-10-11까지다. 날짜와 뒤따르는 후기 본문을 자동 확인하고 실제 수집 본문을 점검했다. 이는 후기의 존재를 확인하는 기준이며, 충분한 후기 수집이나 조용함 판정의 정확도를 검증한 기준은 아니다. 모델이 답한 정보만 있고 독립적으로 읽은 상세 원문이 없으면 완전 성공으로 세지 않았다.

## 숙소별 결과

시간은 실행 프로세스 시작부터 종료까지이며 초기화와 정리를 포함한다.

| 숙소 | 카카오 확인 주소 | 기존 OpenAI | JEV + Chrome | Chrome 단독 |
| --- | --- | --- | --- | --- |
| 글래드 강남 코엑스센터 | 서울 강남구 테헤란로 610 | 성공 · 25.000초 | 상세 오류 · 23.578초 | 성공 · 28.719초 |
| 호텔 리베라 청담 | 서울 강남구 영동대로 737 | 성공 · 35.266초 | 상세 오류 · 17.953초 | 성공 · 29.219초 |
| 신라스테이 삼성 | 서울 강남구 영동대로 506 | 부분 성공 · 20.937초 | 상세 오류 · 21.547초 | 성공 · 28.953초 |

기존 OpenAI 방식의 신라스테이는 상세 URL과 시설·평점 등을 반환했지만, 후속 독립 원문 조회가 HTTP 403으로 실패했다. 기존 정규화 결과에서도 후기 기반 조건인 조용함은 `unknown`이었다. 숙소 검색 자체가 전부 실패한 사례는 아니지만 위의 원문 확보 기준은 통과하지 못했다.

JEV는 3곳 모두 실제 숙소 상세 URL까지 이동했으나 서비스 이용 불가 화면에서 중단됐다. 검색 버튼을 통해 일반 검색 결과를 열라는 목표를 주었음에도 실제 행동 기록에서는 자동완성 숙소 항목을 클릭했다. 따라서 이 결과는 **현재 JEV 흐름의 실패**이며, Chrome 엔진이나 JEV 자체의 일반적 성능을 뜻하지 않는다. 같은 별도 세션 처리까지 JEV에 적용한 실험은 하지 않았다.

Chrome 단독으로 확인한 평점·후기 수는 글래드 4.7/4,878건, 리베라 4.7/2,467건, 신라스테이 4.6/3,301건이었다. 앞의 두 숙소는 기존 OpenAI 방식에서 독립 조회한 원문 수치와도 일치했다. 상세 숙소 ID는 각각 `3012015`, `3000865`, `1000105844`였다.

## 시간·API 비용·로컬 메모리

| 항목 | 기존 OpenAI | JEV + Chrome | Chrome 단독 |
| --- | --- | --- | --- |
| 상세 원문 확보 | 2/3건 | 0/3건 | 3/3건 |
| 3건 평균 종료 시간 | 27.068초 | 21.026초 | 28.964초 |
| 3건 API 비용 합계 | 확인된 사용량 기준 최소 약 $0.02438, 일부 누락 | $0.014278304 | $0 |
| 실행별 최고 메모리의 평균 | 167.3 MiB | 1,576.0 MiB | 1,321.3 MiB |
| 3건 중 가장 높은 메모리 | 169.2 MiB | 1,601.3 MiB | 1,419.0 MiB |

JEV 시간은 **실패까지 걸린 시간**이므로 빠른 성공으로 해석할 수 없다. 기존 OpenAI와 Chrome이 모두 성공한 글래드·리베라 두 곳만 비교하면 평균은 각각 30.133초와 28.969초였다. 차이는 약 1.2초이고, 각 숙소를 한 번씩만 실행했으므로 속도 우위의 근거로 삼기 어렵다.

메모리는 `psutil`로 250ms마다 실행 프로세스와 자식 프로세스의 작업 집합을 합산한 값이다. 공유 메모리가 중복 합산될 수 있어 실제 전용 물리 메모리 사용량과 같지 않다. OpenAI·OpenRouter 서버의 자원은 제외했다. 같은 로컬 측정에서 Chrome 단독은 기존 OpenAI 호출 프로세스보다 약 7.9배 컸으나, 이 값으로 서버 용량이나 동시 처리량을 확정할 수는 없다. CPU와 동시 부하 실험은 하지 않았다.

### 비용 계측의 한계

기존 OpenAI의 초기 계측에 누락이 있었다. 글래드는 API 응답 사용량을 포착하지 못했고, 리베라는 검색 응답만 포착했으며 이후 조건 해석 호출이 빠졌다. 실행 중 계측을 보완했지만 이 두 건을 유료 재실행하지 않았다. 누락을 0달러로 간주하지 않는다.

| 숙소 | 기존 OpenAI에서 확인된 비용 | JEV의 OpenRouter 보고 비용 | Chrome 단독 |
| --- | --- | --- | --- |
| 글래드 | 계측 누락, 미확정 | $0.004771346 | $0 |
| 리베라 | 최소 $0.012625495, 후속 해석 호출 누락 | $0.004757858 | $0 |
| 신라스테이 | 약 $0.011759020 | $0.004749100 | $0 |

OpenAI 비용은 응답의 토큰 사용량과 `search` 동작 수에 공식 표준 단가를 적용한 추정값이며 청구서 대조 결과는 아니다. 포착한 리베라·신라스테이 응답에는 각각 유료 검색 동작이 1회 있었다. 웹 검색은 1,000회당 $10이며 검색 내용에 대한 모델 토큰 비용도 별도다. `open_page`와 `find_in_page`를 추가 검색 1회로 세지는 않았다. 계산 근거: [OpenAI 가격표](https://developers.openai.com/api/docs/pricing), [gpt-6-luna 단가](https://developers.openai.com/api/docs/models/gpt-6-luna), [웹 검색 동작과 과금](https://developers.openai.com/api/docs/guides/tools-web-search).

JEV 비용은 각 실행에서 OpenRouter가 반환한 `usage.cost`를 합산했다. 3건 모두 응답 비용을 포착했다. Chrome 단독의 $0은 검색·브라우저 조작용 모델 API 비용이다. Codex 이용료, 컴퓨터·서버 운영비와 향후 조건 판정용 모델 호출은 포함하지 않는다.

## 실행 방식의 차이

| 방식 | 이번 실행 구성 | 비교 시 유의점 |
| --- | --- | --- |
| 기존 OpenAI | 기존 `lodging.search` → 독립 `PublicReader` → 정규화. `gpt-6-luna`, 기존 90초 탐색 예산 | 주차·피트니스 필수, 조용함 선택 조건을 고정 입력했다. 원문 수집 뒤 기존 모델의 조건 해석도 실행하므로 Chrome 단독보다 작업 범위가 넓다. |
| JEV + Chrome | JEV 0.16.0, 일반 Chrome, `typesafe/jev-1.13-20260917`, 텍스트·검토 모델 `openai/gpt-6-luna`, 최대 40단계/120초 | 단일 세션에서 자율 탐색했다. 서비스 이용 불가나 사람 인증이면 중단하도록 했다. |
| Chrome 단독 | 일반 검색 결과에서 실제 숙소 ID 발견 → 별도 Chrome 세션에서 관찰한 상세 URL 형식으로 조회 → 탭 활성화·화면 렌더링 후 DOM 읽기 | 검색·조작 모델 호출이 없다. 원문과 기본 항목 수집까지이며 조용함 등 사용자 조건의 의미 판정은 구현하지 않았다. |

Chrome 단독은 세션 분리, 상세 URL의 `verticalCategory` 지정, 렌더링 후 본문 읽기를 함께 적용했다. 어떤 변경이 성공에 결정적이었는지는 분리해서 검증하지 않았다. 기존 서비스의 조건 판정과 후기 근거 검증을 이 코드만으로 대체할 수 없다.

환경은 Windows의 일반 Chrome 154.0.8037.98, Node.js 24.19.0이었다. 동시 실행 간 간섭을 피하려고 9건을 순차 실행했고 방식 순서를 숙소마다 바꿨다: 글래드 OpenAI→JEV→Chrome, 리베라 JEV→Chrome→OpenAI, 신라스테이 Chrome→OpenAI→JEV. 실험이 끝난 뒤 이 실험 경로를 사용하는 Chrome 프로세스가 0개임을 확인했다.

## 적용 판단

Chrome 단독 수집은 유료 검색 호출을 줄이는 개선 후보로 유지한다. 이번 표본에서는 원문 확보 결과가 좋았고 호출 비용도 없었다. 다만 속도는 기존 방식과 비슷했으며 로컬 자원 부담은 더 컸다. 숙소 4곳을 약 29초씩 순차 조사하면 단순 계산상 약 116초여서 기존 90초 탐색 예산과 맞지 않을 수 있다.

후속 적용에서는 기존 조건 판정·6시간 결과 캐시를 유지하고, Chrome 작업 수 제한과 취소·정리를 포함해야 한다. Docker·서버에서의 성공률, 동시 요청 자원, 사이트 구조 변경, 동명 숙소·다른 지역·다른 숙소 유형을 추가 검증해야 한다. 날짜별 가격·객실 재고·예약 가능 여부는 이번 범위에 없다. 서비스 코드는 아직 변경하지 않았다.
