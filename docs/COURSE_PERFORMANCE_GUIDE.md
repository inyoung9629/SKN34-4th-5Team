# 코스 생성·수정 성능 유지 지침

코스 또는 공용 LLM·도구·검색·지도 코드를 수정하거나 팀 develop을 통합하기 전에 읽는다. 목표는 일반적인 코스를 대부분 30초 내외에 완성하는 것이다. 요청한 방문이 빠지거나 다른 메뉴·브랜드를 넣은 결과는 빨라도 성공이 아니다. 상세 후기·시설 조사와 캐시 없는 숙박 조회는 별도로 측정하며 모든 요청의 30초 완료를 보장하지 않는다.

함께 적용할 정책 문서는 [LLM 평가 기준](../backend/llm/v2/evaluation/EVALUATION_CRITERIA.md)이다. 평가용 단계 구분은 운영 요청마다 평가 모델을 추가 호출하라는 뜻이 아니다. 기존 근거를 보존하고, 확인된 선택·날짜를 재질문하지 않으며, 독립 조회의 병렬 실행을 유지한다. 30초 목표는 완료 품질과 함께 확인하는 개발 목표이고 전체 요청을 강제 종료하는 정책값이 아니다. 현재 발견된 미충족 항목은 [평가 기준과 코스 흐름 점검](test_results/evaluation-criteria-course-audit-20261012.md)에 기록한다.

## 1. 보존할 처리 구조

| 경로 | 유지할 동작 | 속도가 다시 늘어나는 변경 |
| --- | --- | --- |
| 새 코스 | JEV 분류 → `ask_course` 한 번 → 방문·조건 해석 → 후보 조회·시간표 → 검증 결과 표시 | 메인 모델이 도구를 다시 선택하거나 완성된 결과를 단순히 다시 쓰는 호출 추가 |
| 단순 수정 | `literal_edits`가 원문 전체를 처리할 때만 해석 생략, 수정 대상만 교체 | 돈카츠·메가커피 교체 때 전체 코스·다른 방문의 메뉴를 다시 조사 |
| 요청 해석 | 단순 새 코스는 `low`, 근거·주차·금연 등 상세 조건은 `medium`; 모델 복제본 사용 | 공유 모델 설정 덮어쓰기, 모든 요청에 높은 추론 수준 또는 큰 편집 스키마 사용 |
| 독립 조회 | 일정 준비와 해석을 겹치고, 실시간 후보와 벡터 조회를 겹침; 업종별 벡터 조회는 최대 2개씩 | `parallel.alongside` / `parallel.reads`를 순차 루프로 되돌리거나 무제한 동시 호출 |
| 후보 검사 | 실제 방문의 앞 지점에서 가까운 후보부터 검사하고 같은 지점의 중복 검사 제거 | 전체 반경 후보를 모두 정밀 조사한 후 선택 단계에서 다시 조사 |
| 일반 추천 | `balanced`에서 기존 근거·업종·거리로 추천, 새 평점·실내 조사는 백그라운드로 분리 | 일반 카페 요청에도 후기·실내 사진·웹 검색을 전수 실행 |
| 숙박 | 결정적 서버 Chrome 수집, 정확한 매장 신원 및 명시 조건 확인, 기존 시간·횟수 제한 | JEV 브라우저 조작 모델이나 OpenAI 검색을 기본 흐름에 다시 추가, 실패 후보 무한 재시도 |

품질·증거 조사 예산과 상태 변경은 요청 스레드에서 처리한다. 병렬 작업은 요청의 취소·구장·내부 허용 컨텍스트를 전달하고, 실행 중 작업 정리와 DB 연결 해제를 유지한다. 취소·실패를 빈 목록이나 성공으로 바꾸지 않는다.

`CourseAnswerMiddleware`의 직접 반환은 정상적인 코스 전용 요청에만 적용한다. 첨부, 날씨·가격·규정·하이라이트 등 별도 질문, 미처리 수정에서는 기존 답변 흐름을 유지한다. 속도를 이유로 사용자 질문 일부를 생략하지 않는다.

## 2. 팀 공용 검색·에이전트 변경을 통합할 때

- 팀 develop의 새 정책과 데이터 구조를 기준으로 통합한다. 파일 전체를 개인 버전으로 덮어쓰지 않는다. 리베이스 전 복구 브랜치를 만들고 미커밋 작업을 보존한다. 이미 squash merge된 커밋은 포함 여부를 확인한 뒤 중복 재생하지 않는다.
- `llm.tools.knowledge`의 규정·구장 문서용 하이브리드 검색과 모델 리랭커를 코스의 모든 업종 후보 조회에 자동 연결하지 않는다. 코스는 `course.agent.search_places`의 구장·업종 필터 벡터 검색과 실시간 장소 조회를 사용한다. 이 경로를 바꾸려면 검색 품질과 지연을 별도로 비교한다. 공용 문서 검색의 리랭커를 전역으로 끄는 방식도 사용하지 않는다.
- `ask_course`와 `ask_travel_research`, `search_documents_tool`로 같은 코스를 중복 조사하지 않는다. 새 공용 도구 정책이 코스 전용 빠른 경로를 우회하게 만드는지 검사한다.
- 부분 수정에서는 현재 코스의 구장·날짜를 보존한다. 화면의 기본 구장 값이 기존 코스를 덮지 않게 하는 팀의 수정도 유지한다.
- 확인 질문의 선택 답변도 수정 경로의 회귀 대상으로 둔다. `질문: N번 상호`가 직전 사용자 요청 전체와 연결되는지, 선택한 대상만 변경되는지 검사한다. 선택 문구만 보고 추가 조건을 버리거나 기존 단순 수정보다 불필요한 해석·근거 조회를 추가하지 않는다. 선택지 URL은 기존 장소 데이터로 붙이며 추가 검색하지 않는다. [선택 답변·링크 검증](test_results/course-choice-repair-20261012.md)을 참고한다.
- 선택 질문의 문구 대신 서버의 원 요청·방문 ID·코스 스냅샷과 실제 선택 UI로 이어간다. 알려진 페이지의 일부 근거는 신규 검색 금지로 버리지 않으며 미확인을 성공으로 바꾸지 않는다. 가상 경기 안내를 생성·부분 수정·서버 기억·공개 결과에서 유지한다. [평가 기준 후속 수정](test_results/evaluation-criteria-course-audit-20261012.md)의 반례와 검증을 함께 유지한다.
- 새 첨부 읽기·하이라이트 기능이 있는 복합 질문에는 해당 기능을 유지한다. 단순 코스에는 불필요한 추가 도구를 붙이지 않는다.

## 3. 속도를 위해 완화하면 안 되는 조건

날짜·경기 시각, 출발지, 방문 종류·순서, 명시 메뉴·브랜드·제외 조건, 현재 반경, 확인된 휴무·브레이크타임은 유지한다. 일반 구장 도착은 경기 시작 20분 전, 바로 앞 내부 먹거리는 30분 전 도착 후 경기로 연결한다.

내부 먹거리는 이번 요청에 내부 표현이 있을 때만 자리어때 수집 자료로 구성한다. 카카오 내부 매장으로 대체하거나 다음 요청에 내부 허용을 남기지 않는다. 내부 매장에는 외부 매장 평점 필터를 적용하지 않는다. 매장 상세 위치 링크를 보존한다.

캐시는 현재 출발지·앞 방문지·반경·조건에 맞는 가까운 후보일 때만 우선한다. 캐시 여부·기존 추천 횟수로 먼 가게를 고정 추천하지 않는다. 질문·구장·조회일·좌표·반경·업종·검색어가 다른 사전 조회를 재사용하지 않는다. 실패·부분 수집을 검증 완료 캐시로 저장하지 않는다.

수정하지 않은 방문의 ID·좌표·순서·세부 업종·체류시간, 완료·고정 상태를 보존한다. 지도 조작 중에도 요청 시작 시점의 입력으로 생성하고 완성된 코스를 반영한다. 생성·수정 내용으로 ‘나만의 이야기’ 편집란을 자동 채우지 않는다.

## 4. 전후 측정 절차

1. 통합 전후 커밋, 모델·추론 설정, `COURSE_RECOMMENDATION_MODE`, 외부 조사 설정, 경기 데이터, 백그라운드 워커 상태를 기록한다. 실제 키·사용자 인증·개인 대화는 보고서에 넣지 않는다.
2. 동일한 유효 경기 날짜·시각과 출발 좌표로 아래 생성/수정 쌍을 비교한다. 현재 시연용 일정은 2026-10-16 광주 14:00, 잠실 17:00이며 사용 전 활성 여부를 확인한다. 날짜가 지나거나 가상 일정을 지웠으면 양쪽 버전에 같은 시험 일정을 지정한다.
3. 광주: 자장면 → 내부 간식 → 경기 → 술집 → 산책을 생성하고, 식당만 돈카츠로 수정한다. 잠실: 카페 → 내부 간식 → 경기 → 술집 → 산책을 생성하고, 카페를 메가커피로 수정한다. 메가커피+호텔 복합 수정은 별도 숙박 표본으로 둔다.
4. 실제 `/api/v2/chat/sessions/{id}/messages/`의 완료 이벤트까지 측정한다. `APIClient`는 프록시·브라우저 시간이 제외되고, `agent.answer` 직접 측정은 분류·저장·SSE까지 제외된다는 점을 명시한다. 서로 다른 측정 경계의 시간을 개선율로 비교하지 않는다.
5. 각 조건을 가능하면 3회 이상 반복하고 캐시 사용/미사용을 분리한다. 운영 캐시를 임의로 삭제하지 않는다. 코스 결과 캐시, 장소 근거 캐시, OpenAI 프롬프트 캐시는 서로 다르므로 ‘캐시 없음’의 범위를 적는다. 전후 실행 순서를 번갈아 외부 응답·준비 순서 영향을 줄인다.
6. 성공 여부, 전체 시간·중앙값·최대값, 모델·검색 도구 호출 수, 단계 시간, 실패·시간 초과·누락을 함께 기록한다. 작은 표본의 P90이나 한 번의 빠른 결과로 장기 성능을 주장하지 않는다.

통합 판정 기준: 필수 조건·지도 적용·수정 보존 실패는 처리 시간과 관계없이 실패다. 같은 조건에서 불필요한 모델·웹 호출이 늘었거나, 30초 초과가 반복되거나, 반복 측정 중앙값이 전보다 `max(3초, 20%)` 이상 늘면 원인을 조사한 뒤 반영한다. 이 기준은 개발 중 회귀 탐지 기준이며 서비스 SLA나 성능 보장 수치가 아니다. 60초 이상 표본은 평균에 묻지 말고 단계 기록을 별도 남긴다.

실행 가능한 기존 평가 도구는 `python manage.py evaluate_courses --help`와 팀의 `python manage.py chat_eval --help`로 확인한다. 전자는 실제 유료 호출에 `--live`가 필요하다. 시나리오의 경기 날짜·출발지와 검사 항목을 확인하지 않고 서로 다른 결과를 비교하지 않는다. 원시 측정은 Git 제외 경로 `backend/artifacts/`에, 요약·한계는 `docs/test_results/`에 남긴다.

| --- | --- |
| `intent_ms` | 요청 해석·준비 합류 대기; 일반 요청에 상세 조건 해석이나 큰 스키마가 붙었는지 |
| `preparation_ms`, `preparation_wait_ms` | 일정·장소 사전 조회가 모델보다 늦어 합류를 막는지 |

## 6. 필수 회귀 검사

백엔드: `test_course_candidate_sources`, `test_course_creation`, `test_course_preparation`, `test_course_parallel`, `test_course_literal_edits`, `test_course_editing`, `test_course_visit_requests`, `test_course_recommendation_policy`, `test_course_route_ranking`, `test_course_quality_proximity`, `test_vector_store_cancellation`, `test_lodging_chrome`, `llm.v2.tests.test_course_answer`를 실행한다. 팀 에이전트·첨부·검색 변경이 있으면 `llm.v2.tests`와 변경된 검색 검사도 포함한다. 같은 테스트 DB를 쓰는 명령은 동시에 실행하지 않는다.

프론트엔드: 지도·코스·채팅 관련 테스트, 전체 `npm test`, 타입 검사를 수행한다. 기존 실패는 변경 전 동일 실패를 확인하고 별도로 기록한다. 테스트 통과를 위해 실제 메뉴 데이터를 꾸미거나 실패 검사를 삭제하지 않는다.

프론트엔드 검사 중 일부는 저장소의 형제 경로 `backend`, `data`, `nginx`도 읽는다. Docker에서는 이 경로도 읽기 전용으로 마운트한다. 프론트엔드만 마운트한 환경의 `ENOENT`나 Windows의 테스트용 심볼릭 링크 권한 오류를 제품 오류로 판정하지 말고, 전체 소스가 보이는 Linux 테스트 환경에서 다시 실행한다.
