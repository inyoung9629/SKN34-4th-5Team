# 직관 코스 경기 기준·후보 탐색·시간 검증 — 백엔드 1차 구현

대상: V2 채팅의 규칙 **1·2·3·5(조건 판단·경기 선택·같은 방 기억·응원팀 기본값)**.
2026-09-30: 확정 경기 이후 단계적 장소 탐색과 전체 시간표 검증을 추가했다. 프론트 선택 박스/지도 화면은 변경하지 않는다. 영업시간·실내 경로·실시간 대기 검증은 아직 미연결이다.

2026-10-02 최신 변경: V2 코스의 외부 장소 공급원을 **카카오 실시간 구역 분할 조회**로 교체했다. 앞서 연결한 [로컬 RAG 후보](place-rag.md)와 소상공인 수집본은 보존하지만 현재 코스 후보나 자동 대체 자료로 사용하지 않는다. 현재 검색 반경의 후보 목록 확보와 메뉴·후기 검증을 분리한다. 프론트와 핀 표시 방식은 바꾸지 않는다.

2026-10-02 추가 변경: 공통 모델을 `gpt-6-luna`로 전환하고 승인된 저장 근거를 결정론적 코스 검증에 연결했다. 음식·후기 자동 웹 검증은 기본 배포 설정에서 **꺼짐**(`COURSE_WEB_VERIFICATION_ENABLED=false`), `docker-compose.local.yml`을 적용한 로컬에서만 켠다. 이제 켰을 때의 경로는 OpenAI 웹검색이 아니라 **저장 근거 우선 → 부족한 조건만 Serper 검색 → 서버 본문 읽기 → 도구 없는 Luna 분석**이다. 프론트 추가와 DB 마이그레이션은 없다.

## 현재 메뉴·후기 근거 경로 (2026-10-02)

1. 카카오 API로 현재 반경의 외부 후보를 확보한다. 기존 소상공인 후보로 되돌아가지 않는다.
2. 정확히 같은 카카오 장소 ID의 승인된 `PlaceKnowledgeObservation`을 조회한다. 이름이 비슷하다는 이유로 소상공인 ID와 합치지 않는다. 반경 확대와 시간 검증을 포함한 첫 코스 탐색은 저장 근거만 사용한다. 더 먼 저장 후보로 완성됐으면 가까운 미확인 후보에 유료 검색을 하지 않는다. 시간·후보 탐색 한도 안에서만 검색하므로 모든 주변 장소의 완전 탐색을 보장하지 않는다.
3. 완성할 수 없고 메뉴/필수 후기 근거가 부족하거나, 완성한 코스에 미확인 후기 선호가 남아 있으면 로컬 웹 설정에 따라 두 번째 탐색을 한다. 같은 후보·경로 캐시를 재사용한다. DB 장애는 유료 검색으로 대체하지 않는다.
4. Serper에 공개 매장명·주소·미확인 조건만 전달한다. 대화 전체/사용자 ID/출발지는 전송하지 않는다. 검색 결과 URL 중 허용된 공개 HTTPS 페이지를 서버에서 읽는다. 원문을 못 읽으면 검색 요약만으로 통과시키지 않는다.
5. Luna가 읽은 본문만 구조화하고 코드가 출처 ID·동일 상호/도로명 건물번호·인용·날짜를 대조한다. 메뉴 동의어 의미와 현재 메뉴 여부는 여전히 모델의 판단이다. 없는 메뉴, 다른 지점, 모순된 근거를 임의로 통과시키지 않는다. 후기 필수 조건은 기존 독립 긍정 2개/반대 없음 및 실제 방문 시간 규칙을 유지한다.
6. 허용된 출처의 검증 키워드만 증분 저장하고, 결정론적 일정 검증 후 선택된 장소의 근거 URL을 기존 답변에 표시한다. HTML/인용문/리뷰/사진/작성자/API 상호·주소·좌표 원본은 이 저장기에 넣지 않는다. 새로운 장소는 카카오 ID 참조만 만든다.

| 제한 | 현재 값 |
| --- | --- |
| 상세 검색 | 전체 코스 요청에서 Serper 최대 4회, 장소당 최대 2회 |
| 본문 분석 | 전체 요청 Luna 최대 4회, 장소 최대 4곳, 읽은 페이지 장소당 최대 4개 |
| 검색·분석 시간 예산 | 첫 상세 검색부터 45초, 메뉴/후기 공유 |
| 분석 입력/출력 | JSON 입력 28,000자 이하, 출력 3,500토큰 이하 |
| 자동 재시도/대체 검색 | 0회, OpenAI `web_search` 자동 대체 없음 |
| 같은 조건 재조사 | 근거 부족/완료 이력 6시간, 공급자 오류 10분 대기 |
| 승인된 새 근거의 재사용 | 기본 30일, 후기는 확인 가능한 관찰일로부터 180일 기준도 적용 |

4회는 코스용 **상세 검색 예산**이다. 질문 해석·경기 기준 선택의 LLM, 카카오 후보 검색, 길찾기 호출까지 4회라는 뜻이 아니다. 진행 중 네트워크 요청의 서버 측 과금 취소나 엄격한 실시간 종료는 보장하지 않는다. 새 Luna 직접 호출도 기존 사용자 토큰 예산에 사전 예약·실사용 정산하며 오류로 usage를 모르면 기존 미확인 사용량 정책을 따른다.

GPT-6 Luna의 Responses/추론 설정은 [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-luna)를 따른다. 코스의 경기 조건·방문 요청 추출 두 호출은 응답 지연을 줄이기 위해 `reasoning_effort=low`로 지정하고, 다른 역할의 추론 강도는 유지한다. 추론 호출의 `temperature`는 보내지 않는다. 설치된 tiktoken의 GPT-6 매핑이 없어 해당 정확한 모델 이름에만 UTF-8 바이트 수+서식 여유분을 쓰는 보수적 사전 예산 계산을 적용한다. 정확한 토크나이저라고 간주하지 않으며 정산은 응답 usage를 쓴다. 모르는 다른 모델은 계속 차단한다. JEV/임베딩 모델은 변경하지 않았다.

제한 사항:

- 저장은 출처의 현재 허용 상태를 그대로 따른다. 처음 발견한 URL은 `unreviewed`이며 **그 URL의 키워드가 자동으로 승인·축적되지는 않는다**. 출처 메타데이터/조사 이력과 승인된 키워드 저장을 구분한다.
- 외부 식당 음식 종류·메뉴와 카페 음료·디저트 메뉴를 검증한다. 식당·카페·산책 후기 항목은 조용함·청결·아늑함·데이트 분위기·경관·걷기 편함(산책 전용)이다. 숙박 상세 검증, 전체 리뷰 선제 추출, OCR, 영업시간/예약 검증은 미지원이다. 산책 후기를 공공 출입·야간 개방·조명·휠체어 접근 보증으로 쓰지 않는다.
- 공개 페이지 읽기는 호스트 허용 목록, DNS 검사, robots, 접근 차단, 용량·시간 제한을 따른다. 로그인·자바스크립트·CAPTCHA를 우회하지 않으므로 접근 실패는 미확인으로 남는다.
- 저장 근거 재조회는 정확한 ID/정규화 조건 기반이다. 과거 실험 결과 전체나 벡터 유사도 결과를 승인 근거로 자동 승격하지 않는다.
- 아래 9월 30일 메뉴/후기 절의 OpenAI 웹검색·별도 60초 예산·요청 내 캐시 설명은 **이전 구현/실험 기록**이다. 현재 실행 경로는 이 절이 우선한다. 이전 검증기와 probe는 비교용으로 남겼으며 직접 실행하면 별도 유료 호출이 가능하다.

주요 코드: `knowledge_verification.py`(저장 우선 연결), `evidence_memory.py`(재사용/증분 저장), `serper_evidence.py`(제한된 검색·분석), `travel/public_page_reader.py`(공개 본문), `itinerary_service.py`(2단계 일정 검증).

검증: 재빌드한 로컬 백엔드에서 외부 호출 없는 코스/메뉴/후기/저장/에이전트 회귀 298개 통과. 별도 PostgreSQL 테스트 DB에서 사용량·증분 저장 68개 통과(일부 테스트 중복). 실서비스 DB나 개발/운영 서버에 테스트 자료를 적재하지 않았다. SQLite에서는 기존 동시 지갑 예약 테스트가 잠금 오류를 내므로 해당 검증은 PostgreSQL에서 수행했다.

실제 모델 연결 스모크: `probe_luna_course.py`로 가상 지점의 현재 메뉴 ‘돈카츠’를 ‘돈까스’ 조건으로 검증해 pass를 확인했다. GPT-6 Luna 1회, 입력 1,078/출력 115토큰, 검색·페이지 조회·DB 쓰기 0회. 공식 단기 컨텍스트 Standard 정가로 약 $0.0001653(캐시/할인 전 추정, 청구서 아님). 실제 매장 검색 품질이나 브라우저 채팅 종단 성공을 검증한 결과는 아니다. 코스 페이지와 백엔드 `/api/v1/healthz/`의 HTTP 200을 확인했다.

토큰 사전 예산은 보수적이므로 긴 대화/본문에서 실제 사용량보다 먼저 제한될 수 있다. 예산을 몰래 늘리거나 부족한 입력을 무검증으로 잘라 통과시키지 않는다. 공식 tokenizer 지원 후 이 추정기를 다시 검토한다.

## 처리 흐름과 책임

### 2026-10-02 카페·산책 / 후보 비교 / 부분 교체

- 카페 메뉴는 기존 `food` AND/OR·동의어·배제 검증을 재사용한다. 카페에 음식 업종(`cuisine`)을 넣거나 산책 장소에 판매 메뉴를 붙이는 요청은 거부한다. 새 후기 항목도 독립 긍정 2개·반대 없음·180일·전체 방문 시간·동일 지점 검증을 그대로 적용한다. 주소를 확인하지 못한 공원 페이지도 임의로 통과시키지 않는다.
- 신규 후기 키워드는 기존 `review_feature`와 카테고리에 저장한다. `cozy→아늑함`, `date_friendly→데이트 분위기`, `scenic_view→경관`, `walking_comfort→걷기 편함`. 기존 출처 허용 범위를 자동 확대하지 않는다. 메뉴·식당·카페·산책 모두 요청당 Serper 4회/분석 4회/45초를 **공유**한다.
- 후보 비교는 같은 반경의 소수 후보에서 검증 후기 선호 → 텍스트 선호 → 근거 품질 → 실제 이동시간 → 구장 거리 → ID 순으로 결정한다. 마지막 경기 전 방문은 후보→구장 실제 길찾기 시간도 비교하고 최종 일정 검증에 캐시를 재사용한다. 필수 조건·거리·도착 기한은 별도 통과해야 한다. 모든 반경의 전역 최적 코스를 계산하거나 LLM 재순위를 호출하지 않는다.
- `replace_stop_indices`는 게임을 제외한 이전 방문의 0부터 시작하는 교체 순번이다. `null`은 전체 재탐색, `[]`는 모든 장소를 유지한 시간 변경이다. 같은 방의 완료된 같은 경기 코스에서만 유지할 장소 ID/좌표를 가져오며 LLM이 좌표·ID를 만들지 않는다. 구장 내부·방문 수/종류/순서가 달라지는 부분 편집은 범위를 재질문한다.
- 교체 대상의 이전 ID는 새 후보에서 제외한다. 유지 대상은 다시 후보 검색하지 않으며 승인·유효 근거만 다시 읽고 추가 유료 상세 검색을 하지 않는다. 기존 `pass` 문장을 근거처럼 재사용하지 않는다. 모든 이동·체류·구장 도착과 후기 시간대는 재검증하고 실패하면 장소를 몰래 바꾸지 않는다. 새 화면·선택 박스는 없다.
- 재질문이 발생해도 같은 방의 마지막 성공 코스를 `itinerary_baseline`에 보존한다. 유지할 기존 매장의 정확한 이름이 필수 키워드에 추가된 것만으로 변경 조건으로 오인하지 않는다. 미래 경기 수정은 모델이 `edit_past`라고 분류해도 과거 코스 취급하지 않고 현재 일정으로 재검증한다.

프론트 테스트에서 발견한 연결 수정:

- 크롤러의 연속 저장 구간 안에서 다음 경기가 확정되면 그달 나머지 날짜까지 모두 있어야 한다는 불필요한 조건을 제거했다. 그 경기 전 날짜에 미수집 공백이 있으면 여전히 중단한다. 외부 일정 자동 호출이나 임의 DB 자료 추가는 없다.
- 조건 추출에 전체 코스 근거/탐색 로그를 보내지 않는다. JSON 스키마 표시용 메타데이터·기본값과 이미 구조화된 조건에 중복되는 과거 발화를 줄였다. Pydantic 검증은 유지하며 토큰 한도는 늘리지 않았다. 사용량 제한을 사용자 조건 해석 오류로 바꾸지 않는다.
- 카카오 사각 구역 경계에서 실측 약 0.4m 오차가 전체 조회 실패를 일으켰다. 응답 검증에만 2m 허용을 두되, 최종 원형 반경과 초록/빨강 구장 필터는 그대로 적용한다.
- 후보가 드문 영역에서 반경을 확대할 때 여러 외곽 조각을 매번 검색하던 병목을 수정했다. 캐시 안의 후보가 15개 이하이고 미검색 조각이 여러 개면 확대 사각형을 통째로 재조회한다. 조밀한 영역은 분할/페이지 수집을 유지하고 전체 응답의 완전성 검증과 중복 제거를 생략하지 않는다. 시간 예산 소진 시 발생한 공급자 오류도 `time_budget`으로 분리한다.

검증 기록: 로컬 격리 SQLite 관련 회귀 **312개 통과**, 별도 PostgreSQL 채팅·사용량·근거 저장 **145개 통과**(두 묶음 일부 중복). PostgreSQL 전용 채팅 검사를 SQLite에서 먼저 실행했을 때의 환경 오류는 분리 실행으로 확인했다. 서비스 DB에 테스트 자료를 강제 적재하지 않았으며 임시 테스트 DB는 테스트 러너가 정리했다.

### 실제 프론트 검증 기록 (2026-10-02)

## 규칙 1 — 조건 판단

- 이번 요청의 발화 > 새 화면 선택 > 같은 방 상태 > 마이페이지 응원팀 순으로 적용한다. 화면 선택과 발화가 충돌하면 발화가 우선이다.
- 팀·구장·특정 경기 어느 것도 없고 응원팀도 사용할 수 없으면 팀 또는 구장 하나를 묻는다. 이미 받은 다른 선호는 보존한다.
- 팀의 단순 언급/팬 소개와 실제 관람 대상을 구별하도록 추출 지침을 둔다. 모호한 지역·복수 대상은 명확화 질문으로 넘긴다.
- 화면 선택 생략은 초기화가 아니다. 반복해서 전달되는 동일 화면 값은 이후 채팅에서 바꾼 조건을 덮지 않는다. 명시적 `clear_fields`와 응원팀 사용 거부를 별도로 기억한다.
- 출발·구장 도착 시각은 `preferences`에 저장하며 경기 시작 시각 필터로 사용하지 않는다.

## 규칙 2 — 경기 선택

| 입력 조건 | 처리 |
|---|---|
| 구장만 | 해당 구장의 가장 가까운 시작 전 경기 1개 |
| 팀 + 구장 | 두 조건을 동시에 만족하는 경기 1개 |
| 팀 + 홈 또는 원정 | 그 팀 기준 해당 쪽의 가장 가까운 경기 1개 |
| 팀만, 홈·원정 미지정/상관없음 | 가장 가까운 홈·원정 각 1개를 후보로 제시하고 선택받음 |
| 특정 경기 ID / 상대팀 지정 / 다음 경기 하나 | 나머지 조건까지 만족하는 가장 가까운 1개 |
| 같은 날짜·시각의 복수 경기 | 임의 ID로 확정하지 않고 후보를 제시해 선택받음 |

- 날짜·경기 시각 조건은 위 조건들과 **AND**로 적용한다. 구장은 팀의 홈구장 매핑으로 정하지 않는다.
- KST 기준, 원천 일정의 `scheduled/PREV/READY` 중 아직 시작하지 않은 경기만 고른다. 취소·연기·진행·종료·미확정 상태는 자동 선택하지 않는다.
- 명시한 날짜 범위는 넓히지 않는다. 한 날짜 경계만 보내면 해당 날짜 하루로 해석한다. 최대 기간은 시작일~종료일 차이 366일이다.
- 날짜 미입력 기본 탐색 범위는 **오늘부터 현재 연도 말까지**다. 월별 최신화 후 필요한 후보를 모두 찾으면 중단하고 확인한 범위를 답변에 표시한다. 차기 시즌 일정은 임의로 추정하지 않는다.
- 기존 TVING 최신화 경로와 `ScheduleDay.game_codes`를 이용한다. 원천에서 더 이상 활성 상태가 아닌 예전 CSV 경기나 일정에서 빠진 행은 고르지 않는다. 프로필/입력의 `OB` 등 두 글자 팀 코드를 DB의 `DOOSAN` 등 코드로 변환한다.
- TVING의 현재 구장명이 기존 CSV 구장 FK와 다르면 현재 원천명을 우선한다. DB에 있는 정식 구장명/원천 약칭으로 확정할 수 있을 때만 인메모리로 연결하며 원본 수집 데이터를 수정하지 않는다. 미등록 제2구장 등을 팀 홈구장으로 대체하지 않는다.
- 최신화 실패, 날짜별 일정 누락, 필요한 구장·시각 미확정은 **일정 확인 불가**이며 **조건에 맞는 경기 없음**과 구분한다. 조건을 조용히 완화하지 않는다.
- 홈·원정 두 후보와 프로필 기반 후보는 선택 전까지 고정 경기가 아니다. 모호한 “카페 바꿔줘”로 후보를 자동 선택하지 않는다.

## 규칙 3 — 기억과 재검증

- 완료된 코스 답변의 JSON 상태를 해당 방 checkpoint의 `turns[질문 ID].course_state`에 저장한다. 별도 전역 메모리/사용자 간 공유 캐시/대화 벡터화는 추가하지 않는다. 옛 `ChatMessage.course_state`는 기존 대화 이관 시에만 읽는다.
- 최신 완료 스냅샷에서 조건, 조건 출처, 선호, 해제 항목, 선택 경기, 후보, 확인 대기 상태를 이어간다. 부분 수정은 나머지 조건을 유지한다.
- 팀·구장·날짜 등 경기 조건이 바뀌면 고정 경기/후보를 무효화한다. 명시적으로 받은 다른 조건은 유지한다. 오래된 선택 경기 ID가 새 요청의 숨은 필터로 남지 않게 한다.
- 확정 경기를 쓰는 후속 코스 요청은 ID로 최신 일정을 재확인한다. 시작·종료·취소되면 답변 첫머리에 이전 기준의 문제를 알리고 **이전 코스 수정 / 다음 경기로 변경**을 묻는다.
- 경기 시각·구장·대진 변경은 재확인을 받는다. 변경된 경기 자체가 명시한 날짜·시각 등 조건과 충돌하면 조건 수정 여부부터 묻는다.
- “이전 기록 보여줘”는 저장된 기준 경기 조회다. “지난 코스 자체를 수정”은 과거 기록 수정임을 표시하고 장소 작성 단계에 전달한다. 현재 방문 가능성을 확인했다고 표현하지 않는다.
- “다음 경기로 새로”는 이전 날짜/선택 ID를 해제한다. 특정 ID로만 골랐던 경기라면 이전 경기의 실제 구장을 이어받았음을 알린다.
- API 메시지 삭제는 지정한 사용자 메시지 이후를 지우므로 해당 스냅샷들도 삭제되고 이전 상태가 복구된다. 메시지 수정도 같은 방식이다. 방 삭제는 FK CASCADE로 스냅샷까지 삭제한다.
- 새 방은 새 상태에서 시작한다. 같은 사람의 다른 방 기록은 전달하지 않는다. 기존 V1/과거 메시지를 일괄 분석해 스냅샷을 만드는 백필은 하지 않는다.
- 같은 방 동시 요청은 develop 저장 구조에 맞춰 각 턴을 보존한다. 코스 기억은 **완료된 턴 중 질문 순서가 최신인 상태 우선**이다. 늦게 끝난 옛 답변이 최신 코스 기억을 덮지 못한다. 수정·삭제는 revision 검사로 오래된 스트림의 저장을 차단한다. 외부 모델 호출 중에는 DB 락을 유지하지 않는다.

## 규칙 5 — 응원팀

- 세션 소유 회원의 `accounts.CustomUser.team_code`를 서버에서 읽는다. 게스트는 프로필 기본값이 없다.
- 명시 입력/이 방의 조건·선택 경기가 없는 경우에만 기본값으로 쓴다. 날짜만 입력했다면 그 날짜는 유지한다.
- “마이페이지 응원팀 기준”을 표시하고 후보를 제시한다. 사용자 선택/확인 전에는 고정하지 않는다.
- 회원 정보가 바뀌어도 방에서 이미 선택한 경기를 덮지 않는다. “내 응원팀으로 바꿔”는 명시적인 변경으로 처리한다.
- 명시적으로 팀·구장·경기 조건을 지운 뒤 프로필로 몰래 채우지 않는다. “응원팀 사용하지 마”는 방 상태에 유지한다.

## API와 내부 상태

현재 활성 경로: `POST/PUT /api/v2/chat/sessions/<uuid>/messages/`.
기존 `content`만 보내는 요청도 동작한다. 선택적으로 `context.course`를 보낼 수 있다.

```json
{
  "content": "일식 먹고 카페 들르는 코스 짜줘",
  "context": {
    "course": {
      "team_code": "OB",
      "stadium_code": "JAMSIL",
      "date_from": "2026-10-01",
      "date_to": "2026-10-03"
    }
  }
}
```

`context.course` 허용 필드:

- `team_code`, `opponent_code`: `SS|KT|LG|HT|OB|NC|HH|LT|SK|WO`.
- `stadium_code`: DB 구장 코드. `game_id`: 양의 정수.
- `date_from/date_to`: ISO 날짜. `game_time_min/game_time_max`: 시간대 없는 한국 현지 시각.
- `home_away`: `home|away|any`. `single_game`: boolean.
- `clear_fields`: 해제할 조건 이름 배열. `preferences`를 넣으면 선호를 전체 해제한다.

기존 `context.stadium/intent/origin` 계약도 유지한다. 비어 있는 선택 박스는 해당 필드를 생략한다. `profile`, `action`, `course_state`, `course_runtime`은 클라이언트 선택 조건으로 허용하지 않는다. 조건 추출에서 얻는 동작과 서버 프로필은 별도 내부 데이터다.

SSE는 기존 `delta: {text}` / `done: {message_id, assistant_message}` 계약을 유지한다. 상태 JSON은 현재 공개 메시지 serializer나 SSE에 노출하지 않는다. 미래 프론트 카드/지도용 구조화 출력은 별도 단계다.

## 단계적 반경 확대와 시간 검증 (2026-09-30)

- 코드: `itinerary_request.py`(요청 스키마/추출), `itinerary_planner.py`(결정론적 탐색), `itinerary_service.py`(연결/출력). 최종 코스의 장소·시각을 두 번째 자유형 LLM이 다시 작성하지 않는다.
- 기본 검색: **100 → 300 → 500 → 800 → 1,000 → 1,500m**. 사용자가 명시한 구간 거리 상한은 별도로 적용한다. 더 큰 상한은 명시적으로 받은 경우만 사용한다(입력 최대 20km이지 수집 범위가 20km라는 뜻은 아니다).
- 첫 검색 중심은 확인된 출발지, 없으면 실제 구장이다. 이후는 직전 방문지다. 출발지가 없으면 구장→첫 장소라는 가짜 이동 구간을 만들지 않는다. 지명으로 모델이 좌표를 생성할 수 없다. 사용자 제공 좌표·정확한 구장명 외에는 구장 2.5km 안에서 카카오로 출발지 명칭을 검색하고 **유일한 정확한 이름**인 경우만 사용한다. 동명이점·범위 밖·불명확한 주소는 좌표를 요청한다. 첫 검색 결과를 자동 출발지로 고르지 않는다.
- 현재 반경의 카카오 후보를 확보한 다음 방문 종류/상호·주소 필수·제외 키워드를 적용한다. 외부 식당의 음식 분류·판매 메뉴 필수 조건은 아래 음식 웹 검증을 통과해야 한다. API 업종은 검색 우선순위의 힌트이지 실제 메뉴 증거가 아니다. 가격·접근성·반려동물 등 나머지 필수 조건은 확인 필요로 중단하며 자동 완화하지 않는다. 미확인 선호는 미확인으로 표시한다.
- 가까운 반경에 완성 가능한 코스가 있으면 확대를 중단한다. 후보 배치(4개) 안에서 선호 일치→조회된 이동시간→구장 방향 순으로 비교한다. 구장에서 멀어지는 것은 금지하지 않는다. 뒤의 방문이 불가능하면 같은 반경의 다른 후보, 큰 반경, 앞 방문 후보 교체 순으로 탐색한다. 전역 최적 경로를 보장하는 알고리즘은 아니다.
- 카카오 후보 조회는 아래 구역 분할 규칙을 사용한다. 기존 로컬 수집 원의 교집합으로 카카오 후보를 제한하지 않는다. 조회 실패 시 소상공인/RAG 후보로 자동 폴백하지 않는다.
- 호출 폭주 방지: 요청당 탐색 노드 160, 길찾기 24회, 기본 탐색 25초에 후보 조회 예산 최대 45초를 더한다(음식·후기 검증을 켠 경우 해당 예산 별도 가산). 동일 구간은 요청 안에서 재사용한다. 길찾기/경로 한도 소진은 불가능 판정이 아니라 `search_limited`다. 후보 160곳만 수집한다는 뜻은 아니며 상세 경로 탐색의 별도 한도다.
- 기본 이동수단 도보, 외부 체류 식사 60분/카페 40분/산책 30분, 이동 구간별 여유 5분. 사용자 지정이 우선이며 기본값·여유시간은 답변에 표시한다.
- **내부 방문이 없는 코스의 기본 구장 도착 목표는 경기 시작 20분 전**이다. 명시한 도착 시각이 있으면 그 기한을 사용한다.
- 전체 이동+모든 체류+여유를 합산해 검사한다. 출발 시각이 없으면 역산해 제안하며 현재보다 과거인 시작은 새 코스로 통과시키지 않는다. 과거 코스 수정은 서버의 별도 historical 플래그로 표시한다.
- 실제 길찾기 응답 실패/오래된 캐시/NaN/누락을 시간 검증 성공으로 취급하지 않는다. 경기 후 일정은 사용자 예상 시각 또는 경기 시작 3시간 후를 임시 기준으로 사용하는 조건부 일정이며 실제 종료 후 재계산이 필요하다.
- `course_state.itinerary_request`와 `itinerary_result`에 구조화 요청/결과/선택 ID/시각/탐색 근거를 저장한다. 같은 방 기억·삭제·마지막 요청 우선 정책을 그대로 사용한다. 선호 전체 초기화는 이전 일정 요청도 초기화한다. 새 마이그레이션은 없다.

## 카카오 반경 후보 확보 (2026-10-02)

- 코드: `travel/kakao_course_candidates.py`, `place_service.search_candidate_cell`, `travel/stadium_scope.py`. 내부 Python 공급자이며 공개 지도 API·프론트 계약은 그대로다.
- **식당 FD6 전체 분류**로 시작하며 음식명 키워드 상위 45개로 후보를 줄이지 않는다. 카페는 CE7 및 FD6 제과점/디저트, 편의점은 CS2, 산책은 공원/산책로/둘레길 및 AT4, 실내는 CT1 및 볼링장/보드게임카페/방탈출/영화관을 조회한 뒤 종류를 분류한다. 산책·실내의 키워드 목록이 모든 장소를 망라하지는 않는다.
- 원을 감싸는 사각형을 `rect`로 조회한다. `total_count > pageable_count`이면 해당 사각형을 4등분해 반복한다. 잘리지 않은 구역은 최대 15개씩 3페이지를 끝까지 읽는다. 겹치는 경계·카테고리 결과는 카카오 ID로 중복 제거하고 원 밖의 장소는 거리로 제외한다. [카카오 Local 공식 문서](https://developers.kakao.com/docs/ko/local/dev-guide#search-by-category).
- `is_end=true`만으로 전체 확보를 판단하지 않는다. 건수·페이지 종료·중복 ID·부모/자식 구역의 결과 합계를 검사한다. 응답이 변하거나 페이지가 누락되면 미완료다. 최소 셀 약 10m/분할 깊이 12에 도달해도 잘리는 동좌표 밀집 장소 역시 미완료다.
- 요청 하나의 후보 조회 상한은 **120회, 누적 조회 시간 45초**, 호출 시작 간격 최소 0.25초다. 각 HTTP 호출 timeout은 남은 예산과 8초 중 작은 값이다. 이 예산은 모든 방문·반경·출발지 조회에서 공유한다. 인증 실패·429·잘못된 응답을 반복 재시도하거나 우회하지 않는다. 프로세스 공통 동시/분당 제한도 그대로 적용한다.
- 완료한 사각형과 문서는 **해당 생성 요청 메모리에서만** 재사용한다. 반경 확대/이전 후보로 되돌아갈 때 이미 완료한 영역은 빼고 남은 영역만 조회한다. 전체 후보를 Place DB·RAG·대화 상태에 복제하지 않는다. 선택된 코스 장소와 건수/호출/범위/완료 상태 감사 정보만 기존 결과에 남긴다.
- 검토된 9개 구장 외곽 도형(기존 지도와 같은 convex frame·padding) 및 명시적 구장 지점명으로 소속 후보를 일반 외부 후보에서 분리한다. 종합운동장 공용 주소만 같다고 이웃 가게를 일괄 제외하지 않는다. 내부 방문은 기존 별도 시설 목록과 개방 시각 검증을 유지한다.
- 해당 반경의 조회가 끝나야 조건 순위·메뉴/후기 검증·길찾기에 진입한다. 한도/밀집/응답 변동은 `candidate_search_incomplete`, 연결/설정/잘못된 응답은 `candidate_search_unavailable`이며 일부 후보만으로 코스를 확정하거나 `no_match`로 표시하지 않는다.
- `candidate_retrieval`에는 공급원 `kakao_adaptive`, 호출 수, 분할 수, 요청 내 재사용, 확보/제외/후보 수, 방문별 검색 범위/쿼리/완료 상태를 남긴다. `search_trace.pool_count`는 그 반경에서 확보한 외부·해당 종류 후보 수이며 `matching_count`는 조건·중복 방문 제외 후 수다.
- **완료의 의미는 선언한 API 분류/키워드에서 반환 가능한 결과를 확인했다는 것**이다. 카카오 지도 전체 또는 현실의 모든 사업장을 100% 보장하지 않으며, 코스 역시 전역 최적값 보장은 아니다. 모든 반경을 미리 수집하지 않고 현재 반경에서 완성 코스를 찾으면 기존처럼 중단한다.
- 후보를 더 많이 찾는 것과 전부 유료 웹검증하는 것은 별개다. 자동 웹검색 기본 꺼짐·음식/후기 검증 한도·숙박 시간 검증 미연결 상태를 유지한다. 필수 메뉴/후기 근거가 없으면 여전히 후보 검색 이전에 `knowledge_insufficient`로 중단한다.

## 외부 식당 음식 종류·판매 메뉴 웹 검증 (1차)

- **프론트 변경 없음**. 기존 코스 체인에 `food_requirements.py`(조건/AND·OR), `food_verification.py`(웹 증거/한도)를 연결한다. `itinerary_request.py`는 사용자 뜻을 추출하고, `itinerary_planner.py`는 음식 조건을 통과한 수집 후보만 전체 일정에 대입한다. 지도 좌표·장소 ID·경기 시각은 모델이 만들지 않는다.
- `StopRequest.food.all_of`는 AND, 각 그룹의 `any_of`는 OR다. 조건은 `kind=cuisine|menu`, `name`, `qualifiers`, `exclude`로 구성한다. 최대 4그룹/그룹당 4조건/전체 8조건이다. 동의어는 기존 모델이 정규화하고 세부 속성은 유지한다. ‘치즈 없는 돈까스’는 해당 메뉴의 속성이지 치즈 메뉴도 판매하는 식당 전체를 제외하라는 뜻이 아니다. 식당 전체에 대한 명시적 제외만 `exclude=true`다.
- 구형 방 상태의 `cuisine`은 외부 식당에 한해 같은 필수 음식 조건으로 변환한다. 일식 업종이라는 이유만으로 돈까스 판매를 확인했다고 간주하지 않는다. 카테고리/상호에 메뉴명이 없어도 후보 자체를 삭제하지 않고, 반경 안 검색 우선순위 힌트로만 쓴다.
- 음식 조건이 없는 일반 방문, 카페·숙박·구장 내부에는 이 웹검색을 자동 실행하지 않는다. 내부 음식 조건은 보존한 뒤 `internal_details_unverified`로 중단한다. 기존 내부 방문/개방/경기 시간 규칙은 유지한다.
- 후보는 기존 반경 **100→300→500→800→1,000→1,500m** 안에서 카카오 분할 조회로 확보한다. 반경 안에서 업종·메뉴명 텍스트 일치 힌트, 거리 등을 사용해 먼저 볼 후보를 고른다. 하나를 웹 확인한 뒤 전체 경로를 먼저 시도하고, 실패해야 다음 후보를 조회한다. 4곳을 모두 검색할 필요는 없다. 조건에 맞는 가까운 식당을 찾지 못하면 기존 반경 확대/백트래킹이 이어지지만 웹 한도는 함께 공유한다.
- 검색 수단: 기존 `OPENAI_API_KEY`/`LLM_MODEL`을 사용하는 Responses `web_search` + Pydantic 구조화 출력. `LLM_MODEL`이 없으면 기존 공통 모델 기본값 `gpt-6-luna`를 유지한다. 모델을 Sol로 자동 변경하거나 새 검색 서비스 키를 추가하지 않는다. 실제 검색어·도메인은 웹 도구가 선택하므로 구글/네이버 전체 검색 결과를 전부 수집하는 기능이 아니다. [공식 웹검색 문서](https://developers.openai.com/api/docs/guides/tools-web-search), [구조화 출력 문서](https://developers.openai.com/api/docs/guides/structured-outputs).
- 검색 입력은 해당 식당의 **공개 상호·주소·구장 소속 힌트와 음식 조건**뿐이다. 사용자 ID·전체 대화·출발 좌표를 검색 요청에 보내지 않는다. 상호+지점/주소+메뉴로 검색하며 공식 매장/메뉴 안내를 우선하고 해당 지점의 지도·예약·메뉴 목록을 사용한다. 후기는 보조 근거로만 허용하고, 후기만으로 판매 메뉴를 통과시키지 않는다.
- 출처의 지점 동일성, 외부 매장 여부, 조건별 근거를 각각 판정한다. 실제 웹 도구의 출처/인용 메타데이터에 있는 공개 HTTP(S) URL만 인정한다. 모델 JSON에만 등장한 URL, 미완료 검색, 빠진/중복된 조건 ID는 통과시키지 않는다. 단, **페이지 의미·주소 동일성·최신 메뉴 여부는 모델의 해석**이다. 스키마나 URL 확인만으로 내용의 정확성을 보장할 수 없으며 독립적인 원문 대조 엔진은 아니다.

## 외부 식당 조용함·매장 청결도 후기 검증 (2026-09-30, 1차)

- 프론트/선택 박스/지도/공유 DB/마이그레이션 변경 없음. `review_requirements.py`, `review_verification.py`를 기존 추출→수집 후보 탐색→전체 일정 검증→채팅 응답에 연결한다. 기존 메뉴 검증의 공식/메뉴 근거 기준을 후기로 완화하지 않는다.
- 식당 `StopRequest.reviews.all_of`에 `aspect=quietness|cleanliness`, `priority=required|preferred`를 최대 2개 저장한다. 동일 항목 중복은 거부한다. `조용하고 매장이 깔끔한`은 두 필수 조건, `가능하면 조용한`은 선호다. OR·절대 소음 없음/위생 안전 보장·그 밖의 특징은 확인 질문 또는 미확인 조건으로 보존한다. 내부 식당 후기 조건은 보존하되 미지원으로 중단한다. 카페 등 다른 업종으로 자동 확대하지 않는다.
- 기존 방에 미확인으로 기록된 조용함/매장 청결도는 추출 모델이 우선순위를 보존해 `reviews`로 옮긴다. 관계없는 가격/주차 등 조건은 남긴다. 사용자의 조건 취소가 최우선이다. 필수 조건을 선호로 몰래 낮추지 않는다.
- 검색 대상은 해당 수집 식당의 공개 상호/주소/구장 소속 힌트와 요청한 두 특징뿐이다. 사용자 ID, 대화, 출발 좌표, 개인 일정은 후기 검색 입력에 전달하지 않는다. 기존 모델 설정을 유지하는 OpenAI Responses 웹검색으로 긍정·반대 근거를 함께 찾으며, 특정 플랫폼 후기 API를 새로 연동하거나 로그인/앱 전용 후기를 긁지 않는다.
- 실제 도구의 출처/인용 메타데이터에 있는 공개 URL, 본문 열람 표시, 같은 지점, 외부 매장임을 확인해야 한다. 검색 스니펫만 확인/다른 지점/모델이 만든 링크는 인정하지 않는다. 본문 열람·의미 분류·지점·협찬 여부·중복 경험 식별은 **모델의 해석**이며 독립적인 원문 대조 결과가 아니다. 이 한계를 답변에 표시한다.
- 방문자 후기만 사용한다. 업주 홍보·플랫폼의 집계 키워드·협찬/광고/체험단 표시·광고 여부 미확인은 제외한다. `not_disclosed`는 표시가 발견되지 않았다는 뜻이지 광고가 없음을 보증하지 않는다. 조용함은 소음/대화, 매장 청결도는 매장/테이블/식기 등 물리적 청결이다. `국물 맛이 깔끔`, `깔끔한 인테리어`만으로 청결도를 통과시키지 않는다.
- 날짜 정책: 게시일/방문일 중 알려진 값이 하나 이상 있어야 하며, 알려진 날짜 모두 현재 한국 날짜 기준 180일 이내여야 한다. 미래 날짜, 게시일보다 늦은 방문일, 오래된 경험을 새로 게시한 글은 제외한다. 검색일/페이지 수정일을 후기 날짜로 사용하지 않는다. 180일은 조정 가능한 초기 정책이지 정확성 보장이 아니다.
- 중복 정책: 같은 URL(추적 파라미터/fragment 제외), 동일 경험 그룹, 동일 요약을 연결해 한 근거로 센다. URL 하나에 여러 후기가 있어도 최대 한 근거다. 서로 다른 URL만으로 다른 작성자임을 보장하지 않으며, 모델이 놓친 재게시/광고가 남을 수 있다. 중복 그룹 안의 반대 의견도 버리지 않는다.
- 항목별 판정: 서로 독립으로 분류된 긍정 근거 **2개 이상 + 반대 0개**는 `positive`, 긍정/반대 동시 발견은 `mixed`, 반대만 있으면 `negative`, 무근거/긍정 하나뿐이면 `unknown`. 긍정 다수결로 반대 근거를 덮지 않는다. 이 숫자는 방문자 전체 비율/평점이 아니라 제한된 검색에서 확인한 근거 수다.
- 시간 정책: 특정 요일/시간대 후기는 `limited`로 보존하고 최종 코스의 **방문 시작~종료 전체**가 그 범위에 들어갈 때만 적용한다. 명시된 오후는 초기 규칙상 12~18시다. 조건부 평가는 전 시간대로 확대하지 않는다. 시간 불명/경기일 혼잡 같은 미지원 문맥은 미확인으로 제외한다. 자정을 넘는 제한된 방문도 보수적으로 제외한다. 뒤 방문의 검색 지연과 백트래킹 이후에도 최종 시간으로 재판정하며, 판정 과정에서 새 유료 검색은 하지 않는다.
- 필수 후기 조건은 모든 항목 `positive`여야 코스에 채택한다. `negative`는 반대 근거이지 실제 매장 상태 확정이 아니다. 혼재/부족한 근거는 `review_unverified`, 반대만 있는 필수 조건은 `review_mismatch`, 검색 한도/연결 실패는 `review_search_limited`/`review_search_unavailable`로 구분한다. 실패 시 부분 코스를 내보내지 않는다.
- 선호는 미확인/반대여도 다른 필수 조건과 시간이 맞으면 코스를 만들 수 있고, 미충족 사실을 답변에 표시한다. 같은 반경에서 최대 2개씩 비교하는 후보 배치 내 일반 후기 점수를 `positive +2 / mixed -1 / negative -2 / unknown 0`으로 먼저 비교한다. 특정 시간대 후기는 이 사전 순위 점수에서 제외하고 최종 시간 판정에만 사용한다. 반경 전체/모든 식당의 최적 선호 코스를 보장하지 않는다. 메뉴 조건도 있으면 메뉴 검증을 먼저 통과해야 한다.
- 보고서의 `eligible`(필수 조건 기준 코스 채택 가능)와 `status`(전체 후기 조건의 근거 판정)를 분리한다. 예를 들어 필수 조용함은 긍정이고 선호 청결도는 미확인이면 `eligible=true`, `status=unknown`으로 저장하며 청결도까지 충족한 것처럼 `pass`로 기록하지 않는다.
- 후기 검색 한도(`ReviewSearchPolicy`): 요청당 식당·조건 조합 최대 **4회**, 조합당 웹 도구 최대 **3회**, 응답 출력 최대 4,500토큰, 재시도 0, 호출 timeout 최대 25초, 첫 후기 조회부터 60초. 후기 조건이 없는 요청에는 호출하지 않는다. 메뉴 예산과 별도이므로 두 검증을 함께 사용하면 최대 응답 8회/웹 도구 20회, 탐색 예산은 기본 25초 + 메뉴 60초 + 후기 60초다. 이는 전체 API 요청의 강제 종료/과금 상한 보장이 아니며 추출·경기 선택 시간은 별도다.
- 동일 요청 안에서 장소 ID+후기 조건으로 증거를 재사용하되, 방문 시간이 바뀌면 판정은 다시 한다. 공유 RAG/벡터 DB/다른 사용자 재사용은 구현하지 않는다. 원문·사진·작성자 계정은 저장하지 않고 선택된 코스의 짧은 해석·출처·확인 시각·문맥·판정만 기존 방 상태에 남긴다. 출처의 장기 재이용 허가를 자동 확보하는 기능은 아니다.
- 채팅 응답에는 항목별 긍정/반대/혼재/미확인, 중복 제외 근거 수, 클릭 가능한 링크, 확인 시각, 실제 소음/청결/위생 안전을 보증하지 않는다는 안내를 넣는다. [OpenAI 공식 웹검색 문서의 출처/인용 지침](https://developers.openai.com/api/docs/guides/tools-web-search)을 적용한다.

## 구장 개방 시각과 내부 코스

- `gate_times.py`는 사용자 첨부 이미지의 **2026 시즌, 2026-09-28 조사표**를 옮긴다. 표의 공식 확인/블로그/두산 추정을 별도로 저장한다. ‘공식 확인’은 첨부표의 주장이고 이 구현이 독립적으로 공식 확인한 것은 아니다.
- 구장과 **실제 홈팀**을 기준으로 평일/금요일/주말을 처리한다. 한화 FULL과 SSG 시즌권은 명시한 경우에만 적용한다. 사직 레드데이/개막전도 명시한 특별 경기인 경우만 3시간 전 기준을 적용한다. 표에 없는 월요일·평일 공휴일 예외, NC 일반 입장, 다른 시즌은 임의 기본값으로 채우지 않는다.
- 공휴일 분기는 [2026 월력요항 발표](https://www.kasi.re.kr/kor/post/newsMaterial/32031)와 [2026 노동절·제헌절 추가 공지](https://openminister.mpm.go.kr/mpm/comm/newsPress/newsPressRelease/?boardId=bbs_0000000000000029&cntId=4250&mode=view)를 참고한 2026 목록을 사용한다. 신규 임시공휴일/시즌 변경은 데이터 갱신이 필요하다.
- 오픈 맞춤 요청 또는 명시적 내부 방문에만 별도 구장 시설 목록을 연결한다. 오픈 맞춤만 요청하고 내부 종류를 지정하지 않으면 **내부 먹거리 1곳을 기본 제안했다고 명시**한다. 일반 코스에 내부 목록을 자동 추가하지 않는다. 기존 공개 수집본의 구장 소속 후보 주석은 이 기능과 별개이며 전면 제외 필터로 바꾸지 않는다.
- 내·외부가 `internal`로 분류된 항목만 내부 후보로 사용한다. 외부 부속시설은 제외, `unknown`은 확인 필요다. 현재 편의시설 원본에는 unknown이 많으므로 모든 시설을 바로 내부 코스로 확정할 수 있는 것은 아니다.
- 좌표가 없는 내부 매장은 층/구역으로 안내하며 좌표를 생성하지 않는다. 근사 핀도 실내 길찾기 좌표처럼 쓰지 않는다. 내부 기본 체류는 먹거리/카페 30분, 시설 20분, 편의점 10분이며 명시한 값이 우선이다. 각 내부 방문 전 이동·대기는 임시 10분을 사용해 **조건부 시간표**로 표시한다.
- 내부 방문은 `max(구장 도착, 개방 시각)` 이후에 시작한다. 필요한 체류/내부 이동을 역산해 외부 일정의 입장 목표를 앞당긴다. 개방부터 경기 시작까지 요청한 시간이 들어가지 않으면 방문을 몰래 줄이지 않는다.
- **마지막 경기 전 장소가 구장 내부이면 전체 경기 전 코스의 기한은 경기 시작 시각 자체**다. 20분을 추가로 빼지 않고, 내부 마지막 장소→구장 이동도 추가하지 않는다. 외부 장소→구장 입장 이동은 여전히 포함한다. 내부→외부 재입장 순서를 임의로 재배열하지 않는다.
- 개방 시간이 있어도 매장 영업·입장권·시설 접근 권한이 검증된 것은 아니다. 내부 방문의 현재 이용 가능 여부는 별도 검증 대상이다.
