코스·챗봇 작업의 최종 동작과 검증 기록. 작업 브랜치는 `feat/remove-sbiz-data`이며 GitHub PR에는 기능별 최종 변화와 배포 조건을 요약한다. 파일 수정 시각만으로 작업 범위를 판별하지 않으며 실제 `.env`, 키, 생성된 평가 보고서·스크린샷은 포함하지 않는다.

## 문제와 변경 후 동작

기존에는 한 번 요청한 카페 브랜드도 대화 취향으로 남고, 교체한 장소가 자동 제외될 수 있었다. 복합 수정이나 구간별 이동수단 변경을 자연스럽게 이어가기 어려웠으며, 장소 키워드 저장 모델과 활성 코스 검증 경로도 분리되어 있었다.

이제 일회성 조건은 그 요청에서만 사용하고, ‘싫어해·제외해·앞으로·기억해’처럼 명확히 선언한 취향만 유지한다. 현재 지도 코스를 기준으로 부분 수정하고, 수정 결과의 이동시간·시간표·지도 경로를 함께 갱신한다. 검증된 장소 키워드는 출처 정책에 따라 PostgreSQL에 저장하고, 다음 요청의 조건 검증에 재사용한다. 저장 여부 자체는 추천 가산점이 아니다.

## 기능별 변경

### 코스 생성과 후보 정확도

- 같은 대화창에서 새 코스를 만들면 이전 대화와 조건·제외·고정·날짜·이동수단을 초기화한다. 현재 지도 구장·출발지·선택 경로는 유지한다. 부분 수정은 해당 코스 생성 이후의 대화만 참고하며 보이는 과거 대화는 삭제하지 않는다.
- 기존 분류 호출에서 새 생성/수정을 구분하고, 완료된 새 생성에 기억 경계를 저장해 새로고침 후에도 오래된 코스가 섞이지 않게 한다. 관련 자동 테스트 189개, 실제 분류 10/10, 실제 새 생성 → 체류시간 수정 연속 호출을 검증했다. 브라우저 확인은 비회원 크레딧 소진으로 제한됐다.
- 팀 선택과 구장 선택 모두 해당 홈구장의 가장 가까운 경기 기준으로 안내하고 정확한 날짜 입력을 권장한다.
- 요청한 식사·카페·산책의 순서와 경기 전후 구성을 유지한다. 요청하지 않은 야식·추가 카페를 넣지 않는다.
- 시간이 부족해도 장소를 임의로 삭제하지 않고 방문이 어려워지는 순서를 안내한다.
- 기본 이동수단은 도보다. 실제 길찾기 실패 시 추정임을 표시한다.
- GPS/지도/채팅 출발지와 직접 그린 경로를 반영한다. 주변 장소 범위는 구장 반경 2.5km 안에서 넓힌다.
- 조건을 통과한 후보를 업종별 한 곳으로 미리 줄이지 않고 동선 계산에 남긴다.
- ‘한식 말고 일식’ 같은 부정 조건을 긍정 선호와 분리한다. 특정 메뉴 제외를 전체 음식 분류 제외로 확대하지 않는다.
- ‘삼성역’, ‘롯데월드’ 같은 지명을 구단으로 오인해 구장이 바뀌는 문제를 수정했다.

### 챗봇과 연속 수정

- 장소 교체, 추가·삭제, 순서 변경, 체류시간, 장소 고정·해제, 명시적 제외·해제, 직전 수정 취소.
- ‘카페→구장만 대중교통’처럼 구간별 이동수단을 변경한다.
- ‘카페 교체 + 식당 앞으로 이동 + 20분 체류’처럼 최대 6개 수정은 전체를 검증한 뒤 한 번 재계산한다. 실패하면 부분 반영하지 않는다.
- 출발지만 변경/삭제해도 방문지·순서·제목은 유지한다.
- 출발 지연, 경기 종료 지연, 방문 완료, 요청한 야외→실내 교체를 반영한다.
- 생성 중 질문은 2개까지 예약하고 입력창 위에서 수정·취소한다.
- 작은 챗봇에서도 대화 목록을 열고 삭제할 수 있다.
- 응답을 기다리는 동안 사용자가 지도를 바꿨으면 자동 덮어쓰기를 막고 적용 상태를 안내한다.

### 작성 화면·대화 복원·일정

- 코스 제목·출발지·완성 상태를 대화 스냅샷과 초안에 보존한다. 명시적으로 지운 출발지를 복원하지 않는다.
- 새로고침/화면 재진입/기존 대화의 코스 다시 열기에서 지도·본문·체류시간·구간 이동수단을 보존한다.
- 기존 작성 내용이 있는 화면에 다른 대화 코스를 열 때 자동으로 덮어쓰지 않는다.
- 경기 없는 날 메인 화면에는 가장 가까운 다음 경기를 표시한다. TVING 일정 갱신과 경기 조회 관련 회귀 검증을 추가했다.

### 장소 근거와 RAG

- `menu`, `cuisine`, `review_feature`의 요청 키워드만 검증한다. HTML·리뷰 원문·채팅·개인 취향은 공용 근거 DB에 넣지 않는다.
- 동일 장소 ID와 지점 주소, 실제 페이지 열기, 출처 종류, 긍정/부정, 유효기간을 검사한다.
- 단일 후기·상충 정보·검색 누락을 확정 특징이나 미판매로 승격하지 않는다.
- DB에 저장된 장소를 먼저 추천하지 않는다. 현재 확보한 후보의 조건을 검사할 때만 근거를 재사용한다.
- 기본 DB가 RDS인 배포에서는 그대로 공유하며, 로컬만 별도 연결할 때는 `RAG_DB_*`와 전용 router를 사용한다.
- 출처 자동 승인은 하지 않는다. `PLACE_EVIDENCE_STORAGE_POLICIES=[]`이면 검증 결과를 현재 요청에 사용할 수 있어도 실제 키워드 관찰은 자동 저장하지 않는다.

## 배포 시 필요한 것

1. 기존 변경의 `travel` 마이그레이션 0014·0015(근거), 0016(이동수단) 적용 여부를 확인한다.
2. 기존 `DB_*`가 팀 RDS라면 추가 DB 설정 없이 근거를 같은 PostgreSQL에 저장한다. 별도 연결이면 `RAG_DB_*`와 TLS 정책을 설정한다.
3. 웹 추가 확인을 사용할 환경에서만 `COURSE_WEB_VERIFICATION_ENABLED=true`를 설정한다.
4. 실제 저장을 허용할 출처의 URL 범위·허용 속성·보관 기간을 `PLACE_EVIDENCE_STORAGE_POLICIES`로 설정한다.
5. 프론트·백엔드를 함께 배포하고 코스 응답의 `writerState`, `legModes`, `stayOverride`, `progress` 전달을 확인한다.

자세한 설정은 [공용 장소 근거 연결](shared-place-evidence.md), API 동작은 [대화로 코스 수정하기](course-conversation.md)를 참고한다.

### 추가 검증: 메뉴·후기 조건 (2026-10-05)

실제 API 16턴으로 메뉴 근거가 필요한 생성·식당 교체·복합 조건 실패를 확인했다. 일반 가까운 후보만 조사하던 누락, 메뉴 맥락 오분류, 불필요한 중복 조사, 근거 없는 코스 완료 안내를 수정했다. 확인된 메뉴·후기 근거는 일정 끝의 작은 링크로 표시한다.

대표 메뉴 요청은 약 30초, 모델+웹 검색 비용은 건당 약 $0.0144~$0.0463이었다. 실패를 포함한 평가 16턴 합계는 약 $0.2862이며, 전체 정확도나 고정 응답 시간 보장은 아니다. ‘조용함’의 충분한 근거는 확보하지 못해 미확인으로 처리했다. 마지막 코드에서 백엔드 235개·프론트 65개를 검증했으며 위의 이전 355개와 중복되므로 합산하지 않는다.

실제 원문 대조, 보고서 경로, 저장 정책·RDS 제한은 [웹 근거 검증 보고서](course-web-evidence-verification-2026-10-05.md)에 정리했다. 로컬 웹 확인은 활성화돼 있지만 승인된 저장 출처는 0개이므로 실제 키워드 영구 저장은 별도 설정이 필요하다.

검색 모델이 페이지를 읽었다는 선언만으로 메뉴 근거가 확정되는 문제를 막았다. 별도 공개 페이지 리더가 실제 상호·주소·메뉴 구역·인용문을 대조하고, ‘짬뽕전골’을 일반 ‘짬뽕’으로 받아들이는 등의 의미 오류를 검사한다. 긍정 메뉴 조건의 검색은 후보별 상세 페이지 발견에 집중하고 메뉴 충족 여부는 실제 본문으로 판정한다.

처음 조사한 후보가 부족하면 다음 후보·대체 출처를 최대 3차례 확인한다. 한 차례 후보 4곳, 새 본문 URL 4개·한 턴 12개, 첫 조사부터 90초 예산이며 충족 후보를 찾으면 멈춘다. 구장 2.5km 제한과 저장 장소 우대 금지를 유지한다. 이전 코스 추출기 근거는 `course-evidence-v6`에서 재검증한다.

최종 백엔드 회귀 테스트 **254개**, 실제 API 최종 **4턴 시나리오 검사**가 통과했다. 메뉴 두 조건 생성 39.333초/$0.03478966, 식당만 교체 33.149초/$0.03428391, 근거 없는 복합 조건의 수정 거절·기존 코스 보존 35.542초/$0.05478999를 확인했다. 금액은 모델+웹 추정이며 전체 정확도/성능 보장으로 해석하지 않는다. 중간 오류와 수동 원문 확인까지 [검증 보고서](course-web-evidence-verification-2026-10-05.md)에 보존했다. 이번 변경으로 새 마이그레이션이나 출처 저장 승인을 추가하지 않았다.

‘스테이크 썰고’ 같은 식사 문맥을 FOOD로 해석하고 실제 메뉴 조건까지 이번 요청에 유지한다. 과거 식사·식사 제외·카페 디저트는 새 식사로 추가하지 않으며 구장 방문을 관광으로 중복 추가하지 않는다. 스테이크 토핑 음식과 단품 스테이크를 구분하도록 v7 근거 검증을 보강했다.

숙박 유형·시설은 상세 정보, 청결·조용함은 최근 실제 후기로 확인한다. 다음 후보를 순차 조사하고 충분하면 작은 출처 링크만, 끝까지 미확인이면 평점·평가 수를 보정한 대안을 안내한다. 호텔이라는 상호와 실제 업종을 구분하고 방문 순서를 숙소 조건으로 오해하지 않게 했다. 구장 2.5km·가격/예약 정보 제외·명시적 불일치/제외 유지 정책을 적용한다.

숙박도 공개 상세 페이지의 날짜별 후기 원문을 별도로 읽어 인용·날짜를 대조한다. 실제 검증에서는 첫 4곳 중 청결 긍정·반대 근거가 확인된 호텔을 선택하고 링크만 표시했다(59.178초, 모델+웹 약 $0.03831). 관련 백엔드 282개·프론트 출처 28개 검증과 중간 추천 오류는 [검증 보고서](course-web-evidence-verification-2026-10-05.md)에 기록했다. 새 DB 마이그레이션·RDS 설정·출처 저장 승인을 추가하지 않았다.

### 추가 수정: 처리 중 잠금 복구와 재시도 예약

서버 재시작 이전부터 남아 있던 로컬 사용량 잠금 한 건은 작업 종료를 확인한 뒤 기존 정산 함수로 복구했다. 알려진 사용량은 보존하고 미확인 호출을 표시했다. 현재 해당 지갑은 전송 가능한 상태이며 서버 재시작 자동 복구 기능을 추가한 것은 아니다.

기존 질문의 수정·재시도 PUT도 `usage_busy` 시 예약하도록 보완했다. 원래 질문 ID와 승인된 수정 범위를 유지하며 예약 내용 수정·취소, 대기 중 대화 변경·질문 삭제를 검사한다. 프론트 102개·백엔드 사용량 44개와 TypeScript/대상 ESLint 검사 통과. 상세 원인과 검증 범위는 [검증 보고서](course-web-evidence-verification-2026-10-05.md)에 기록했다.

### 커밋 목적 분리

후속 브라우저 검증에서 Nginx의 60초 연결 끊김을 확인해 10초 SSE 연결 유지, 정체 제한 분리, 채팅 전용 프록시 설정, 서버 작업을 기다리는 예약의 이유 표시를 추가했다. 프론트 개발 서버의 변경 감지 누락도 재시작·실제 번들 확인으로 바로잡았다. 제보와 같은 사직 코스가 실제 Chrome에서 93.881초 만에 완료되고 네 장소의 핀·경로에 반영됐다. 프론트 104개·백엔드 관련 134개가 통과했다. 배포 Compose의 Gunicorn도 스레드 방식으로 준비했으며 팀 서버 배포는 실행하지 않았다. 속도 개선 완료로 해석하지 않는다.

현재 트리에 이전 수집 데이터 제거·Docker·일정·코스 변경이 섞여 있으므로 `git add .`로 전부 한 커밋에 넣지 않는다. 공유 파일은 diff의 변경 부분을 나눠 검토한다. 예시 커밋 목적:

- `fix: 대화 복원 시 코스 제목과 출발지 상태 보존`
- `fix: 경기 없는 날 다음 홈경기 표시`
- `fix: 일회성 코스 조건과 지속 제외 조건 분리`
- `feat: 검증된 장소 키워드의 공용 저장과 재조회 연결`
- `feat: 챗봇 복합 수정과 구간별 이동수단 변경 지원`
- `fix: 메뉴 조건 후보 누락과 근거 확인 중복 조사 개선`
- `fix: 장소 원문 대조와 단계적 후보 조사 강화`
- `fix: 식사 문맥과 메뉴 조건을 함께 반영`
- `feat: 숙박 후기 확인과 평점 기반 대안 추천`
- `fix: 기존 질문 재시도와 수정 요청의 예약 처리 보완`
- `fix: 장소 조사 중 채팅 연결 끊김과 예약 대기 표시 개선`
- `fix: 출발지만 지정한 지도 상태 보존과 요청 활동 후보 유실 방지`
- `fix: 모든 챗봇 후보 검색에 구장 내부 장소 기본 제외 적용`
- `fix: 코스 우클릭 되돌리기에서 마지막 별도 출발점 삭제`
- `refactor: 지도와 챗봇의 현재 코스 상태 및 변경 처리 통합`

출발지만 찍은 지도도 유효한 작성 상태로 전달해 과거 코스가 출발지를 덮지 않도록 보완했다. 같은 요청 조건의 검증 완료 후보를 경로 탐색에서 재사용하고, 전진하는 후보가 없을 때는 2.5km 안의 조건 충족 우회 후보를 확인한다. 백엔드 120개·프론트 64개와 타입·정적 검사 통과. 실제 Chrome에서 같은 출발 좌표를 유지한 식사→산책→사직 코스와 지도 경로를 확인했다. 세부 검증 및 남은 이동시간 합계 표시 차이는 [검증 보고서](course-web-evidence-verification-2026-10-05.md)에 기록했다.

작업 브랜치는 개인 Fork인 `origin`에 올리고 PR 대상은 팀 `upstream/develop`이다. 팀장 리뷰·승인 후 Squash and merge 규칙을 따른다. 이 정리를 위해 커밋·Push·PR 생성·Merge를 실행한 것은 아니다.

후속 수정으로 구장 내부 시설은 모든 추천 후보 경로에서 기본 제외하며, 현재 질문이 명시적으로 요청한 구장·업종만 일시 허용한다. 실제 기존 추천의 코피발리 인천문학점이 내부로 분류되어 제외되는 것을 확인했다. 코스 방문지를 우클릭으로 비운 뒤 별도 출발점도 삭제되도록 수정하고 Chrome에서 마지막 출발 핀과 작성 상태가 함께 비워지는 것을 확인했다. 상세 검증 범위는 위 검증 보고서에 기록했다.

### 추가 개선: 현재 코스 상태 통합

구장·출발지·방문 순서·이동수단·완성 여부·제목/본문을 하나의 작성 상태로 통합했다. 지도와 챗봇 수정, 초기화, 구장 변경, 저장·복원이 같은 변경 처리를 사용한다. 질문 전송 시점의 최신 코스를 직접 읽고, 늦은 답변/GPS 결과와 오래된 되돌리기가 후속 편집을 덮지 않도록 버전을 검사한다. 새 추천 적용과 저장된 편집본 복원을 분리해 빈 과거 초안으로 추천이 사라지던 문제도 수정했다.

프론트 174개·백엔드 관련 계약 67개, 타입/린트 검사 통과. 실제 Chrome에서 수동 순서 변경 이후 카페만 교체, 출발지·다른 장소 보존, 지도 핀/경로 갱신, 한 구간만 자동차로 변경, 마지막 출발점까지 우클릭 삭제와 오래된 되돌리기 차단을 확인했다. GPS의 실제 위치 획득은 재요청하지 않고 늦은 콜백을 자동 테스트했다. 세부 범위와 남은 추천 문구 문제는 [대화 및 현재 코스 상태](course-conversation.md)에 기록했다. DB 마이그레이션이나 배포는 추가하지 않았다.

### 추가 수정: 중식 메뉴 표기와 후보 실패 안내

‘카페 전에 자장면 먹을 중식집 추가’에서 후보 29곳을 찾고도 자장면/짜장면 표기 차이로 메뉴 검증이 실패하던 문제를 수정했다. 검색·본문 대조·저장 근거 재조회에 같은 메뉴 표기를 연결하고, 간짜장·유니짜장면은 실제 메뉴 문맥으로 판단한다. 짜장밥·소스·라면과 다른 가게의 근거는 계속 제외한다. 해당 메뉴의 과거 실패 대기만 새 판별기로 재확인하며 다른 캐시와 저장 정책을 유지한다.

후속 화면 검증에서 기본 중식 업종에도 웹 근거를 중복 요구하고, ‘중식 자장면’ 복합 검색의 일부 결과만 검사하던 문제를 추가로 확인했다. 기본 업종은 장소 분류로 검사하고 복합 검색에는 해당 업종의 후보를 보완한다. 자장면 메뉴 근거와 사용자 조건, 2.5km 제한은 그대로 검증한다.

후보가 있는데 조건을 확인하지 못한 경우 후보 수·미확인 조건을 구분해 안내한다. 최종 공개 장소 검증에서 남경반점을 기존 카페 앞에 추가하고 카페·산책·구장 방문을 유지했다(27.77초). 상세 재현 범위와 중간 실패는 [검증 보고서](course-web-evidence-verification-2026-10-05.md)에 기록했다. 커밋 목적 예시는 `fix: 중식집 후보 검색과 메뉴 조건 판별 누락 수정`이다.

최종 Chrome에서 동일 문장으로 복미각이 기존 카페 앞에 추가되고 출발 핀·카페·산책·구장이 유지되는 것을 확인했다. 추천 카드·지도 4개 핀·구간 이동시간·시간표가 함께 갱신됐으며 관련 백엔드 134개가 통과했다. 로컬 백엔드에 적용했고 팀 서버 배포나 공개 코스 저장은 실행하지 않았다.

### 추가 개선: 출발지부터 이동시간 우선 선택

출발지 코스에서 구장에 가까워지는 것 자체에 주던 가산을 제거했다. 조건을 통과한 후보로 최대 4개 코스를 만들어 실제 이동시간으로 고르고, 앞 방문지 주변의 후보가 없으면 2.5km 안에서 구장 방향의 후보를 확인한다. 길찾기로 전체 코스를 확인하지 못한 경우에도 같은 조건 안에서 구장 방향을 우선하며 추정값 안내를 붙인다. 요청한 활동·순서·출발지·제외 조건과 직접 만든 경로는 유지한다.

동일 구간의 길찾기를 재사용하고, 최종 시간표·카드·지도 좌표에 선택된 코스를 전달한다. 실제 사직 공개 장소 검증에서 네 후보(도보 56분 8초~70분 32초) 중 최단인 온천초등학교 → 해성관 → 티제이 → 사직야구장 → 석사빛공원을 선택했다. 전체 응답 25.68초, 단계별 후보 검색·비교 4.177초였다. 백엔드 서로 다른 235개 검사가 통과했으며, 비교 범위와 기존 합계 표시의 제한은 [검증 보고서](course-web-evidence-verification-2026-10-05.md)에 기록했다. 커밋 목적 예시는 `fix: 출발지 코스 이동시간 우선 선택과 구장 방향 대체 탐색`이다.

### 추가 개선: 이미 읽은 근거 페이지의 영업 정보 반영

추천 근거로 읽은 페이지에 명확한 영업 정보가 있으면 예정 방문 날짜·시각·체류 시간에 적용한다. 폐업·휴무·시간 충돌이 확인되면 같은 활동·음식·제외 조건의 다음 후보를 확인하고 시간표와 이동 경로 데이터를 다시 계산한다. 출발지·2.5km·직접 만든 경로와 구장 내부 기본 제외 정책을 유지한다. 정보가 없거나 애매하면 후보로 사용하며, 영업시간을 찾기 위한 추가 검색·페이지·모델 호출은 하지 않는다.

공개 남경반점의 기존 메뉴 출처에서 날짜별 영업시간을 읽어 방문 가능·불가 시각을 검증했고, 관련 백엔드 326개가 통과했다. 날짜 탭·익일·브레이크타임과 호텔 시설 시간 오인 방지도 포함한다. 영업 정보는 요청 안에서만 사용하며 DB 마이그레이션이나 팀 배포는 추가하지 않았다. 자세한 범위는 [검증 보고서](course-web-evidence-verification-2026-10-05.md)에 기록했다. 커밋 목적 예시는 `feat: 출처 페이지의 영업 정보 반영과 불가 후보 대체`다.

## 서버 관리자에게 보낼 문의 문구

> 직관 코스 챗봇에서 확인한 가게 키워드를 팀 PostgreSQL(RDS)에 공용 근거로 저장하고, 이후 동일 조건 요청에서 재사용하려고 합니다. 카카오 장소 ID에 메뉴·특징 키워드, 출처 URL, 확인일·유효기간을 연결하며 리뷰 원문이나 사용자 대화·취향은 저장하지 않습니다. 저장된 가게를 추천에서 우대하지 않고 조건 검증에만 사용합니다.
>
> 로컬 PostgreSQL 저장·재조회 검증은 진행했습니다. 배포 연결을 위해 아래 사항 확인 부탁드립니다.
> 1. 개발/배포 백엔드의 기존 `DB_*`가 동일한 RDS를 사용하는지, 이 DB에 근거 테이블 4개를 함께 사용해도 되는지
> 2. `travel` 마이그레이션 0014·0015 적용 여부와 적용 담당자, 실행 계정의 해당 테이블 조회·쓰기 권한
> 3. 환경변수/Secret을 등록하는 위치와 DB 접속정보를 안전하게 전달받을 방법
> 4. 로컬 검증을 연결할 경우 허용된 VPN/터널/개발 서버 경로와 TLS 인증서 설정 방식
> 5. 출처별 저장 허용 범위·보관 기간 설정(`PLACE_EVIDENCE_STORAGE_POLICIES`)과 웹 추가 검증 활성화/비용 제한을 어디서 관리할지
>
> 기존 배포 DB가 RDS라면 별도 벡터 DB를 새로 만들 필요는 없습니다. 필요하면 가게 근거 테이블만 별도 `RAG_DB_*` 연결로 분리할 수 있게 준비했습니다. DB 비밀번호나 API 키는 GitHub/일반 채팅에 올리지 않고 지정된 Secret 경로로 공유 부탁드립니다.
