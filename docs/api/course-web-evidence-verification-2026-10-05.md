# 코스 웹 근거 실제 검증 — 2026-10-05

> 아래 초기 16턴 기록 이후, 사용자가 원문 대조와 단계적 조사 개선을 추가 요청했다. 최신 구현은 문서 마지막의 **추가 개선: 원문 대조·단계적 조사(v6)** 절과 `shared-place-evidence.md`를 따른다. 초기 두 차례 조사 제한과 측정값은 당시 기록으로 보존한다.

## 결론

특정 메뉴를 요구하는 코스 생성·식당 교체에서 실제 후보 누락과 근거 해석 오류를 발견해 수정했다. 잠실 돈까스, 돈까스+냉모밀, 수원 짬뽕 요청은 같은 지점의 메뉴 근거를 확인한 뒤 추천했다. 근거 없는 필수 조건은 추천하지 않으며, 선택 조건은 미확인이라고 표시한다.

실제 API 16턴을 실행했다. 초기·중간 실패 5턴도 보존했으며, 개선 후 대표 8턴은 각 시나리오의 검증 기준을 통과했다. 이 표본에서 전체 추천 정확도나 성공률을 추정하지 않는다. 특히 ‘조용함’은 충분한 후기 근거를 확보하지 못했으므로, 정확하게 추천했다는 결과가 아니라 **미확인 상태를 정직하게 처리했다는 결과**다.

최종 코드의 백엔드 회귀 테스트 235개, 프론트 응답·렌더링 테스트 65개가 통과했다. 이번 화면 검증은 React 렌더링 테스트이며 브라우저에서 지도 핀을 다시 조작한 검증은 아니다.

## 방법과 범위

- 기존 사용자 대화·현재 GPS를 읽지 않는 새 가상 게스트 세션을 사용했다. 공개 구장·가게 정보만 실제 공급자에게 전달했다.
- `evaluate_courses --live`가 공개 v2 Django API 뷰와 SSE 응답, 실제 모델·카카오·웹 도구, 코스 저장, 사용량 정산을 호출했다. 추천 답변을 모킹하지 않았다.
- 측정 시간에는 API 뷰·체크포인트·공급자·정산이 포함되며 HTTP 프록시·브라우저 렌더링은 제외된다.
- 생성된 코스의 구장, 2.5km 반경, 장소 중복, 요청한 활동, 시간표, 저장 결과를 검사했다. 메뉴 검증은 카카오 링크 존재만으로 통과시키지 않고 선택 장소의 해당 키워드가 `match`인지 확인했다.
- 최종 선택 메뉴 근거의 원문을 별도로 열어 상호·지점 주소·메뉴를 대조했다. 현재 판매 가능·가격·예약·영업시간을 보장하는 검증은 아니다.
- 반복 실행 사이 공급자 캐시와 근거 부족 재검색 대기가 존재한다. 전부 캐시 없는 동일 조건 실험으로 해석하면 안 된다.

## 발견한 문제와 수정

| 문제 | 수정과 검증 |
| --- | --- |
| 가까운 일반 식당 4곳만 조사해 요청 메뉴가 있는 가게를 놓침 | 필수 메뉴/음식 분류로 카카오 후보를 보충하고 실제 키워드 검색 적중 후보부터 조사한다. 일반 업종 대체 결과는 적중으로 표시하지 않는다. 근거 없는 후보는 여전히 통과하지 못한다. |

| 인용 URL은 출력했지만 실제로 다른 페이지만 열어 근거 탈락 | 실제 검색 결과에서 발견한 미열람 URL에 한해 한 번 더 열도록 요청한다. 열기만으로 기존 주장을 승인하지 않고 새로 확인한 내용이 필요하다. 전체 턴의 2회 제한을 공유한다. |
| 근거 부족 후 추가 조사를 반복하고 없는 코스 카드를 안내 | 코스 도구가 반환한 미확인 결과를 그대로 종료한다. 주변 전체에 조건에 맞는 장소가 없다고 단정하지 않는다. |
| 조사 대기 중인 앞의 4곳 때문에 다른 후보도 조사하지 못함 | 대기 중인 후보를 건너뛰고 조사 가능한 후보를 최대 4곳 고른다. 추출기 버전 변경 전 실패 이력은 새 버전 조사를 막지 않는다. |
| 미확인 선택 조건을 모델이 추천 사유에서 확정 표현할 수 있음 | 조건 검사 결과로 추천 사유를 만들고 ‘조용함 미확인’처럼 표시한다. |
| 메뉴·후기 근거 링크가 화면에 URL 문법으로 노출될 수 있음 | 해당 코스 설명 끝의 ‘메뉴 근거’·‘후기 근거’ 작은 링크로 렌더링한다. 기존 카카오 장소 링크와 구분하며 스크립트/인증정보 URL은 링크로 만들지 않는다. |
| 웹 페이지 열기까지 검색 호출 요금에 포함 | 공급자 `search` 액션만 검색 요금으로 계산한다. `open_page`/`find_in_page`는 별도 검색 호출 요금에 더하지 않는다. |

조사 순서와 최종 추천 순서는 구분된다. 저장된 근거·이전 추천 횟수를 추천 가산점으로 쓰지 않으며, 검증된 후보의 기존 순서는 유지한다.

## 자동 검증

- 백엔드 235개: 생성·후속 수정·메뉴 후보·근거·구장·2.5km·일정·출발지·작성 상태·숙박·도구 종료 흐름.
- 프론트 65개: SSE·대화 복원·코스 반영 계약·출처 링크 실제 React 마크업. 정상 링크는 작은 버튼으로 표시하고 원문 URL을 화면 텍스트에 노출하지 않는지 검사한다.
- 출처 부적합, 다른 지점, 열지 않은 URL, 실패한 열기, 오래되거나 미래인 후기, 광고/맥락 미확인, 단일/상충 후기, AND/OR/제외 조건, 공급자 타임아웃, 재검색 대기, 전체 턴 호출 제한을 가상 근거로 검증했다.
- 가상 승인 출처로 PostgreSQL 저장→재조회와 웹 호출 생략을 검증했다. 실제 외부 사이트 저장 승인을 시험용으로 추가하지 않았다.
- 프론트 수정 파일 ESLint 및 `git diff --check` 통과.

공급자 장애는 격리된 자동 테스트로 재현했으며 외부 공급자에 실제 장애를 유발하지 않았다.

## 실행 상태와 남은 한계

현재 로컬 컨테이너에서 확인한 `COURSE_WEB_VERIFICATION_ENABLED`는 **true**, 저장 정책 수는 **0**이다. 로컬 compose의 기존 활성화 설정이 적용 중이며, 평가 명령도 해당 값을 명시한다. `.env.example`의 기본값은 false다.

`PLACE_EVIDENCE_STORAGE_POLICIES=[]`이므로 현재 요청의 웹 확인 결과는 사용할 수 있어도 실제 사이트 키워드 관찰을 공용 DB에 자동 영구 저장하지 않는다. 조사 이력·장소 참조는 남을 수 있다. 실제 RDS 연결 정보도 없어 배포 DB 저장·다른 서버에서의 재사용은 아직 검증하지 않았다.

후기 특징은 최근 180일 안의 실제 후기와 상반된 근거를 검사한다. 제한된 조사 횟수로 해당 근거를 못 찾으면 추천 가능한 가게를 놓칠 수 있다. 따라서 ‘못 찾음’을 ‘가게가 없음/메뉴를 안 팖’으로 안내하지 않는다. 이 동작은 환각을 줄이지만 검색 포괄성 문제까지 해결한 것은 아니다.

필수 메뉴/음식 분류 키워드 검색은 요청 활동별 최대 두 키워드, 웹 확인은 전체 턴 최대 두 차례다. 더 많은 복합 조건·다른 구장·광범위한 표현의 일관성은 추가 표본이 필요하다. 전 구장 성공률·반복 측정 p95·실제 사용자 부하 성능은 이번 검증 범위에 포함하지 않았다.

## 재현과 증빙

```sh
# 유료 실제 API를 사용하는 명령. 기존 공급자 설정이 있는 로컬 컨테이너 기준.
docker exec -e COURSE_WEB_VERIFICATION_ENABLED=true skn34-4rd-5team-backend-1 \
  python manage.py evaluate_courses --live --scenario evidence_menu_suwon --limit 1 \
  --output artifacts/evidence-menu-suwon-recheck.json

docker exec -e COURSE_WEB_VERIFICATION_ENABLED=true skn34-4rd-5team-backend-1 \
  python manage.py evaluate_courses --live --scenario evidence_dialogue --limit 3 \
  --output artifacts/evidence-dialogue-recheck.json
```

다른 시나리오: `evidence_menu`, `evidence_menu_and`, `evidence_quiet`, `evidence_quiet_gocheok`, `evidence_optional`.

Git 제외 경로 `backend/artifacts/`에 다음 보고서를 보존한다. `final` 이름이어도 이후 재검증 전 실패 보고서인 경우가 있으므로 파일명만으로 성공을 판단하지 않는다.

- 초기/중간: `evidence-menu-baseline.json`, `evidence-quiet-baseline.json`, `evidence-menu-and.json`, `evidence-menu-suwon.json`, `evidence-menu-suwon-final.json`, `evidence-dialogue.json`
- 대표 개선 결과: `evidence-menu-targeted.json`, `evidence-menu-and-final.json`, `evidence-menu-suwon-hints.json`, `evidence-optional.json`, `evidence-quiet-gocheok.json`, `evidence-dialogue-final.json`

보고서는 각 요청의 조건 검사, 실제 호출 시간·토큰·검색 액션, 근거 확인 흔적을 포함한다. 평가 도구 실행 자체가 커밋·Push·PR 생성을 수행하지 않는다.

## 추가 개선: 원문 대조·단계적 조사(v6)

사용자가 요청한 개선 1·2번을 적용했다. 원문 확보·메뉴 구역 추출·장소 일치·인용 일치가 확인되어야 코드가 내부 검증 표시를 부여한다. 모델 응답 스키마에는 이 표시가 없어 모델이 스스로 확인 완료를 선언할 수 없다.

- 공개 페이지를 별도로 읽어 실제 제목·주소와 메뉴 구역을 확인한다. 건물번호 10/100, 10-1/101, 숫자가 다른 지점은 구분하고, 제목에서 지점명이 생략된 일반적인 표기는 주소 확인과 함께 처리한다.
- 태그·후기·주변 가게 추천을 현재 가게 메뉴로 사용하지 않는다. 원문에 ‘짬뽕전골’이 있다고 일반 ‘짬뽕’ 판매로 줄여서 기록하지 않는다. 전체 메뉴명을 유지해 필요한 경우 별도의 의미 검사에 전달한다.
- 긍정 메뉴 조건만 있는 요청은 검색 모델에 후보별 상세 페이지 발견만 맡기고 실제 메뉴 판정은 별도 리더가 수행한다. 검색 모델의 메뉴 누락 때문에 이미 찾은 페이지를 놓치지 않으며, 추정하거나 새 URL을 만들어 채우지 않는다. 후보별 첫 URL을 먼저 읽어 첫 가게가 본문 확인 예산을 독점하지 않게 한다.
- 유력 후보 4곳에서 확인하지 못하면 다음 후보를 조사한다. 더 조사할 후보가 없으면 이전 URL을 피하여 다른 출처를 요청한다. 한 턴 최대 3차례, 첫 조사부터 90초의 추가 호출 예산이며 조사 한 차례당 새 URL 최대 4개·한 턴 최대 12개 URL을 확인한다. robots/이동을 포함한 HTTP 요청은 최대 20회다. 코스 전체 응답 시간의 상한을 보장하는 수치는 아니다.
- 조건 충족 근거를 얻으면 추가 조사를 중단한다. 2.5km 밖으로 범위를 넓히거나 저장 후보에 가산점을 주지 않는다.
- 소스가 접근을 거부하면 미확인으로 둔다. 본문은 요청 메모리에만 보관하며 공용 DB에는 기존 정책을 통과한 키워드 구조만 저장한다. 승인된 출처가 없는 현재 환경에서는 실제 관찰 영구 저장을 켜지 않았다.

### 중간 실패에서 추가로 찾은 문제

첫 수원 실측은 외부 API `RateLimitError`로 중단됐다. 해당 보고서에는 가격 미확인 호출 1개가 있어 실험 전체 비용을 정확한 총액으로 주장하지 않는다. 재시도를 반복하거나 근거를 만들어 추천하지 않았다.

수원 중간 실행은 자동 조건 검사상 통과했지만 원문 수동 감사에서 술집의 ‘짬뽕전골’을 일반 짬뽕으로 받아들인 것이 확인됐다. 이를 **추천 오류**로 기록하고 메뉴 의미 검사와 회귀 사례를 추가했다. 자동 통과만으로 정확도를 확정하면 안 된다는 사례다.

그 밖에 실제 공급자의 `sources: null` 응답 처리 오류, 제목의 지점명 축약, 건물번호 뒤 층 숫자, 긴 페이지 발췌로 메뉴 경계를 놓치는 문제, 검색 모델의 근거 누락을 수정했다. 후속 조사 성공이 이전 실패의 60분 대기에 계속 막히는 문제도 수정했다.

중간 보고서 `evidence-v4-*.json`, `evidence-v42-*.json`, `evidence-v5-*.json`은 Git 제외 경로에 그대로 보존한다. 성공·실패·이전 후보의 재검색 대기가 섞여 있으므로 단순 평균이나 전체 성공률로 사용하지 않는다.

## 숙박 후기·평점 대안과 식사 표현 인식 추가 개선

‘스테이크 썰고’처럼 식사라는 단어가 없는 요청도 기존 대화 해석 호출에서 FOOD 방문으로 인식한다. 정확한 사용자 원문을 이번 요청의 음식 조건에도 전달해 방문 유형만 인식하고 실제 메뉴를 잃어버리지 않게 했다. 이미 먹은 식사·명시적 제외·카페 디저트는 새 식사를 추가하지 않는다. 구장 방문은 관광으로 중복 추가하지 않는다. 추출기 v7은 스테이크 파히타·버거·덮밥 등의 재료를 단품 스테이크 식사로 인정하지 않는다.

숙박은 상세 정보의 유형·시설과 최근 1년의 실제 후기를 구분해 확인한다. 작성일·중복·반대 의견을 검사하고 조건을 확인하지 못하면 다음 후보를 조사한다. 최대 3차례·12곳·90초의 숙박 조사 예산을 사용하며, 상세 읽기를 누락한 URL은 같은 예산 안에서 한 번 더 확인한다. 충분한 조건 근거가 있으면 일정에 야놀자 링크만 붙인다. 충족 후보가 없으면 실제 확인한 평점과 평가 수를 보정해 대안을 선택하며 미확인임을 표시한다. 상세 판정과 보정식은 [공용 근거 문서](shared-place-evidence.md)에 정리했다.

### 발견한 오류와 한계

- 초기 복합 요청은 식사를 누락하거나 구장 방문을 관광으로 중복 추가했다. 스테이크 파히타를 스테이크 식사로 인정한 문제도 원문 대조에서 확인했다.
- `semantic-steak-lodging-live-v2.json`은 활동 종류 검사만으로 자동 통과했지만 실제로 오리 식당을 골랐다. **추천 오류**다. 음식 원문 조건을 보존하고 평가에서도 스테이크 메뉴 근거를 필수 검사하도록 고쳤다.
- 숙박 조사에서 호텔 유형이 빠지거나 ‘경기 후 숙박’이라는 방문 순서가 숙소 조건으로 들어갔다. 웹 조사와 조건 추출을 분리하고 방문 순서는 제외했다.
- 이름에 ‘호텔’이 들어간 모텔을 호텔로 인정한 실패도 확인했다(`lodging-clean-hotel-live.json`). 숙소 유형 필드를 분리해 실제 페이지 분류를 확인하며 상호 자체는 유형 근거로 인정하지 않는다.
- 점/슬래시 형식의 후기 작성일을 미확인으로 처리할 수 있던 날짜 해석기를 보강했다. 지역명이 붙은 NOL 상호도 전체 주소가 일치할 때 같은 숙소로 비교한다.
- `lodging-clean-hotel-live-v2.json`은 세 번째 조사에서 공급자 `RateLimitError`로 중단됐다. 실패 호출 비용이 없어 실험 전체 비용을 정확한 합계로 주장하지 않는다. 앞선 후보 판정·근거를 보존하고 확인하지 못한 호텔을 만들어 넣지 않았다.

초기 숙박 구현은 공개 웹 검색 모델의 읽기 결과에 의존했다. 아래 최종 v5에서 숙박도 별도 HTTP 본문·날짜·인용 대조를 추가했다. 후기는 보이는 표본만 검사하며, 접근 실패나 공급자 한도 때문에 충분한 후보가 있어도 미확인으로 끝날 수 있다. 공개 후기·작성자·HTML을 공용 DB에 저장하는 변경은 하지 않았다.

### 검증

원문 대조 추가 전 백엔드 회귀 테스트 **278개**, 기존 출처 링크·답변 마크업 프론트 테스트 **28개**가 통과했다. 후기 긍정/부정·날짜·중복, 미확인과 불일치 구분, 다음 후보 조사, 평점·평가 수 보정, 명시적 제외 보존, 숙소 유형, 식사 표현과 일회성 조건 전달을 포함한다. 이전 테스트 수와 중복되므로 합산하지 않는다. 브라우저 화면 조작을 새로 검증한 수치는 아니다.

실제 모델 식사 해석 6개 사례(스테이크·파스타·초밥·이미 먹은 식사·명시적 제외·경기 후 국수)의 활동 종류/시점이 통과했다. 이는 해석 단계 평가이며 식당 선택 정확도 100%를 뜻하지 않는다.

복합 요청 `semantic-steak-lodging-live-v3.json`에서 메뉴 근거가 있는 **아웃백스테이크하우스 인천롯데점 → 커피너티 → 인천 SSG 랜더스필드 → 숙박 대안**이 생성됐다. 83.636초, 모델 $0.01239352 + 웹 검색 $0.08 = **$0.09239352**, 원장 일치·가격 미확인 호출 0개였다. 해당 시점의 숙박 대안은 이후 유형/날짜/누락 처리 보강 전 결과이므로 최종 호텔 품질 검증으로 세지 않는다. 실제 식당의 연남로 35 주소와 토마호크 스테이크 메뉴는 [메뉴 원문](https://www.diningcode.com/profile.php?rid=SSuXV4aBmN0V)에서도 대조했다.

숙박 평점 대안의 초기 실제 실행 `lodging-review-live-v3.json`은 청결 근거가 있으나 조용함은 미확인인 후보를 그 상태 그대로 대안으로 안내했다(52.110초, 모델+웹 $0.06867632). 이 값은 최종 코드의 고정 응답 시간이나 모든 숙소 추천의 성공률로 일반화하지 않는다.

원문 대조 추가 전 `lodging-clean-hotel-final.json`에서는 세 차례·12곳 확인 후 **아늑 시그니처 호텔 인천 구월**을 미확인 평점 대안으로 코스에 넣었다. 호텔 분류는 확인했고, 추출된 청결 후기 표본은 긍정 1건·부정 1건이어서 청결을 확정하지 않았다. 57.563초, 모델 $0.00912827 + 웹 검색 $0.05 = **$0.05912827**, 원장 일치·가격 미확인 호출 0개였다. 이 실측은 충분한 후기의 성공 경로로 세지 않는다.

### 최종 숙박 v5: 원문 대조

## 추가 장애: 종료된 작업의 사용량 잠금과 재시도 예약 누락

대전 코스 질문에서 ‘진행 중인 답변이 끝난 뒤 다시 시도해 주세요’가 계속 표시됐다. 추천 조건 해석에 도달하기 전 사용량 검사에서 거절된 것이다. 로컬 원장에는 10월 4일 09:32:22 UTC에 생성된 `reserved` 한 건이 남아 있었고, 현재 백엔드 컨테이너의 시작은 같은 날 17:21:55 UTC로 더 늦었다. 현재 프로세스도 확인해 해당 이전 작업의 종료를 확인했다.

확인한 한 건만 기존 `settle_abandoned`로 정산했다. 알려진 사용량을 보존하고 확인할 수 없는 호출은 `settled_unknown`으로 기록했다. 이후 해당 지갑의 `active_turn=false`, `can_send=true`, 남은 예약 0건을 확인했다. 사용량을 초기화하거나 추정 비용을 추가하지 않았다. 이는 이번 로컬 장애의 수동 복구이며, 서버 재시작 시 자동 복구를 추가한 것은 아니다. 실행 중인 다른 worker가 있을 수 있으므로 오래됐다는 이유만으로 잠금을 해제하지 않는 정책을 유지한다.

프론트에서는 새 질문 POST만 `usage_busy`를 예약으로 처리하고 기존 질문 재시도·수정 PUT는 오류로 노출하던 누락을 수정했다. 예약에 원래 질문 ID를 유지하고, 서버가 명시적으로 거절한 경우만 자동 재시도한다. 네트워크 결과가 불확실한 요청은 자동 중복 전송하지 않는다. 예약 내용을 수정하면 최신 내용으로 보내고 취소 시 기존 대화를 보존한다. 대기 중 서버 대화가 바뀌면 예약을 멈춰 재확인하며, 원래 질문이 삭제됐으면 새 POST로 바꾸지 않는다.

프론트 `chat-provider-race`, `chat-direct`, `chat-progress` **102개**, 백엔드 `test_usage_credits` **44개**, 프론트 TypeScript 검사와 해당 컴포넌트 ESLint가 통과했다. 이 수치는 이전 추천 품질 테스트와 별도이며 합산하지 않는다. 실제 지갑 복구 상태와 모의 서버를 사용한 예약 흐름을 확인한 결과로, 이번 장애 질문의 실제 모델 답변 생성 완료를 뜻하지 않는다.

## 후속 장애: 프록시 연결 끊김과 실제 브라우저 검증

같은 요청이 ‘다음에 보낼 질문’에 머무르거나 연결 오류로 끝나는 후속 제보를 확인했다. 이번 원장은 정상 정산되고 있었으며 과거 잠금과 원인이 달랐다. Nginx에 채팅 전용 설정이 없어 공개 이벤트가 뜸한 식당·호텔 조사 중 기본 60초 읽기 제한으로 연결이 끊겼다. 04:17:27, 04:28:05, 04:29:53 UTC의 `upstream timed out ... while reading upstream` 로그를 확인했다. 서버 조사는 그 후에도 진행되어 다른 질문이 사용량 검사에서 대기했다. 대화 삭제는 실행 중인 외부 호출의 즉시 종료를 뜻하지 않는다.

- 대기 중 10초마다 SSE 주석으로 연결을 유지한다. 실제 진행 이벤트 기준의 정체 제한과 분리해 heartbeat가 정체 작업을 무한 연장하지 않는다.
- 실제 공개 이벤트 대기 기본값은 식당·숙박의 연속 조사 예산을 감안해 300초로 조정했다. 코스의 검색 예산이나 전체 턴 시간을 무제한으로 만든 것은 아니다.
- 로컬·HTTPS Nginx의 `/api/v2/chat/`에 버퍼링/캐시 해제, 읽기 제한 360초를 설정했다. 로컬 `nginx -t` 후 reload했다.
- 배포 Compose는 요청 처리와 worker 생존 확인을 분리하는 Gunicorn `gthread`, 프로세스 2개·스레드 각 4개로 변경했다. 팀 서버에 배포한 것은 아니다.
- 프론트는 분할 수신되는 SSE 주석을 답변 이벤트와 구분한다. 서버의 이전 작업을 기다리는 예약에는 ‘이전 요청 처리 대기’와 이유를 표시한다. 확인 주기는 기존 1.2초다.

첫 브라우저 검증에서 프론트 개발 서버가 변경된 소스를 감지하지 않아 예전 번들을 계속 제공한 것도 확인했다. 따라서 heartbeat를 구버전 파서가 형식 오류로 처리했다. 소스 테스트 통과만으로 실제 반영을 판단할 수 없었다. 프론트 개발 컨테이너를 재시작하고 브라우저를 새로고침해 실제 JS 번들에 `remainingFields`·`queueWaitingForServer`가 들어간 것을 확인한 뒤 다시 검증했다. Windows/Docker 파일 감지가 누락되는 경우에는 이후 변경에서도 실제 번들 확인과 개발 서버 재시작이 필요하다.

## 출발 핀 유실과 식사·산책 누락 후속 검증

Chrome 사용 화면에서 ‘여자친구랑 초밥 먹고 산책 하다가 구장 갈건데 코스 짜줘’를 확인했다. 사용자가 직접 찍은 출발 핀 1개가 추천 적용 후 사라졌고, 최초 답변은 식당과 사직야구장만 포함했다. 카드의 되돌리기로 원래 핀을 복원해 같은 위치에서 재검증했다.

- 출발 핀만 있는 경우 프론트가 `currentCourse` 자체를 생략했다. 서버는 과거 추천을 복원한 뒤 그 추천의 `writerState.origin=null`로 현재 지도에서 보낸 출발지를 덮었다. 빈 방문 목록이라도 유효한 `writerState`를 포함한 요청은 현재 화면의 명시적 상태로 처리한다. 빈 추천 카드의 허용 범위는 넓히지 않았다.
- 구버전 클라이언트에서 출발지만 보낸 경우에도 과거 방문 목록을 끼워 넣지 않는다. 현재 화면에서 출발지를 명시적으로 삭제한 경우에는 이전 출발지를 되살리지 않는다.
- 카카오 산책 조회에서는 사직 반경 내 36곳이 확인됐다. 출발지 수정 후 첫 실브라우저 재검증에서는 산책이 들어왔지만 식사가 빠졌다. 후보 묶음이 달라질 때 이미 같은 요청 조건으로 검증된 장소까지 재판정하던 경로를 보완했다. 같은 요청·같은 조건의 통과 결과만 재사용하며 조건 변경·제외 목록은 계속 검사하고, 저장 여부로 순위 가산하지 않는다.
- 출발지 기준 탐색에서 구장 방향으로 전진하는 후보가 없으면 요청한 활동을 바로 버리지 않고, 같은 조건을 만족하는 우회 후보를 확인한다. 구장 반경 2.5km와 금지·제외 조건은 유지한다. 이 선택을 사용한 경우 돌아가는 구간이 포함됐다는 안내를 붙인다.

최종 같은 요청은 **57.033초**에 완료됐다(로컬 사용량 원장 182, 입력 59,718·출력 2,623토큰). 지도에 **기존 출발지 → 육회바른연어 부산사직운동장점 → 석사빛공원 → 사직야구장**이 반영됐다. 앞선 검증과 최종 결과의 출발 위도·경도를 비교해 정확히 일치함을 확인했다. 지도에는 세 구간의 도보 시간이 각각 15분·4분·9분으로 표시됐다. 마지막 실브라우저 요청에서 누락 경고는 없었다.

백엔드 출발지·후보·조건·활동·경로·대화 수정 관련 **120개**, 프론트 문맥·작성기·초안 관련 **64개**가 통과했다. TypeScript, 변경 대상 ESLint, diff 공백 검사도 통과했다. 중간 회귀 검사에서 동일 후보 묶음을 두 번 판정한 테스트 실패 1건을 확인하고 묶음 캐시와 장소별 통과 캐시를 함께 유지하도록 고친 후 120개를 재실행했다.

프론트 개발 컨테이너를 재시작하고 실제 번들에서 `allowEmptyContext`를 확인했다. 새로고침한 Chrome에서 최신 답변의 코스를 다시 적용해 출발지와 세 방문 핀·경로를 확인했다. 화면 캡처는 Git 제외 경로 `backend/artifacts/course-origin-walk-fixed-2026-10-05.jpg`에 보관했다. 최초 산책 누락 턴에는 후보 단계별 로그가 남아 있지 않아 당시 어느 개별 후보가 탈락했는지까지 단정하지 않는다.

별도 남은 표시 차이: 새 코스 답변의 ‘총 도보’는 첫 추천 장소 이후 구간(이 사례 13분), 지도 합계는 별도 출발지 구간을 포함한 값(28분)이다. 이번 수정으로 좌표·핀·지도 경로는 복구했으며 두 합계의 계산 범위 통일은 이 검증의 통과 주장에 포함하지 않는다.

## 구장 내부 장소 추천 차단과 마지막 출발점 삭제

카카오 공급자는 `stadiumArea`를 표시했지만 챗봇의 출발지·동선 탐색, 메뉴·브랜드 추가 검색, 오래된 RAG 후보 선택에서 이를 공통으로 검사하지 않았다. 일부 일반 검색은 구장 도로명 주소나 이름만 비교했다. 대화 기억 초기화로 정책을 잊은 문제가 아니라 후보 경로마다 적용 범위가 달랐던 문제다.

- `course/venue_policy.py`에서 후보 좌표를 현재 지도 경계와 다시 대조한다. 구장 내부는 기본 제외하고, 현재 질문이 명시적으로 요청한 구장·업종만 이번 호출에서 허용한다. 권한은 대화 취향이나 RAG에 저장하지 않는다.
- 새 생성, 출발지·동선 검색, 추가·교체, 메뉴 검색, 캐시/RAG 선택 모두 같은 검사를 거친다. 내부 후보만 있는 첫 페이지에서 멈추지 않고 공급자의 다음 페이지를 확인한다. 외부 지점은 상호에 ‘야구장점’이 있다는 이유만으로 배제하지 않는다.
- 경기장 목적지 자체와 사용자가 이미 선택한 다른 방문지는 유지한다. 기존 2.5km와 종합운동장 제외 영역은 유지하며, 내부 허용 요청이 있어도 해당 제외 영역을 해제하지 않는다. 경계는 프로젝트 지도 분류이며 공식 입장권 구역의 측량 정보는 아니다.

실제 Chrome의 기존 답변에 있던 **코피발리 인천문학점**을 카카오로 다시 조회해 `scope=internal`, `stadium=MUNHAK`를 확인했다. 수정된 필터는 이 후보를 제외했다. 실제 모델로 일반 카페 요청·구장 안 카페 요청·구장 안 카페 제외 요청을 해석해 각각 기본 제외·명시 허용·제외를 확인했다. 실제 새 생성은 **13.06초**에 **커피너티(외부) → 인천 SSG 랜더스필드**를 반환했다. 사용자 대화에 추가 메시지를 저장하지 않는 서버 검증이며, 유료 제공자 비용을 별도로 집계한 성능 실험은 아니다. 결과는 Git 제외 경로 `backend/artifacts/course-venue-policy-live-2026-10-05.json`에 보관했다.

출발점이 남는 원인은 우클릭이 방문 배열만 처리하고 별도로 보관한 챗봇/GPS 출발지는 지우지 않았기 때문이다. 방문지를 모두 되돌린 다음 우클릭하면 별도 출발 상태도 지운다. 진행 중 위치 요청도 무효화하며 부모 작성 상태와 챗봇 문맥에 삭제가 전달된다. 완성 잠금 중에는 삭제하지 않는다.

Chrome에서 **내 코스 0개 + 출발점만 남은 실제 상태**를 확인한 뒤 최신 프론트를 불러와 우클릭했다. 출발 핀이 사라지고 출발 선택이 ‘첫 번째 지점’으로, 전체 보기·초기화 버튼이 비활성으로 바뀌었다. 캡처는 `backend/artifacts/course-origin-rightclick-fixed-2026-10-05.jpg`다. 오래된 추천 카드 적용 시에는 저장된 편집본(방문 0개·출발점만 존재)이 복원되어, 이번 브라우저 검증은 마지막 출발점 삭제를 직접 확인했다. 챗봇 방문을 순서대로 지운 뒤 별도 출발점까지 지우는 전체 순서는 자동 회귀 테스트로 확인했다.

최종 백엔드 관련 **148개**, 프론트 관련 **65개**, TypeScript와 대상 ESLint가 통과했다. Next 개발 서버의 자동 생성 타입 파일에 남은 중복 꼬리는 해당 생성 파일만 재생성한 후 타입 검사를 다시 통과했다. 백엔드 확대 검증 중 기존 테스트가 모든 가상 가게를 구장 내부 좌표 또는 좌표 없이 만들던 것을 실제 외부 후보 좌표로 바로잡았으며, 정책을 완화하지 않았다. 148개에는 9개 구장의 모든 방문 업종 기본 제외, 현재 요청에 한한 업종·구장 허용, 부정 표현, 새 생성·부분 수정, 출발지·동선·다음 페이지 검색과 기존 회귀 사례가 포함된다.

## 후속 수정: 자장면 표기 차이로 중식집 추가 실패

제보 문장 ‘카페 가기전에 중식집 하나 들러서 자장면 먹고 싶어. 수정해줘’를 현재 화면에 보이는 공개 장소 세 곳(대웅다방 → 대흥1어린이공원 → 대전 한화생명 볼파크)으로 재현했다. 기존 대화 원문을 DB에서 검색하지 않고 공개 장소 ID와 질문만 사용했다. 후보는 **29곳**이었지만 메뉴 근거의 ‘자장면’과 실제 메뉴의 ‘짜장면·유니짜장면·간짜장’을 연결하지 못해 선택 결과가 없었다. 수정 전 후보 조사 3회·39.98초의 실패 기록은 Git 제외 경로 `backend/artifacts/jajang-public-baseline.json`에 있다. 원래 사용자 요청의 내부 추적 로그를 읽은 결과는 아니다.

- 자장면/짜장면/자장/짜장을 같은 메뉴 표기로 검색하고 본문과 대조한다. 간짜장·유니짜장면·삼선짜장 같은 메뉴는 원문을 보존한 별도 의미 검사로 판단한다. 짜장밥·소스·라면, 후기의 희망 표현, 다른 지점의 메뉴는 판매 근거로 인정하지 않는다.
- 같은 메뉴 표기로 저장된 유효 근거를 재조회할 수 있게 했다. 저장 원문·관찰 키워드는 바꾸지 않고 판정 입력에서만 요청 표기에 맞춘다. 이미 저장된 가게를 추천 순위에서 우대하지 않는다.
- 이전 판별기로 생긴 해당 메뉴의 실패 기록만 새 조사 대상으로 삼는다. 수정 후 조사 실패의 재시도 대기와 다른 메뉴의 대기는 유지하며 전체 캐시를 비우지 않는다.
- 후보가 있는데 메뉴 조건 근거가 부족한 경우 후보 수와 확인하지 못한 조건을 안내한다. ‘가게가 없다’는 인상을 주거나 이미 제공한 업종을 다시 묻는 응답을 제거했다.
- 한식/중식/일식/양식 같은 기본 업종은 제공된 장소 분류로 확인한다. 모델이 이를 `cuisine`으로 반환해도 `catalog`로 처리하고, 자장면 판매 여부·비건 같은 세부 조건은 별도 검증을 유지한다. 제외·필수·선택과 OR 조건 묶음을 바꾸지 않는다.
- ‘중식 자장면’처럼 업종과 메뉴가 합쳐진 검색어는 해당 업종 검색도 함께 수행한다. 첫 복합 검색 결과가 있다는 이유로 다른 중식집을 누락하지 않는다. 정확한 메뉴·브랜드 조건과 2.5km·기존 방문/구장 내부 제외 정책은 후속 선택에서도 유지한다.

표기 수정 단계의 실제 검색·본문 검증을 포함한 코스 수정은 **25.96초·조사 1회**에 **남경반점 → 대웅다방 → 대흥1어린이공원 → 대전 한화생명 볼파크**를 반환했다. [남경반점 메뉴](https://www.diningcode.com/profile.php?rid=GxMLyWQk5o7a)의 상호·전체 주소·메뉴 구역을 대조했다. 원래 세 방문 ID와 순서가 유지되고 식당→카페 도보 6분을 포함한 시간표가 재계산됐다. 기록은 `backend/artifacts/jajang-public-fixed.json`이다.

그러나 첫 Chrome 재검증에서는 ‘중식 · 자장면 · 중식 자장면’ 조건으로 16곳을 찾고도 실패했다. 기본 업종까지 별도 웹 근거로 조사하는 것을 확인해 분리했다. 이어 복합 검색어만 사용한 공개 재현은 6곳만 조사해 실패했다(`jajang-compound-fixed.json`, 38.99초). 업종 검색 보완 후 같은 복합 조건은 **27.77초·조사 1회**에 남경반점 추가와 기존 세 방문 ID 보존에 성공했다(`jajang-compound-final.json`). 중간 성공 한 건만으로 전체 수정 완료로 판단하지 않았다.

위 서버 실행은 공개 장소로 만든 검증이며 비용을 별도 집계하지 않았다. 수정 전후 실행 범위가 달라 응답 속도 개선율로 해석하지 않는다. 새 DB 마이그레이션이나 팀 서버 배포는 없다.

최종 Chrome 재검증에서는 원문 그대로 다시 전송해 **복미각 → 대웅다방 → 대흥1어린이공원 → 대전 한화생명 볼파크**를 받았다. 기존 출발 핀 위치와 세 장소를 유지하고 지도 핀 4개·경로가 갱신됐다. 추천 카드와 지도 구간 안내에서 출발→복미각 17분, 복미각→대웅다방 8분, 이후 22분·19분이 일치하는 것을 확인했다. 전체 합계 65분은 구간별 올림값 합이 아니라 초 단위 합계를 반올림한 결과다. 메뉴 근거 링크도 표시됐다. 화면은 `backend/artifacts/jajang-add-fixed-2026-10-05.jpg`에 보관했다. 대화에 검증 질문을 추가했으며 공개 코스 저장은 실행하지 않았다.

최종 코드에서 관련 백엔드 **134개**가 통과했다. 근거·저장/재조회·후보·수정 70개와 대화·요청 활동·식사 표현·제보 회귀·구장 내부 제외 64개다. 중간 실행 수와 합산하지 않는다.

## 출발지 코스: 이동시간 우선, 후보 부족 시 구장 방향으로 확장

기존 단계별 점수는 이전 지점과의 거리를 빼면서 구장에 가까워지는 정도를 더했다. 같은 방향에 있는 두 장소 중 구장에 더 가까운 곳이 오히려 유리해져 출발지 주변을 지나치는 경향이 있었다. 변경 후에는 먼저 방문으로 추가되는 거리로 후보를 추리고, 조건을 통과한 코스 최대 4개를 실제 이동시간으로 비교한다. 비교 범위는 출발지(반경 밖 출발지는 경로 진입점) → 요청한 경기 전 방문 → 구장 → 요청한 경기 후 방문이다. 경기 전·후 구분과 활동 순서는 바꾸지 않는다.

- 앞 방문지 주변에서 조건에 맞는 장소를 찾지 못하면 구장 반경 2.5km로 검색을 확장하고, 경기 전에는 구장 방향으로 진행하는 후보를 우선한다. 음식 조건·제외 장소·구장 내부 기본 제외·반경 제한은 같은 필터를 사용한다. 그 안에도 없으면 요청하지 않은 활동을 추가하는 대신 누락을 안내한다.
- 경로 일부만 확인한 코스와 전체 이동시간을 확인한 코스를 추정치로 섞어 비교하지 않는다. 전체 경로를 확인한 코스가 없으면 조건 충족 후보 중 구장 방향을 우선하고, 이동시간에 추정값이 포함될 수 있음을 알린다. 경기 후는 구장 또는 직전 장소에서 가까운 후보를 선택한다.
- 비교 호출은 최대 18구간, 새 호출을 시작하는 시간 예산은 8초다. 이미 진행 중인 제공자 요청의 최대 10초 제한은 별도여서 전체 비교의 엄격한 8초 상한은 아니다. 실패 구간은 재호출하지 않고 다른 후보를 시도하되 실패 2회면 추가 조회를 멈춘다. 같은 방향의 동일 구간은 요청 안에서 재사용하고, 최종 시간표에도 같은 조회 결과를 쓴다.
- 기본 도보와 명시적 자동차·대중교통을 구분한다. 실제 차량 길찾기 시간에 주차가 포함됐다고 표시하지 않으며 대중교통 시간을 도보로 표시하지 않는다. 사용자가 직접 만든 경로는 기존 경로 주변 선택을 유지한다.

공개 장소 **온천초등학교**를 출발지로 같은 질문 ‘중식집, 카페 갔다가 구장 가고 싶어. 끝나고 산책도 좀 하고 싶어’를 새 생성했다. 개인 대화 DB 조회나 사용자 대화 추가 없이 실제 카카오·모델을 호출했다. **25.68초**, 단계별 후보 검색과 경로 비교 합계 **4.177초**, 길찾기 9구간으로 네 코스를 모두 확인했다.

| 후보 코스 | 출발지부터 마지막 방문까지 도보 이동시간 |
| --- | --- |
| 해성관 → 티제이 → 사직야구장 → 석사빛공원 | **3,368초 (56분 8초), 선택** |
| 리향원 → 티제이 → 사직야구장 → 석사빛공원 | 4,232초 (70분 32초) |
| 해성관 → 낫스소스 → 사직야구장 → 석사빛공원 | 3,443초 (57분 23초) |
| 해성관 → 티제이 → 사직야구장 → 단비동산공원 | 3,436초 (57분 16초) |

출발 좌표 보존, 식사·카페·산책 포함, 모든 방문지의 구장 반경 2.5km 이내를 확인했다. 근거 결과는 Git 제외 경로 `backend/artifacts/route-duration-public-2026-10-05.json`에 있다. 추가 LLM 호출 없이 시간 비교를 수행하며 이 실행에서 외부 서비스 비용은 별도로 집계하지 않았다.

백엔드 관련 234개 회귀 검사를 통과한 후 추천 카드·지도 좌표·시간표까지 선택 결과가 동일하게 전달되고 경로를 중복 조회하지 않는 통합 사례 1개를 추가했다. 최종 이동시간 모듈 20개를 모두 통과해 **서로 다른 235개 검사**가 통과했다. 모의 경로 장애·오래된 경로·잘못된 시간·취소·호출 상한·조건 불충족·구장 방향 대체·직접 그린 경로 보존을 포함한다. 중간에는 테스트 문장의 암묵적 기본 방문을 기대에서 빠뜨린 1건을 확인해, 명시적인 요청 방문 구성을 설정한 뒤 재검증했다.

제한: 최대 4개의 추린 후보 조합 안에서 비교하므로 모든 가게 조합의 전역 최단경로를 보장하지 않는다. 실제 도로 이동거리는 2.5km를 넘을 수 있으며, 2.5km는 방문지 좌표의 구장 반경이다. 기존 답변의 ‘총 도보’와 코스 전체 시간은 첫 추천 장소부터 계산하고 별도 출발 구간은 지도에서 확인하는 구조를 이번에 통합하지 않았다. 위 56분 8초는 출발 구간을 포함한 **선택용 비교 값**이며 기존 답변의 55분 표시와 범위가 다르다. 이번 검증은 서버 실제 생성과 데이터 계약 검증이며 새 Chrome 조작 검증이나 팀 서버 배포는 포함하지 않는다.

## 근거 페이지에서 확인한 영업 정보 반영

사용자 정책에 따라 영업시간 확인을 추천의 필수 요건으로 만들지 않았다. 메뉴·특징·숙소 조건의 근거로 이미 읽은 페이지에서 같은 상호와 전체 주소가 확인되고 영업 정보가 명시된 경우에만 반영한다. 영업시간을 찾기 위한 별도 검색·페이지 조회·모델 호출은 추가하지 않았다. 본문을 읽지 못했거나 시간이 없거나 애매한 곳, 저장된 메뉴 근거만 재사용해 영업 정보를 새로 읽지 않은 곳은 그대로 후보로 사용한다.

- 확실한 폐업은 제외하고, 정기 휴무와 날짜별 예외·영업시간·브레이크타임·주문 마감은 **예정 방문 날짜·도착 시각·체류 시간**으로 판단한다. 현재의 ‘영업 종료’ 표시만으로 미래 방문을 제외하지 않는다.
- 자정을 넘는 영업과 익일 방문을 구분한다. 페이지의 ‘오늘’ 또는 월·일 날짜 탭을 매주 반복되는 정보로 확대하지 않는다. 호텔 조식·수영장·체크아웃 시간은 숙소 자체의 영업시간으로 사용하지 않는다. 후기 속 옛 폐업 언급, 다른 지점, ‘폐업 신고’ 버튼도 폐업 근거로 쓰지 않는다.
- 출처 간 명시적 정보가 충돌하거나 격주·공휴일 등 날짜를 확정할 수 없으면 미확인으로 남기고 후보를 유지한다. 지원하지 않는 페이지 형식까지 영업 여부를 보장하는 기능은 아니다.
- 방문이 불가능한 경우 같은 활동과 음식·제외 조건을 유지하며 다음 후보를 확인한다. 2.5km와 구장 내부 기본 제외, 출발지·직접 그린 경로 조건을 유지한다. 확정된 시간 충돌은 전체 시간표를 다시 계산해 검사하며 바뀐 장소·시간표·이동 구간을 응답 데이터에 함께 반영한다. 한 방문의 대체 확인은 최대 4회이고, 대안이 없으면 그 방문만 제외한 이유를 안내한다.
- 영업 정보는 현재 요청 안에서만 보관한다. RAG DB에 원문·영업시간을 새로 저장하거나 마이그레이션을 추가하지 않았으며, 저장된 장소의 추천 순위도 올리지 않는다.

공개 장소 **남경반점**의 기존 [메뉴 근거 페이지](https://www.diningcode.com/profile.php?rid=GxMLyWQk5o7a)를 실제 페이지 리더로 확인했다. 같은 상호·전체 주소와 2026-10-06 날짜 탭의 **11:30~19:30**을 읽었다. 해당 날짜의 50분 방문을 10:00·23:00에는 제외하고 12:00·18:00에는 유지했다. 페이지 리더의 공개 요청은 robots 확인과 본문 조회 2회이며, 별도 영업시간 검색이나 모델 호출은 없었다. 영업 종료까지 남은 시간과 ‘폐업 신고’ UI를 폐업으로 잘못 해석하지 않는 것도 확인했다. 구조화된 검증 결과만 Git 제외 경로 `backend/artifacts/availability-public-page-2026-10-05.json`에 보관했다.

관련 백엔드 **326개**가 통과했다. 새 생성·부분 수정에서 시간 충돌 후보 교체, 다른 방문·출발지 보존, 시간표 재계산, 정보 없는 후보의 추가 검색 생략, 숙소의 기존 조회 재사용과 요청 간 상태 분리를 포함한다. 실제 공개 페이지 읽기와 자동 통합 검사 결과이며, 이번 변경에 대한 Chrome 전체 흐름 재실행이나 팀 서버 배포는 포함하지 않는다. 파일 변경 후에도 개발 서버 프로세스가 갱신되지 않아 로컬 백엔드 컨테이너를 재시작해 반영했다.
