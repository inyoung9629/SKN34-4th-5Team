# 공용 장소 근거 연결

2026-10-05 현재 구현 기준. `plan_course → course.agent → editing.choose → evidence_memory`가 활성 경로다. 과거 별도 결정론적 코스 구현을 설명하는 문서보다 이 문서와 실제 코드를 우선한다.

## 저장·사용 흐름

1. 현재 요청과 명시적으로 기억한 조건을 분리하고 필수/선택/제외를 해석한다.
2. 카카오·기존 장소 자료에서 구장 2.5km 안 후보를 확보한다. 장소의 동일 ID로 필요한 키워드만 조회한다.
3. 같은 지점·유효기간·출처 정책·현재 적용 조건을 통과한 관찰만 사용한다. 한 후기, 상충 근거, 근거 누락은 확정 사실로 바꾸지 않는다.
4. 메뉴·후기 등의 추가 근거가 필요하고 `COURSE_WEB_VERIFICATION_ENABLED=true`이면 한 번에 후보 최대 4곳, 웹 도구 최대 8회, 공급자 호출 최대 45초로 검색한다. 코스 한 턴에서는 최대 3차례 조사하며 같은 조건 해석을 재사용한다. 첫 후보가 부족하면 미조사 후보, 후보를 모두 조사했으면 다른 출처를 찾는다. 필수 조건을 충족한 새 후보를 찾으면 중단한다. 검색·본문 읽기는 첫 조사부터 90초 예산을 공유하며, 추가 의미 판정에는 25초 여유가 필요하다. 이는 코스 전체 응답 시간 보장이 아니다.
5. 실제 검색 도구에서 발견한 URL만 기존 공개 페이지 리더로 별도 열어 상호·도로명 주소·메뉴 구역과 근거 문장을 대조한다. 긍정 메뉴 조건만 있는 요청은 검색 모델이 후보별 상세 페이지를 찾고, 판매 여부는 별도 리더가 실제 메뉴에서 판정한다. 첫 후보가 본문 읽기 예산을 독점하지 않도록 후보별 첫 URL을 먼저 검사한다. 메뉴명이 정확히 같지 않거나 후기·부정 근거라면 짧은 원문 근거로 별도 의미 판정을 거친다. 모델이 ‘본문을 읽었다’고 출력하는 것만으로 통과할 수 없다. 출처 저장 정책이 설정된 URL의 검증된 키워드만 PostgreSQL에 기록한다. HTML·리뷰 원문·작성자·채팅·취향은 공용 DB에 저장하지 않는다.
6. 다음 요청에서 조건이 같으면 재사용한다. 저장 사실/이전 추천 횟수/근거 개수 자체는 추천 가산점이 아니다. 조건을 통과한 후보를 기존 거리·동선 기준으로 비교한다.

기본 브랜드·업종 조건은 이름/업종에서 판단한다. 숙박은 NOL(야놀자) 상세 정보·최근 후기·평점으로 별도 확인하며 아래 숙박 절의 추가 조사와 대안 정책을 적용한다. 이 키워드 저장기의 주 대상은 메뉴·음식 분류·검증 가능한 후기 특징이다. 시설의 법적 보장·알레르기 안전·실시간 영업/가격/예약 가능을 보증하지 않는다. 시점·좌석 등에 한정된 근거는 현재 자동 수집기가 일반 특징으로 저장하지 않는다.

필수 메뉴/음식 분류 요청은 활동별 최대 두 키워드로 카카오 후보를 보충한다. 검색 결과가 비면 돈까스/돈가스/돈카츠, 냉모밀/냉소바 등의 표기 변형을 최대 3개까지 시도한다. 모든 조회와 최종 후보는 구장 반경 2.5km를 유지한다. 실제 키워드 적중과 이름·업종 신호는 제한된 웹 조사 대상을 고를 때만 사용하며, 조건 근거 자체나 저장 장소 우대 점수가 아니다. 조건 통과 후 후보 순서는 유지한다.

본문은 요청 메모리에서만 다룬다. 구역 경계를 잃는 발췌문 대신 읽은 전체 가시 텍스트를 검사하며, 조사 한 차례당 새 URL 최대 4개·한 턴 최대 12개 URL·robots/이동을 포함한 최대 20회 HTTP 요청으로 제한한다. 허용된 공개 호스트, 공개 IP, robots, HTTP 제한을 적용하며 로그인·CAPTCHA·자바스크립트 실행이나 제한 우회는 하지 않는다. 차단·본문 부재·시간 초과는 미확인이다. 전체 본문을 모델·DB·평가 보고서에 넣지 않는다.

이전 버전 코스 추출기로 저장한 관찰은 새 `course-evidence-v7` 경로에서 자동 재사용하지 않고 재검증한다. 스테이크 파히타·버거·덮밥 등의 재료/토핑을 단품 스테이크 식사로 받아들이지 않는다. 사람이 별도로 검토한 다른 추출기의 유효 근거는 기존 정책을 따른다.

필수 근거를 확인하지 못한 생성 요청은 없는 코스 카드를 안내하거나 같은 조사를 반복하지 않고 미확인 결과로 종료한다. 교체 요청에서는 기존 코스를 보존한다. 선택 조건은 미확인 상태를 명시하며, 확인된 메뉴·후기의 URL만 해당 일정 설명 끝에 작은 근거 링크로 표시한다.

조회 실패/근거 부족에는 재검색 대기시간(오류 15분, 근거 없음 60분)을 기록한다. 자동 재시도 예약은 아니다. 대기 중인 후보를 건너뛰고 다른 후보를 조사하며 추출기 버전이 바뀌면 과거 버전 실패 대기를 적용하지 않는다. 검색/모델 호출 횟수는 기록하고 공급자별 금액을 알 수 없으면 비용은 NULL로 둔다. 웹 검색 호출 수에는 `search` 액션만 포함하며 페이지 열기·본문 찾기를 검색 요금으로 중복 계산하지 않는다.

같은 장소·키워드가 후속 출처에서 확인되면 앞선 실패의 대기를 해제한다. 영구 저장 정책이 없는 환경에서도 과거 실패가 나중 성공을 가로막지 않는다. 공급자 오류에는 같은 턴에서 연속 재시도하지 않는다.

## 숙박 확인과 평점 대안

2026-10-05 추가 요청에 따라 숙박의 일괄 미확인 규칙을 제거했다. 호텔 유형·시설은 NOL 상세 정보, 청결·조용함은 최근 365일 안에 실제 이용자가 작성한 후기로 구분한다. 웹 검색에서 발견한 공개 상세 페이지를 별도 HTTP 리더로 읽고 같은 상호·주소를 확인한다. 최근 후기의 날짜별 본문을 모델에 제공한 뒤, 반환된 날짜와 인용문이 실제 같은 후기 블록에 있는지 코드로 대조한다. 모델이 검색만으로 만든 후기 주장이나 존재하지 않는 날짜/인용은 판정에 쓰지 않는다. 유형은 실제 페이지 제목의 호텔/리조트·모텔 분류에서 읽어 상호와 구분한다.

동일 페이지의 실제 후기 여러 건을 사용할 수 있다. 점·슬래시·한글 날짜 표기도 날짜로 정규화한다. 날짜 미확인·미래·1년 초과·중복/유사 복사 후기는 제외하며, 긍정 2건 이상이고 관찰한 관련 후기 중 긍정 비율이 65% 이상이면 해당 후기 조건을 통과시킨다. 부정 2건 이상이면서 부정이 더 많으면 불일치, 나머지는 미확인이다. 이는 확인한 후기 표본의 판단 기준이며 전체 후기를 분석했다는 의미가 아니다. 실제 후기 원문·작성자는 공용 DB에 저장하지 않는다. 상호에 ‘호텔’이 있어도 실제 분류가 모텔이면 호텔 조건을 충족하지 않는다.

웹 조사 전에 숙박 조건을 별도로 추출해 호텔 유형·시설·후기 조건이 검색 중 빠지지 않게 한다. 후보 4곳은 한 차례의 조사 단위다. 미확인이면 다음 후보를 조사하며 최대 3차례·12곳, 총 검색 예산 90초를 적용한다. 차례당 공개 페이지 최대 4개를 읽고 제공된 본문의 조건을 해석한다(웹 검색과 본문 해석 각 1회). 숙박 HTTP 읽기는 robots/이동을 포함해 최대 14회이며 허용 호스트·공개 IP·robots·응답 크기·시간 제한을 적용한다. 후기 원문 읽기가 실패하면 검색 모델의 후기를 확정하지 않는다. 평점 대안에는 실제 열어 본 웹 상세의 평점도 사용할 수 있다. 조건을 충족한 후보를 얻으면 멈춘다. 같은 생성 과정의 경로 필터는 이미 확인한 숙소를 다시 조사하지 않는다. 후속 조사에서도 최초 조건 ID와 의미를 유지한다. 이 예산은 식당 검증의 예산과 별개이며 전체 응답 시간의 상한은 아니다.

충족 후보가 끝까지 없으면 같은 지점의 실제 평점·평가 수가 확인된 미확인 후보 중 하나를 대안으로 선택한다. 5점 척도로 환산한 평점 R과 평가 수 n에 대해 `(n * R + 20 * 3.5) / (n + 20)`를 비교한다. 낮은 표본의 만점이 쉽게 우선하지 않게 하는 구현상의 보정값이며, 절대적인 품질 지표가 아니다. 명시적 불일치나 지켜졌는지 모르는 제외 조건은 평점으로 덮어쓰지 않는다. 평점·평가 수가 없으면 만들어 채우지 않는다. 비교 범위는 실제 확인한 후보이며 구장 2.5km 제한을 유지한다.

충족한 숙소는 이름·방문 시각과 작은 야놀자 링크만 표시하고 조건 근거 설명을 덧붙이지 않는다. 평점 대안은 조건 미확인을 표시한다. 숙박 가격·예약 가능 여부는 계속 제외한다. 기존 v1~v4 캐시는 사용하지 않는 v5 키로 분리했으며, 이 변경은 공용 RAG 테이블에 숙박 후기·평점을 새로 적재하지 않는다. 후기 원문은 해당 요청 메모리에서만 처리하고 캐시/공용 DB/평가 보고서에는 남기지 않는다.

## 로컬과 RDS

기본은 기존 `default` DB다. 로컬은 Docker PostgreSQL, 배포 환경에서 `DB_*`가 RDS를 가리키면 같은 코드가 RDS에 저장한다. `llm_documentchunk`에 원문을 덧붙이는 방식이 아니라 구조화한 다음 네 테이블을 RAG의 근거 저장소로 사용한다. 별도 임베딩이나 SQLite 재빌드는 필요 없다.

- `travel_placeknowledge`: 정확한 장소 ID와 지점 기본정보
- `travel_placeknowledgesource`: 출처 URL·버전·저장 허용 속성·보관기한
- `travel_placeknowledgeobservation`: 키워드·긍정/부정·근거 종류·검증/만료 시각
- `travel_placeenrichmentattempt`: 조사 결과·호출 수·재검색 대기

로컬 회원/대화 DB는 그대로 두고 위 테이블만 RDS에 연결하려면 서버 환경에 `RAG_DB_HOST`, `RAG_DB_PORT`, `RAG_DB_NAME`, `RAG_DB_USER`, `RAG_DB_PASSWORD`를 설정한다. `RAG_DB_SSLMODE` 기본값은 `require`다. 접속정보는 Git에 넣지 않는다. TLS 인증서 검증을 요구하는 환경에서는 CA와 sslmode 정책을 운영자가 설정한다.

별도 연결은 `place_knowledge` alias와 모델 전용 DB router를 쓴다. 트랜잭션/행 잠금도 같은 alias에 적용한다. 이미 기본 DB가 팀 RDS면 별도 `RAG_DB_*` 설정은 필요 없다.

```sh
# 배포 기본 DB를 사용한다면
python manage.py migrate
# 별도 RAG 연결을 설정한 경우, 먼저 계획 확인
python manage.py migrate --database=place_knowledge --plan
python manage.py migrate --database=place_knowledge
```

0014·0015가 근거 테이블을 만든다. 이번 연결 때문에 새 스키마 마이그레이션을 추가하지 않았다. 일반 앱의 기존 코스 이동수단 마이그레이션 0016은 별도다. 다른 서버의 적용 이력은 확인하지 않았으므로 위 명령 실행 전 실제 환경을 확인해야 한다.

## 출처 저장 정책

`PLACE_EVIDENCE_STORAGE_POLICIES`는 JSON 배열이다. URL 접두어별 허용 속성, 검토 근거, 최대 보관일을 설정한다. 기본 `[]`는 출처를 자동 승인하지 않는다. 이때 현재 질문에 검증 결과를 쓸 수 있어도 관찰 키워드 자동 영구 저장은 하지 않는다. 조사 이력과 동일 지점 참조는 기록될 수 있다.

```json
[{"url_prefix":"https://example.com/approved-menu/","attributes":["menu","cuisine"],"reference":"출처 이용·보관 조건을 검토한 내부 문서/버전","days":7}]
```

위 값은 설정 형식 예시이며 실제 서비스에 사용 가능한 출처 승인이 아니다. 운영에서 실제 허용 출처로 교체한다. 기존 source가 blocked로 바뀌거나 만료되면 재조회에서 즉시 제외한다. 같은 출처 버전의 재요청으로 보관기간을 연장하지 않는다.

## 검증 범위

로컬 PostgreSQL 임시 테스트 DB에서 가상 근거로 저장→재조회, 추가 웹 호출 생략, 만료·철회, 다른 지점·스니펫 거부, 단일 후기/충돌 근거 미확정, 캐시 후보 우대 방지, 오류 재조회 제한을 검증한다. 실제 공개 가게의 대규모 자료나 검토되지 않은 출처를 테스트용 사실로 적재하지 않는다.

```sh
python manage.py test llm.tests.test_course_evidence --noinput
python manage.py test travel.test_place_keyword_memory travel.test_place_knowledge --settings=travel.knowledge_test_settings --noinput
```

현재 사용자가 팀 RDS 설정이 아직 없다고 알려 로컬 검증만 수행했다. 개발·배포 서버 주소만으로 DB 접속을 대신할 수 없다.

실제 메뉴·후기 조건의 실패 사례, 수정 사항, 응답 시간·비용은 [2026-10-05 웹 근거 검증](course-web-evidence-verification-2026-10-05.md)을 참고한다.
