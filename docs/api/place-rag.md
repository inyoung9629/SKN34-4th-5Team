# 수집 장소와 분석 기록의 로컬 RAG

> **2026-10-05 현재 활성 코스 경로:** [공용 장소 근거 연결](shared-place-evidence.md)을 참고한다. 아래 10월 1~2일 실험·이전 결정론적 체인 설명은 과거 기록이다. 현재는 `course.agent/editing/evidence_memory`에서 현재 후보의 조건별 근거를 읽고 제한적으로 웹 검증·허용된 출처 키워드 저장을 수행한다. 저장된 장소를 추천에서 우대하지 않는다. `search_place_knowledge` 읽기 전용 도구도 복원했다. 숙박은 기존 NOL 검증기를 사용한다.

> 2026-10-04: 소상공인 수집 자료를 제거했습니다. 아래 건수와 분석 결과는 10월 1일의 과거 기록입니다. 현재 공공 후보는 PARK/TOUR 527건의 보정 반경 내 자료이며, 구장 시설은 유지합니다. 기존 인덱스는 그대로 사용하지 말고 새 수집본에서 `python backend/manage.py build_place_rag --without-analysis`로 다시 생성해야 합니다. 삭제된 장소에 연결된 과거 분석 파일은 재사용하지 않습니다. 현재 팀 챗봇의 LLM 도구 연결은 10월 3일에 되돌려진 상태입니다.

수집한 장소를 웹검색 없이 먼저 찾기 위한 백엔드 검색 인덱스다. 2026년 10월 1일 실제 파일로 생성했으며 장소 이름·주소·분류·좌표와 구장 소속을 조회할 수 있다. 기존 분석 결과는 별도 조사 기록으로 저장한다. 분석에서 통과했다는 이유만으로 현재 판매 메뉴나 분위기를 확정하지 않는다.

외부 임베딩 API 대신 SQLite FTS5와 BM25 순위를 사용한다. 한글은 단어와 인접한 두 글자 단위로 색인한다. **로컬 키워드 검색형 RAG이며 의미 기반 벡터 검색은 아니다.** 인덱스 생성·조회에 검색 API나 모델 호출은 없다. 챗봇의 질문 해석·답변 생성 비용까지 없어진다는 뜻은 아니다.

## 저장 범위

| 구분 | 저장 건수 | 답변에서 사용할 수 있는 범위 |
| --- | ---: | --- |
| 공공 데이터 기반 장소 | 34,779 | 수집 당시 이름·주소·좌표·업종 분류 |
| 구장 먹거리와 편의시설 | 485 | 구장 소속·층·구역과 기존 근사 핀 정보 |
| 감사된 분석 사례 | 25 | 내부 조사 기록 조회만 가능. 메뉴 지지 4건, 미확인 21건 |

장소와 시설은 9개 구장의 자료다. 공공 수집본은 기존 체크섬 검증을 거치고 보정된 구장 중심 반경으로 재필터링한다. 그래서 원본 수집 행 수와 검색 대상 건수가 다르다. 같은 이름의 다른 지점을 합치지 않으며 출처 간 실제 동일 장소의 중복은 남을 수 있다.

구장 소속은 `external_candidate` 외부 후보, `internal` 내부, `stadium_exterior` 외부 부속, `stadium_unknown` 소속은 있으나 내외부 미확인으로 구분한다. 기본 검색은 외부 후보만 반환한다. 외부 후보라는 표시도 실제 외부 영업장임을 확정하는 인증은 아니다.

최근 Serper 검증 실험 중 감사된 25건만 분석 기록으로 가져왔다. 부분 메뉴 목록에 카페라떼가 없다는 이유로 미판매 처리했던 사례는 감사 결과대로 `unknown`으로 보정한다. 이전 300건 비교 실험과 검색 결과만 모은 실험은 검증 수준이 달라 합치지 않았다. 개별 요청 메뉴가 검색 문서에 등장해도 장소의 확정 메뉴 태그로 복사하지 않는다.

리뷰 원문·사진·HTML·작성자 정보·채팅·계정·API 키·전체 모델 응답은 인덱싱하지 않는다. 분석 기록에는 요청 항목, 우리 판정, 감사 상태, 날짜, 조사 중 읽었던 페이지 URL과 원본 기록 식별자만 남긴다. 이 URL들이 모두 조건을 지지한 근거라는 뜻은 아니다. 숙박의 Google ID만 있는 자료는 이름·좌표를 추정하지 않고 제외한다.

## 챗봇 연결과 남은 작업

`search_place_knowledge` 도구가 장소 기본정보를 읽는다. v1 공유 도구 목록과 v2 주변 장소 체인에 연결했다. v2 주변 장소 체인은 매 턴 먼저 수행하던 유료 쿼리 임베딩 검색을 제거하고 로컬 도구를 우선 사용하도록 안내한다. 다른 도메인의 기존 pgvector 검색까지 변경한 것은 아니다.

현재 분석 기록은 재사용 검토 전 상태이므로 모델 도구에 노출하지 않는다. 개발자 조회에서 `--include-research`를 지정해야 볼 수 있다. 날짜가 지난 `pass`를 최신 사실로 승격하지 않으며, `unknown`을 메뉴 미판매나 장소 부재로 해석하지 않는다.

2026년 10월 2일 한때 V2 결정론적 코스 생성에 RAG 외부 후보 조회를 연결했지만, 이후 사용자 요청으로 **활성 코스 경로는 카카오 실시간 분할 조회로 교체**했다. [현재 후보 확보 규칙](course-policy-v1.md#카카오-반경-후보-확보-2026-10-02)을 참고한다. RAG·수집본·기존 `course_candidates.py`는 삭제하지 않았으며 다른 조회/검증에 남아 있다. 카카오 실패 시 자동 대체 자료로 사용하지 않는다.

보존한 로컬 전용 로더는 해당 구장 전체 후보의 원본 일치/체크섬/소속 제외를 검증하며, RAG가 손상·누락·오래된 스냅샷이면 같은 로컬 수집본만 사용한다. 이 로컬 폴백은 **현재 코스의 실행 경로가 아니다**. 활성 `itinerary_result.candidate_retrieval`에는 `kakao_adaptive`와 호출/분할/후보/범위/완료 상태를 기록한다. 반경·경기·입장·체류·실제 이동시간 검증은 기존 계획기가 계속 담당한다.

**장소 후보 연결과 메뉴·후기 근거 재사용은 다르다.** 현재 분석 기록을 승인된 판매 메뉴나 분위기 사실로 바꾸지 않는다. 별도 `PlaceKnowledge` 관찰을 결정론적 코스 검증기에 연결하거나 URL에서 자동 적재하지 않았다. 저장된 카카오 숙박 ID·URL 465개도 좌표·이름이 없는 참조 목록이므로 코스 후보에 넣지 않는다. 프론트와 개발·운영 서버 배포는 변경하지 않았다.

### 2026-10-02: 검증 키워드의 증분 기억

로컬 Docker DB에 지식 테이블 0014·0015를 적용하고 `place_keyword_memory.py`에 검증 결과 저장기를 추가했다. API 응답이나 페이지 원문이 아니라 정규화한 키워드·조건·관찰 상태·시각과 출처 참조를 기존 장소 ID에 연결한다. 아직 실제 카카오 키워드를 넣거나 URL 자동 읽기·추출 작업자를 연결하지 않았다.

`search_place_knowledge`에 `keyword_term="돈까스"`처럼 명칭 하나를 지정하면 장소 목록과 별개인 `keyword_memory`를 반환한다. 승인된 메뉴/음식분류/후기 키워드를 DB에서 즉시 읽으므로 정적 SQLite 인덱스 재빌드나 임베딩 호출이 필요 없다. 기본 장소 조회는 변하지 않는다. 동일 지점·만료·철회·출처 조건·후기 적용 조건을 검사하며 단일 후기나 플랫폼 AI 요약을 매장 전체 사실로 승격하지 않는다. 결과 잘림도 명시한다.

저장 테이블과 읽기 연결은 구현했지만 **브라우저 URL 읽기 → 검증된 다중 키워드 추출 → 자동 저장** 흐름은 아직 미연결이다. 출처 저장 조건을 자동 승인하지 않으며 기존 코스의 필수 근거 부족 처리는 그대로다. 자세한 저장 계약은 [장소 지식 저장 규약](place-knowledge.md)을 따른다.

## 코스 조건과 웹검색 비용 정책

`COURSE_WEB_VERIFICATION_ENABLED` 기본값은 `false`다. 서버 설정에서 명시적으로 `true`로 켠 경우에만 기존 OpenAI 음식·후기 웹 검증기를 사용한다. 사용자 채팅이나 화면에서 이 값을 바꿀 수 없다. Serper 검색·직접 페이지 읽기·승인된 사실 재사용을 자동 연결한 것은 아니다. 이 스위치는 V2 코스의 음식·후기 웹 검증에만 적용되며, 질문 해석 LLM·경기 일정 최신화·길찾기·다른 챗봇 도구까지 끄거나 전체 서비스를 무료로 만들지는 않는다.

| 요청과 자료 상태 | 기본 동작 |
| --- | --- |
| 식당·카페 등 방문 종류만 요청 | 카카오 분할 조회의 외부 후보에서 기존 반경·시간 규칙으로 코스 계산 |
| 메뉴·음식 종류 또는 조용함·청결도 필수 | 재사용 가능한 근거가 없으므로 `knowledge_insufficient`. 조건과 방문 순서를 보존하고, 웹검색·길찾기·반경 확대 없이 안내 |
| 조용함·청결도가 선택적 선호 | 웹검색 없이 미확인 선호로 표시. 다른 필수 조건과 시간이 맞으면 코스 계산 |
| 일반 요청의 후보가 없음 | 기존 한도 안에서 단계적 반경 확대 후 결과 안내. 자동 웹검색 없음 |
| 숙박 요청 | 기존 `unsupported_lodging` 유지. URL만으로 숙소 위치를 만들거나 방문을 삭제하지 않음 |

다음 단계는 승인된 저장 근거의 유효기간·지점·조건 일치를 확인해 재사용하고, 부족한 후보만 제한된 비용으로 추가 검증하는 것이다. 현재는 이 재사용·검색 자동 전환·새 검색 결과 자동 저장이 미연결이다. 인덱스는 빌드 시점 스냅샷이므로 원본 변경 후 재빌드해야 한다.

## 생성과 조회

프로젝트 루트의 PowerShell에서 실행한다. 아래 설정은 `.env`나 실제 서비스 DB를 사용하지 않는 로컬 명령용 설정이다.

```powershell
$env:PYTHONIOENCODING='utf-8'
.\.venv\Scripts\python.exe backend/manage.py build_place_rag --settings=travel.knowledge_test_settings
.\.venv\Scripts\python.exe backend/manage.py query_place_rag --stats --settings=travel.knowledge_test_settings
.\.venv\Scripts\python.exe backend/manage.py query_place_rag 동경 --stadium JAMSIL --include-research --settings=travel.knowledge_test_settings
.\.venv\Scripts\python.exe backend/manage.py query_place_rag --stadium JAMSIL --scope internal --kind food --limit 5 --settings=travel.knowledge_test_settings
```

기본 저장 위치는 `backend/artifacts/place-rag/index.sqlite3`다. 이미 Git 제외된 경로이며 바이너리 인덱스를 커밋하지 않는다. 원본은 수정하지 않으며 실패한 빌드는 기존 인덱스를 유지한다. 인덱스가 없거나 손상되면 빈 성공 응답 대신 `index_unavailable`을 반환하고 자동 유료 검색을 실행하지 않는다.

`--analysis-dir`로 감사된 분석 폴더를 지정할 수 있다. 해당 형식을 검증하므로 아무 JSON 폴더나 자동 수집하지 않는다. 분석 폴더가 없는 환경은 명시적으로 `--without-analysis`를 사용한다. `--output`은 빌드 위치, 조회의 `--index`는 읽을 위치를 지정한다. 서비스 실행 시에는 `PLACE_RAG_PATH` 환경변수로 파일 위치를 바꿀 수 있다.

현재 Compose는 `backend` 폴더를 `/app`에 마운트하므로 로컬 생성 인덱스는 `/app/artifacts/place-rag/index.sqlite3`로 보인다. 개발·운영 서버에는 자동 전송하지 않는다. 별도 환경에서는 필요한 원본과 명령을 준비해 생성해야 한다.

## 검증 결과

로컬 인덱스 생성 후 장소 지식·RAG·도구 등록·음식·후기·코스·입장시간 관련 테스트 348개가 통과했다. 네트워크 연결을 금지한 생성·조회 테스트도 포함한다. 실제 파일 조회에서는 잠실의 동명이점 분리, 대전 카페 필터, 잠실 내부 매장 분리, 분석의 `fail`을 `unknown`으로 감사 보정한 결과를 확인했다. 유료 모델을 호출하는 실제 대화 종단 테스트와 개발·운영 서버 배포는 수행하지 않았다.

2026년 10월 2일 코스 연결 후 관련 회귀 테스트 355개가 통과했다. 실제 9개 구장 인덱스는 모두 `ready`였고, 실행 중인 로컬 백엔드에서도 잠실 외부 후보 4,587개·소속 후보 제외 17개와 자동 웹검색 비활성화를 확인했다. 실제 잠실 후보를 사용한 식당→카페→구장 계획은 가상의 경기 시각과 고정 이동시간으로 검증했다. 이는 실제 길찾기 API나 유료 모델을 호출한 종단 검증이 아니며 실제 경기·추천 시간표를 뜻하지 않는다.
