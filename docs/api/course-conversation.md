# 대화로 코스 수정하기

2026-10-04 적용. 기존 장소 교체·순서 변경에 다음 동작을 추가했다.

| 요청 예시 | 처리 |
| --- | --- |
| 카페 빼줘 | 해당 방문지만 삭제 |
| 구장 들어가기 전에 편의점 추가해줘 | 구장 앞에 실제 검색 후보 삽입 |

| 방금 변경 취소해줘 | 직전 수정 전 장소·체류시간·이동수단·조건 복원 |

수정 후 실제 경로 또는 실패 시 표시된 추정 이동시간과 경기 기준 시간표를 다시 계산한다. 사용자 지정 체류시간은 `stayOverride`로 지도 초안과 다음 요청까지 유지하며, 체류시간은 1~720분이다. 경기 관람시간과 숙박 체류시간은 이 명령의 대상이 아니다. 편의점 기본 체류시간은 10분이다.

새 코스의 방문 구성은 기존 대화 해석 호출에서 `requested_visits`로 함께 읽는다. ‘스테이크 썰고’, ‘파스타 한 접시’, ‘초밥으로 배 채우고’처럼 식사를 뜻하는 문맥도 FOOD로 처리한다. 사용자 요청의 연속 원문이 확인되는 방문만 반영하며, 카페 디저트·이미 먹은 식사·명시적 식사 제외는 별도 식사를 추가하지 않는다. 방문 구성이 지정되지 않았거나 기존 코스를 수정할 때는 기존 구성 처리 방식을 유지한다. 별도 해석 모델 호출을 추가하지 않았다.

식사 원문은 이번 요청의 FOOD 조건에도 전달해 활동만 인식하고 메뉴를 잃어버리지 않게 한다. 이 표현을 지속 취향으로 저장하지 않는다. 단순 ‘밥 먹고’는 방문 의도, ‘스테이크 썰고’는 스테이크 메뉴 조건으로 후속 근거 확인기가 구분한다. 구장 방문은 자동 경기 단계에만 넣어 관광 코스를 중복 추가하지 않는다.

숙박은 상세 정보/실제 후기 확인 후 후보를 추가 조사하고, 충족 후보가 없을 때 평점과 평가 수를 함께 고려한 미확인 대안을 사용할 수 있다. 충족 숙소는 근거 설명 없이 작은 야놀자 링크만 표시한다. [숙박 확인과 대안 정책](shared-place-evidence.md)을 따른다.

새 장소는 구장 반경 2.5km 안에서 찾는다. 최대 12곳이며 경기장은 삭제하지 않는다. 고정은 장소의 유지이고 순서는 변경할 수 있다. 고정 장소의 교체·삭제는 먼저 고정을 해제해야 한다. 지도에서 수동 변경한 뒤에는 이전 대화의 취소로 덮어쓰지 않는다. 되돌리기는 직전 한 번이다.

출발지만 지정했거나 방문지를 모두 지운 지도도 `currentCourse.places=[]`와 유효한 `writerState`로 전송한다. 요청의 빈 작성 상태를 이전 대화의 방문 목록으로 복원하지 않는다. 이 허용은 요청 문맥에만 적용하며 빈 추천 카드는 만들지 않는다. 새 지도 출발지는 과거 대화보다 우선하고, 현재 화면의 명시적인 출발지 삭제는 그대로 유지한다.

동선 검색에서 같은 요청·같은 조건으로 이미 확인한 후보는 재판정으로 버리지 않는다. 조건 변경과 제외는 계속 반영한다. 구장 쪽으로 전진하는 후보가 없을 때는 반경 2.5km 안에서 조건을 만족하는 우회 후보를 확인하고, 채택하면 돌아가는 구간이 포함됐다고 알린다.

## 대화 기억과 공개 응답

2026-10-05 변경: **같은 대화창에서도 새 코스 생성은 이전 대화를 사용하지 않는다. 기존 코스 수정에서만 기억을 사용한다.**

- ‘초밥 먹고 산책하다 구장 갈 코스 짜줘’, ‘처음부터 새로 짜줘’: 이번 질문과 현재 지도에서 선택한 구장·출발지·경로만 사용한다. 이전 활동·날짜·이동수단·취향·제외·고정·수정 취소 상태를 이어받지 않는다.
- ‘카페만 바꿔서 다시 짜줘’, ‘순서 바꿔줘’, ‘20분만 머물게’: 현재 코스와 그 코스를 시작한 이후의 대화만 참고한다.
- 과거 대화는 화면과 DB에 그대로 남긴다. 모델 입력만 새 생성 질문부터 잘라 사용하며, 새로고침 후 수정해도 더 오래된 코스의 기억이 되살아나지 않는다.
- 기존 JEV 호출에 새 생성/수정 분류를 함께 넣는다. 새 생성은 메인 모델 호출 전부터 대화·코스 기억을 비운다. 코스 해석기에서 뒤늦게 새 생성으로 판정되면 깨끗한 입력으로 재해석한 뒤 생성한다.

`plan_course`의 비공개 ToolMessage artifact에 `course_memory`를 저장한다. 새 생성의 완료 답변 또는 도구 결과에 비공개 `course_history_reset`을 기록한다. 완료된 턴에서만 복원하고 실패·중단·답변 삭제·질문 수정으로 제거된 턴은 제외한다. 별도 전역 변수나 계정 전체 취향 저장소는 사용하지 않는다. 새 대화에는 조건을 전달하지 않는다. 장소의 공용 RAG 근거 캐시는 대화 기억과 별개다.

- 조건: 종류별 명시 조건 최대 20개
- 제외: 장소 ID 또는 이름·좌표로 비교, 최근 100곳
- 고정: 장소 식별 정보
- 취소: 수정 전 스냅샷과 적용 후 비교 정보

GET 대화 내역과 SSE `done`에 선택 필드 `coursePreferences`를 전달한다. 공개 값은 `conditions`, `lockedPlaces`, `rejectedPlaces` 문자열 배열뿐이다. 내부 취소 스냅샷은 공개하지 않는다. 코스를 바꾸지 못한 경우에도 인식한 조건과 제외 목록을 보관할 수 있다.

작은 채팅과 확대 채팅 모두 ‘이 대화의 코스 조건’에서 목록을 확인한다. 조건을 누르면 해제 요청이 입력창에 들어가며, 사용자가 보내면 처리한다. 기존 대화는 이후 요청부터 조건을 저장한다.

기존 코스를 수정하는 동안 조건은 추가·해제 차이만 반영하고, 새 코스 생성에서는 초기화한다. **단순 교체·추가·삭제·한 번의 음식 요청은 지속 취향으로 저장하지 않는다.** ‘나는 한식을 싫어해. 제외해줘’, ‘앞으로 스타벅스만’, ‘기억해줘’처럼 명시적으로 선언한 조건만 해당 코스의 이후 수정에 유지한다. 반복 요청 횟수로도 취향을 추론하지 않는다. 방문 구성·이동수단 등 현재 코스 설정은 별도로 유지한다.

`request_preferences`는 이번 요청에서만 적용하고 `preferences`만 대화에 보존한다. ‘이번에는 다른 브랜드’가 기존 취향과 충돌하면 `request_overrides`로 이번 턴에만 예외를 적용하며 기존 취향은 지우지 않는다. 단순 교체된 가게를 `rejected`에 자동 등록하지 않는다. 출발지 주변·선택 경로·전체 생성·부분 교체의 후보에 동일한 조건 검증을 적용한다.

## 2026-10-05 추가 편집

- ‘카페 → 구장만 대중교통’: 인접 구간의 이동수단만 변경하고 나머지 구간의 설정은 보존한다. 별도 출발지는 `origin`으로 참조한다.
- ‘카페를 스타벅스로 바꾸고 식당 앞으로, 체류 20분’: 최대 6개 수정을 순서대로 검증하고 최종 경로·시간표를 한 번 재계산한다. 하나라도 실패하면 전체 변경과 조건 변경을 취소한다. 되돌리기도 전체 묶음 단위다.
- ‘출발지만 삼성역으로’: 검색에서 동일 지점을 확인한 출발지만 변경하고 기존 장소·순서·제목은 보존한다. 모호하면 원본을 유지한다. 출발지 삭제도 지원한다.
- 새 후보는 필수·선택·제외 조건을 구분한다. 확인하지 못한 필수 조건을 충족했다고 표시하지 않으며, 선택 조건 미확인만으로 모든 후보를 버리지 않는다.
- 생성 후보를 업종별 한 곳으로 미리 축소하지 않는다. 조건 통과 후보 전체에서 동선을 계산한다. 저장된 근거 유무는 추천 가산점이 아니다.

## 코스 작성 상태 복원 (2026-10-05)

대화의 코스를 작성 화면에서 다시 열면 제목, 이름 있는 출발지, 방문 순서, 구간별 이동수단과 완성/수정 상태를 함께 복원한다. 이미 작성 중인 내용이 있는 화면으로 코스를 열면 불러오기 확인을 거친다. 제목을 직접 바꾼 뒤 후속 수정 답변을 받아도 그 제목을 유지한다.

- 코스와 `currentCourse`의 선택 필드 `writerState`는 `title`(빈 문자열 허용, 최대 80자), `origin`(이름을 포함할 수 있는 좌표 또는 `null`), `completed`를 담는다. `origin: null`은 출발지를 명시적으로 없앤 상태다. 필드 자체가 없는 기존 내역과 구별해, 이전 출발지가 다시 살아나지 않게 한다.
- 질문에 전달한 상태는 완료 답변의 공개 코스와 서버 대화 체크포인트에 보관한다. 예전 수정 답변에 제목이 없으면 같은 구장의 앞선 코스 제목을 이어받는다. 과거에 저장하지 않은 사용자 지정 제목은 소급 복구할 수 없다.
- 로그인한 사용자가 질문을 보내기 전 수동으로 바꾼 내용은 이 브라우저에 계정·대화·답변별로 보관한다. 다른 기기까지 동기화되는 데이터는 아니다. 서버에서 확인한 대화와 답변에 연결된 초안만 다시 적용한다.
- 새로고침은 일반 작성 초안을 보존한다. 앱 내에서 작성 화면을 비우고 나간 뒤에도 연결된 대화에서 편집본을 다시 불러올 수 있다. 저장 실패·다른 탭과의 충돌은 화면에 알리고 최신 초안을 덮어쓰지 않는다. 비로그인 상태는 기존과 같이 브라우저 영구 초안에 저장하지 않는다.
- 저장된 GPS 좌표는 선택한 출발지로 복원한다. 대화를 여는 것만으로 현재 위치 권한을 다시 요청하지 않는다.

복원 회귀 테스트는 `llm.tests.test_course_writer_state`, `frontend/tests/route-draft.test.mjs`, `chat-direct.test.mjs`, `route-writer-access.test.mjs`에 포함한다. 제목·출발지 삭제·완성 상태 왕복, 대화 및 계정 격리, 기존 작성 내용 보호와 새로고침을 검증한다.

백엔드 관련 54개, 프론트엔드 관련 99개 테스트와 TypeScript·변경 파일 ESLint를 통과했다. 로그인한 실제 화면에서 기존 답변 불러오기 → 사용자 지정 제목 입력 → 새로고침 → 작성 화면 비우기 → 전체 대화의 마지막 코스를 지도에서 다시 열기를 확인했다. 제목·출발지·4개 방문지·완성 상태·본문이 유지됐으며 새 모델 요청 없이 검증했다. 화면을 정리할 때 완성 상태를 거짓으로 되돌리던 지도 효과 정리 동작도 제거했다.

## 현재 코스 상태 통합 (2026-10-05)

작성 화면은 `CourseState` 하나에서 구장·제목·본문·출발지·방문 순서·전체/구간 이동수단·완성 여부·작성 방식을 관리한다. 지도와 챗봇이 각자 코스 사본을 수정하지 않고 같은 `reduceCourse` 변경 처리에 요청한다. 과거 초안의 첫 지점에 들어 있던 출발지는 경계에서 별도 `start`로 변환하고 이후 방문지 목록과 구분한다. 저장 형식은 기존 초안과 호환한다.

- 챗봇은 질문을 실제 전송하는 순간의 현재 코스를 읽는다. 바로 직전 수동 수정이나 앞선 예약 답변의 결과도 반영한다. 수정 요청만 이전 대화를 참고하고 새 생성은 이전 대화 조건을 쓰지 않는 서버 정책을 유지한다.
- 추천을 지도에 새로 담는 작업과 대화의 저장된 편집본을 다시 여는 작업을 구분한다. 추천을 담았는데 과거의 빈 편집본이 덮어쓰는 현상을 방지한다.
- 구장 변경·초기화·추천 적용·복원을 한 번에 처리한다. 출발지만 남은 상태도 구장 변경 확인 대상이며, 방문지를 우클릭으로 비운 뒤 마지막 출발점까지 제거할 수 있다.
- 변경 버전을 검사해 늦게 도착한 챗봇 답변·GPS 결과·과거 추천의 되돌리기가 이후 편집을 덮지 않게 한다. 거절된 되돌리기는 현재 내용을 유지했다고 안내한다.
- 도로 경로는 현재 좌표와 이동수단에 해당하는 계산 결과만 연결한다. 지도 확대/이동·경로 계산 완료·작성 탭 이동만으로 대기 중인 답변을 무효화하지 않는다.
- 대화 기록, 답변별 추천 카드, 저장본은 이력/복원 자료다. 현재 작성 코스를 대신하는 별도 편집 상태로 사용하지 않는다. 공개 저장과 서버의 대화 체크포인트 계약은 유지한다.

프론트 관련 174개 테스트, 백엔드 편집·대화·기억 범위·작성 상태·구장 내부 제외 계약 67개, TypeScript 및 변경 파일 ESLint를 통과했다. 실제 Chrome에서 기존 추천 담기 → 카페를 첫 순서로 이동 → ‘카페만 구장 밖으로 교체’ → 커피너티/기존 짬뽕집/구장 순서와 출발지 유지 → 지도 핀·경로 갱신을 확인했다. 출발→카페만 자동차(9분), 나머지 도보(14분/20분)로 바꾼 뒤 도보로 복구했다. 우클릭 네 번으로 방문지 세 곳과 출발지를 제거했으며, 과거 되돌리기를 실행해도 지점이 되살아나지 않았다. 실제 GPS 권한/위치 획득은 재실행하지 않고 제어 가능한 GPS 콜백 테스트로 늦은 성공·실패를 검증했다.

이 통합은 현재 코스의 일관성을 다룬다. 모델의 조건 해석과 장소 추천 근거의 정확도를 전부 보장하는 변경은 아니다. 실제 카페 교체 답변에는 내부 분류 필드가 추천 이유에 노출되는 별도 문구 문제가 관찰되어 후속 개선 대상으로 남겼다.

## 후속 질문 예약

답변 생성 중 입력창에서 다음 질문을 최대 2개까지 예약한다. 작은 채팅과 확대 채팅 모두 입력창 바로 위에 순번·내용·수정·취소를 표시한다. 현재 답변은 끝까지 받고, 사용량 정산이 끝나면 FIFO 순서로 다음 질문을 전송한다. 직접 API를 동시에 호출하면 기존 `usage_busy` 보호는 유지된다. 클라이언트가 이 응답을 받으면 전송되지 않은 질문을 예약으로 전환하고 사용량 상태를 확인한 뒤 다시 보낸다.

- 예약 수정은 입력창에서 저장하며 순서를 유지한다. 수정 중에는 다음 예약의 자동 전송을 멈춘다.
- 예약 취소는 진행 중인 답변에 영향을 주지 않는다. 서버가 요청을 받기 시작한 항목은 ‘전송 중’으로 표시한다.
- 다음 코스 수정은 앞선 답변으로 갱신된 지도 또는 서버의 최신 코스를 사용한다.
- 답변 실패·사용자 중단·사용량 소진·연결 확인 실패 시 남은 예약을 보존하고 일시 정지한다. ‘예약 계속’으로 재개한다. 결과를 알 수 없는 POST를 자동으로 재전송하지 않는다.
- 예약은 현재 브라우저 탭의 대화별 상태다. 앱 내 화면 이동·팝업 확대/축소에는 유지되며, 다른 대화로 이동하면 해당 대화로 돌아왔을 때 이어간다. 로그아웃·계정 전환 시 비운다. 서버에 예약을 저장하거나 창을 닫은 뒤 실행하는 기능은 포함하지 않는다. 새로고침·창 닫기 시 미전송 예약이 있으면 브라우저 이탈 확인을 띄운다.

예약 관련 회귀 검증은 `frontend/tests/chat-provider-race.test.mjs`에 포함한다. 최대 개수, 순차 실행, 편집·취소, 사용량 해제 대기, 실패 후 재개, 대화·계정 격리, 취소와 사용량 조회의 경쟁 상태, 최신 코스 전달을 확인한다. 실제 로그인 화면에서도 예약 2개 자동 실행, 수정 저장, 취소, 작은 채팅 표시를 확인했다.

연속 대화 검증 중 발견한 방문 중복도 수정했다. 저장된 방문 구성과 새 질문을 이어 붙여 방문 횟수를 늘리지 않고, 현재 요청의 방문 구성을 우선한다. 명시한 카페 두 곳처럼 실제 반복 요청은 유지한다.

진행 상황은 사용자가 알려 준 내용을 반영한다. 실시간 경기 종료나 날씨를 자동 감지하지 않는다. 지연량이나 새 시각이 없으면 확인 질문을 하고 코스는 유지한다. 방문 완료 시 실제 종료 시각이 없으면 기존 시간표 기준임을 안내한다. 앞선 장소가 미완료인데 뒤의 장소만 완료했다고 하면 앞선 방문 여부를 확인해 임의로 완료 처리하지 않는다.

시간 변경으로 경기 전 방문이 어려워져도 장소를 빼지 않고 몇 번째부터 어려운지 표시한다. 실내 후보의 조건을 확인할 수 없으면 원본 전체를 유지하며 일부만 교체하지 않는다. 완료 기록은 코스 카드의 `방문 완료` 표시, 지도 초안, 후속 요청, 대화 복원에 유지된다. 직전 수정 취소로 완료 표시나 지연도 되돌릴 수 있다.

공개 코스의 장소에 `completed: true`, `until`(계획/명시 종료 시각)을 추가한다. 선택 필드 `progress`에는 경기 날짜 자정 기준 `startMinute`(첫 미완료 장소의 도착, 또는 마지막 완료 장소에서 다음 출발), `gameEndMinute`을 전달한다. 값은 0~2879의 정수이고, 지도에서는 `RouteStop.courseProgress`로 보존한다. 완료 이력은 앞에서부터 연속된 방문 구간만 허용한다.

`llm.tests.test_course_progress`에서 지연 누적, 경기 시각 고정, 완료 구간 보호, 자정 이후 시각, 실내 교체 실패 원자성, API·지도 문맥·취소 복원을 검증한다. 프론트엔드 왕복 전달 및 초안 복원 검증은 `chat-direct.test.mjs`, `route-draft.test.mjs`에 포함한다.

실제 로그인 화면에서 출발 30분 지연 → 식당 완료 → 새로고침 후 완료 복원 → 아시아공원을 볼링장으로 교체 → 경기 종료 30분 지연(볼링장 17:31→18:01)을 확인했다. 해당 코스를 지도에서 연 뒤 카페 체류를 20분으로 줄여도 식당 완료와 경기 후 18:01은 유지되고 지도에 자동 반영됐다. 관련 백엔드 90개 테스트, 프론트엔드 회귀 테스트, TypeScript·변경 파일 ESLint를 통과했다.
