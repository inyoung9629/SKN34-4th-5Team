# Public browser research

Optional Docker MCP request tracing uses pinned official `langsmith` SDK `trace` contexts. Set `JEV_LANGSMITH_TRACING=true` and an existing runtime `LANGSMITH_API_KEY`; `LANGSMITH_PROJECT` (default `kbo-rag`) and `LANGSMITH_ENDPOINT` select delivery. Disabled/missing-key operation needs no tracing service; SDK setup/delivery errors cannot fail browser calls. Backend tracing is unchanged. Each completed `jev_browse`/`jev_read_body` call records only input source hostname and output status, source hostname, body UTF-8 byte count (zero for browse/no body), and elapsed milliseconds, including busy, blocked, timeout, overflow and cancellation. The context is emitted after cleanup (the output `duration_ms` measures execution, while SDK timestamps measure summary emission), never given raw goals, bodies, paths, queries, fragments, credentials, headers or exception tracebacks; no clicking/model-step traces are added. Offline regression: `python docker/jev-browser/test_tracing.py`. Live trace delivery must be verified separately using SDK reads, not inferred from browser success.

The main V2 agent handles final answers, except for unambiguous new-course-only requests: those return the existing validated course text directly after the course tool completes. Mixed questions and course edits retain the existing answer model. `ask_web_research` is the sole externally searching/browsing specialist, dynamically exposed by `web_research` (JEV or the manual “웹 조사” group); `ask_travel_research` retains DB/place/document tools only. Main has no native `web_search`. Course creation/edit ownership and evidence validators remain unchanged. Non-lodging bounded structured search and public-reader calls enter the web service directly. Lodging uses the deterministic Chrome collector described below, without invoking a research specialist.

Set `WEB_RESEARCH_ENABLED=true` in runtime `.env`, `OPENROUTER_API_KEY`, and `RESEARCH_API_KEY` (or `OPENAI_API_KEY`) for the general research specialist. `RESEARCH_MODEL=gpt-6-luna` and `RESEARCH_BASE_URL=https://api.openai.com/v1` configure both specialist and upstream text/answer helper. `JEV_MCP_URL=http://jev-browser:8080/mcp` is internal, with no published port. The browser service is part of the default Compose stack and is also needed for lodging when general web research is disabled. Configure `JEV_MCP_TOKEN` before starting; an empty token fails startup. Build/start it with `docker compose up -d --build jev-browser`.

## Server Chrome lodging collection

Compose sets `LODGING_CHROME_TRANSPORT=mcp`. `travel.chrome_lodging` discovers only `chrome_lodging`, which runs `chrome-lodging.mjs` with standard Node.js/CDP APIs. It opens NOL's normal search button flow, follows a uniquely matching observed hotel link, and reads the visible detail DOM in a fresh Chrome profile. Neither JEV nor a search/browser-control model is called, and failure never falls back to paid search. The existing condition models still extract requirements and interpret the observed text; model token costs remain.

Google Chrome runs on the **server**, with Xvfb, a non-root sandbox and the same proxy/firewall restrictions. The image currently installs the official amd64 Linux Chrome package. End users need no Chrome installation; mobile browsers call the same backend. Native development can use `LODGING_CHROME_TRANSPORT=local`, installed Chrome and Node.js 24; optional `LODGING_CHROME_PATH` and `LODGING_CHROME_NODE` override discovery. The native process uses the developer machine's network rather than the container's proxy isolation.

The collector shares the MCP admission lock with other browser tools, returns `busy` immediately on contention, caps each collection at 45 seconds and output at 2 MiB, and reaps its owned process group and profiles before releasing admission. Browser children receive no provider keys. NOL name/address/body identity, page type, quoted facility evidence and dated review grounding are still required. A partial/error page contributes no facts. Candidate category hints affect search order only, never prove lodging conditions. Verification uses at most 12 candidates sequentially within the existing 90-second budget, reserving time for interpretation and stopping on the first match. Successful verification may use the 6-hour cache; collection or interpretation failures do not populate it. DOM text is reused rather than fetched again over HTTP.

Fixed browser sleeps have been replaced by bounded DOM readiness and stable rendered snapshots. The detail fast path waits for address, facilities and usage sections; layouts without the latter headings retain a conservative settling window and the same identity validation. This changes waiting behavior, not the total timeout, candidate limit or model. The condition model selects short source line ranges rather than rewriting quotes or regenerating already validated identity/type/rating. Invalid ranges and ungrounded review quotations remain unverified.

Validated public snapshots also use the `lodging_pages` cache alias, keyed by candidate ID/name/address with an absolute six-hour expiry. The default file cache lives under private `backend/.cache/lodging-pages`, outside static/media, bounded to 256 entries and shared by workers using the same filesystem. Separate hosts need a deliberately configured shared backend to share hits. Cached snapshots are revalidated before use; failed/partial snapshots are never cached. Changed user conditions run a new assessment of the same unexpired source. Condition-result cache lifetime cannot exceed the source expiry, including time spent interpreting it. An interpretation failure can still leave a valid raw snapshot reusable for retry.

Explicit itineraries retrieve only relevant place categories; a game-and-stay itinerary skips unrelated restaurant/cafe/tourism embeddings and retrieval. Internal course artifacts contain `course_timing` for stage diagnosis without adding these fields to public course JSON. See the [latency and quality verification](test_results/lodging-latency-20261011.md) for full chat timings and remaining model latency.

For `NEW` requests, `course.creation` interprets visits and lodging requirements in one compact structured response using the existing model. Required/excluded/optional conditions and detail/review evidence types still pass through the same lodging validators. Parser/schema failure falls back to the full interpreter; edits and selected-place continuations keep their existing path. Only positively identified course-only requests with one successful `ask_course` result, a valid public course, no attachments and no additional questions/tools can skip the final rewrite. Every original course warning/link is retained, with a deterministic past-date note when applicable. Mixed requests, explanations, comparisons and special output formats keep the existing main answer model. See the [second latency verification](test_results/course-latency-round2-20261011.md) for actual end-to-end results and the effect of source failures.

New-course interpretation now overlaps one bounded worker reading the schedule, stadium and explicitly requested raw place candidates. The caller retains model/evidence/policy mutations; prepared data is matched to the exact question, stadium and current date, and worker DB connections are closed before return. Missing reads use the existing lookup path. An omitted or combined explicit hotel/motel type in the compact interpretation triggers the existing dedicated requirement extractor instead of silently weakening that condition.

Compose also runs `lodging-warmer` (`warm_lodging_cache --loop`) against the shared private page cache. It prefers recently used public properties and bootstraps two candidates per configured stadium, attempting at most six collections within a 180-second pass, then waiting 15 minutes. Snapshots with over 30 minutes of validity are skipped; only a new validated read starts a new six-hour expiry. Failed refreshes preserve the old snapshot and its original expiry. Approximate demand stores only public candidate identity, counts and last-use time, capped to 128 properties/seven days; it never changes course ranking. Set `LODGING_WARM_STADIUMS=JAMSIL,SAJIK` to narrow the default all-stadium scope, or `docker compose stop lodging-warmer` to stop warming. No search/condition model runs in the warmer.

The authenticated `chrome_lodging` tool accepts `background=true` for the warmer. Foreground Chrome/JEV requests cancel background collection and wait for owned process/profile cleanup before admission. If cleanup exceeds three seconds, the caller gets the existing busy response instead of overlapping Chrome processes. Background requests never cancel foreground work and defer on contention. The warmer requires MCP transport for this priority contract. The backend image excludes private `.cache` files. See the [parallel/prefetch verification](test_results/course-latency-round3-20261011.md) for live cache sharing, real preemption and mixed-question checks.

The selected lodging's condition verdicts also reach the main model as private tool context, so it can preserve verified/unknown distinctions instead of inferring them from link-only cards. Source quotes and internal assessment fields are excluded from public course JSON; the existing lodging card format remains unchanged. The main model is instructed to preserve the original URL and not infer free parking or booking availability.

Offline tests: `llm.tests.test_lodging_chrome` and `docker/jev-browser/test_chrome_lodging.py`. The existing request-summary tracing applies to `jev_browse` and `jev_read_body`; `chrome_lodging` does not add raw-body traces. See the [local integration results](test_results/lodging-chrome-integration-20261011.md) for real collection and course creation, including limits of that validation.

Upstream is [jev-browse v0.16.0](https://github.com/0x7067/jev-browse/tree/07c2dce0983181d6b2fee3dbdc8b892dae562656), fixed SHA `07c2dce0983181d6b2fee3dbdc8b892dae562656`. OpenRouter's original TypeSafe systemOne decision protocol is unchanged. One explicit local source patch (`docker/jev-browser/patch-helper.mjs`) changes only `src/model/text.ts`: official `api.openai.com` helper requests use `reasoning_effort=low` and `max_completion_tokens=1024` instead of OpenRouter's `reasoning` object and legacy `max_tokens`; other helper providers retain upstream behavior. Build asserts unique pinned patch context, installs the pinned upstream npm lock with `npm ci --ignore-scripts`, runs four offline actual-helper request checks, and rebuilds both bundles using upstream esbuild scripts. The research specialist uses the Responses API with low reasoning, as gpt-6-luna function tools with reasoning are rejected by Chat Completions. Custom research endpoints must support the OpenAI Responses API; the browser text helper still uses Chat Completions. Official Python MCP FastMCP provides Streamable HTTP; `langchain-mcp-adapters` discovers and invokes its tool on demand. Existing synchronous agent streaming is preserved: the synchronous research tool runs its own short-lived async MCP session, never sharing loop-bound sessions or doing discovery during imports.

MCP requires a shared runtime `JEV_MCP_TOKEN` in the backend and browser service. The backend sends an Authorization Bearer header; the service rejects missing, wrong or non-Bearer credentials with 401 before MCP handling. An empty token prevents service startup and backend browser invocation (no unauthenticated fallback). Set it privately in runtime configuration; never commit or print it. HTTP access logging is disabled. This authenticates the backend service, not individual application users; existing application allowlists still govern delegation.

Upstream stdout is read incrementally with a fixed 1 MiB bound. Overflow returns `upstream_stdout_limit_exceeded`, never a silently truncated answer, and kills/reaps the process group and removes the owned temporary root before releasing admission.

URL attachment registration remains metadata-only. After the scope guard, within the existing metered turn, deterministic `web_body` calls `jev_read_body` rather than letting an LLM decide whether to fetch. It returns the genuine visible rendered DOM `document.body.innerText` snapshot and actual browser location, not generated `final_text`, original HTML, hidden text, infinite-scroll content or a claim to have read every page. Chromium uses a disposable sandboxed profile and the existing mandatory Squid/firewall path for redirects/subresources. The new `read-body.mjs` uses Node's built-in WebSocket/CDP, no added dependency/provider call. Busy/blocked/partial/timeout/overflow return no body; there is no silent truncation. Successful full snapshots enter existing attachment byte/token/window boundaries and only then cache in `extracted_text`; failed/cancelled/over-limit turns never cache a partial body. Cached snapshots are reused, not freshness guarantees.

One execution is admitted at both the sync specialist boundary and MCP boundary; concurrent calls receive `busy` (zero waiting queue). Run timeout defaults to 120 seconds, at most 40 upstream steps; cancellation/timeout kills the CLI and Chrome process group before releasing the lock. Every run gets a disposable profile, no shared cookies or user credentials. Child TMPDIR/TMP/TEMP point to an owned subdirectory of that request root, so upstream Node tmpdir-based CDP downloads are removed on success, timeout and cancellation without global glob deletion. Browser progress stderr is not forwarded because it may contain page data.

Squid validates resolved destinations on proxy requests, including redirects/subresources. IPv4/IPv6 firewall rules allow external connections only by Squid's uid; browser and Node cannot bypass the proxy. Chromium has loopback proxy bypass disabled and QUIC disabled. Only HTTP/HTTPS ports 80/443 are allowed; localhost, private, link-local, Docker internal, CGNAT, multicast and reserved networks are denied. Bootstrap needs NET_ADMIN to install rules and fails closed; MCP/CLI/Chrome run as `node` with capabilities dropped. Chromium sandbox remains enabled; no `--no-sandbox` fallback is provided. The checked-in seccomp policy is Moby's standard profile with only clone/unshare/setns additionally allowed for Chromium's non-root namespaces; no SYS_ADMIN or privileged mode is granted. Hosts disallowing Linux sandbox namespaces cannot run this service until their container sandbox configuration is reviewed.

Offline lifecycle checks: `python docker/jev-browser/test_server.py`. Actual loopback MCP auth/overflow checks with backend dependencies installed: `PYTHONPATH=backend python docker/jev-browser/test_auth_output.py` (no paid APIs; tests use a fixed non-secret credential and an ephemeral local port). Real downloaded-sentinel cleanup regression (no paid APIs) after building an image tagged `jev-browser-check`: `docker run --rm --user node --security-opt seccomp=./docker/jev-browser/seccomp.json --entrypoint python -v "$PWD/docker/jev-browser:/checks:ro" jev-browser-check /checks/test_download_cleanup.py`. These do not prove browser navigation or provider availability. Paid API/live browser verification must be reported separately, including actual provider errors; never treat a successful MCP response containing upstream failure as successful research.
